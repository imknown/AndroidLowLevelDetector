# 10-分析细则

> **状态**: **living**, 是 [02-工作原则](02-工作原则.md) 那条验证顺序的细则部分, 收 analyze-file 和 Kotlin LSP 两条验证通道的契约;  
> 规划用的查询通道在最后一节, 有它自己的契约.  
> 要按 `android studio analyze-file` 的结果下判断之前, 先读这份.  
> 02 里留下的是顺序, 这份文件留下义务本身: 每批编辑之后, 每个改动过的文件都要跑一遍验证通道;  
> 规划通道的义务在它自己那一节.

`android studio analyze-file` 驱动一个*正在运行*的 Android Studio 实例, 一次只看一个文件, 报它当下的检查结果.  
它报的是这几类: 编译错误, 各个 Severity 级别的 IDE 检查 (Warning / WeakWarning / Info), Android Lint,  
还有已装插件做的检查. 这个范围比 JetBrains Kotlin LSP 报的更宽, JetBrains 那份包含在内.  
它没有语言分析覆盖的类型是例外: Android Studio 基于 IDEA Community, 不带 JS 插件,  
2026-11-08 实测, 一个带语法错误的哨兵 `.js` 只回了行分隔符这类文件级检查, 语法错误一条没报.  
对 JS 的验证靠 `node --check` 加真实运行; analyze-file 对它们只给文件级检查  
(仓库现有 `.js` 每个都带着一条行分隔符警告, 是常态, 不按发现处理).

## 用法

```bash
android studio analyze-file --project=AndroidLowLevelDetector <path>
```

- 路径写相对当前目录的, 也可以写绝对路径. 一次运行只收一个文件.
- 同时开着多个 Android Studio 实例时, 加上 `--pid=<pid>`.
- Android Studio 能分析的东西都能查, 包括它的已装插件检查的内容.

## 前提条件

- 这个命令自身不带任何分析器, 它问的是一个正在运行的 Android Studio. 所以项目必须先在它里面打开.
- 一份结果值不值得读, 看 `android studio check` 有没有把项目列成 `READY`.  
  没有任何实例打开了这个项目时, 运行会失败. 这时候要请负责人打开 Android Studio 和这个项目.

## 在验证流程里的位置

验证的完整顺序 (自审 → analyze-file → Kotlin LSP → Gradle 三档 → 委派到新上下文的 review) 以 [02-工作原则](02-工作原则.md) 那条为准;  
这份文件写验证两条通道的契约. 每个改动过的文件都要跑 analyze-file, 每个改过的 `.kt` 文件都要跑 Kotlin LSP.

验证顺序的五段从左到右, 每段管多大范围:

```mermaid
flowchart LR
    A[自审] --> B[analyze-file 每个改动过的文件]
    B --> C[Kotlin LSP 每个改过的 .kt]
    C --> D[Gradle 三档 整批改动]
    D --> E[review 委派到新上下文]
```

这么排有理由. analyze-file 排最前, 因为它几秒就回, 读的是 IDE 的实时状态, 一眼就能看出来的问题不用等慢的.  
Kotlin LSP 排第二, 因为它把一个文件的每处编译类发现逐处列出来, analyze-file 做不到; 而且它自己要做一次 Gradle 导入,  
比 IDE 那次检查贵. Gradle 那几档排最后, 因为它们的活儿就是把编译类发现在整批改动上再讲一遍.

Gradle 那几档代替不了 analyze-file, 两边只部分重叠. Gradle 档管这批能不能编译, 加编译器警告和 Android Lint,  
有时也带出自己的语法级警告. analyze-file 补上 IDE 检查的其余部分: 各个 Severity 级别的用法发现, 还有已装插件的检查.  
这些内容一次编译成功的 Gradle 构建永远看不到. 所以 analyze-file 这条义务对每个改动过的文件都成立, 资源文件也算.  
跳过它是真的少了一块覆盖, 不是白跑第二遍.

编译类发现的完整清单来自 Gradle 那几档: 它们答的是和 Kotlin LSP 同一类发现, 但覆盖整批改动,  
每条一个 `Problem found:` 块, 每块带一行 `Location:`.  
Kotlin LSP 是这件事的单文件通道: `node scripts/kotlin-lsp-diagnostics.js <file>` 列出这个文件每一处编译和语义发现.  
analyze-file 做不到逐处列全 (原因见下面那条截断).

## 读结果

- 退出码不是结论. 一次打印出 `ERROR` 条目的运行照样退出 0; 退出 1 只说明调用失败了,  
  也就是没有实例打开这个项目, 或者文件不存在.
- 要看打印出来的 `ERROR` / `WARNING` / `INFO` 块 (analyze-file 的 Severity 是 IDE 的三级: Warning / WeakWarning / Info), 每块都带行号和列号.
- 检查级别的发现 (比如 "Use destructuring declaration") 按语法警告处理: 直接改掉, 不写进文档.

## 结果为什么可能不完整

- **同一个文件里, 一条消息文本只回来一次.** 当同一个文件里两条发现带着同一条消息文本时,  
  analyze-file 回的只有第一条, 所以 N 条发现不等于 N 处位置:  
  当你把报出来的那处改好时, 下一处才冒出来.  
  这条规则看的是消息文本, 不是检查项. 当同一个文件里的几条发现文本各不相同时, 它们会全回来,  
  比如三条 `Property "alpha" / "beta" / "gamma" is never used`, 因为名字各不相同;  
  当同一个文件里的几条发现文本一模一样时, 只有第一条回来,  
  比如四条 `Unnecessary non-null assertion (!!)`.  
  编译错误也一样: 当一个文件里有两条 `Unresolved reference 'missingSymbolOne'.` 时, 只回来一条.  
  全仓实测过: 74 个 Kotlin 文件, 245 条诊断, 没有一个文件里出现过两条文本相同的条目.  
  截断是 IDE 做的, 不是 CLI 做的: CLI 只打印 IDE 交给它的列表.  
  当文件开在编辑器里时, 结果和它关着时一样, 所以开在编辑器里不是原因.  
  当你要数位置时, 你应在源码里数, 不要在一次运行的输出里数.
- **没索引的文件会打印一个假的 `No issues found!`**, 而且仍然退出 0. 本次会话新建的文件,  
  Android Studio 索引到它之前一直是看不见的. 所以别把这份沉默当成通过, 等索引追上之后再重跑一遍.  
  `--project` 点名路径之外的文件, 同样看不见.
- **Android Studio 已经认识的文件, 一编辑就立刻分析**, 那边不用等.

## 另一条通道: 逐处列出的编译与语义发现

`android studio analyze-file` 报的是 IDE 检查项, Android Lint 和已装插件的检查, 上面那条截断对它们全都成立.  
JetBrains Kotlin LSP 是第二条通道. 它报一个文件的编译和语义发现, 每一处都给出, 从不截断.  
两边在编译类发现上重叠, 在检查项上不一样: Kotlin LSP 报的检查项范围更窄,  
`Function name 'ProbeOne' should start with a lowercase letter` 这类它会报,  
`Unused import directive` 和未使用声明那类它不报. analyze-file 报的是完整的检查项范围.

驱动 Kotlin LSP 验证通道的是 `scripts/` 下两个脚本 (规划用的第三个脚本在下面一节):

```bash
node scripts/kotlin-lsp-diagnostics.js <path-to-kotlin-file>   # 一个文件的发现
node scripts/kotlin-lsp-selfcheck.js                            # 分析器是不是真的看得见工程
```

- **工程根目录由脚本自己的位置推出来**, 所以这些脚本必须待在仓库根下面一层, 也就是 `scripts/`.  
  把副本挪到别处跑, 它分析的就是工程模型之外的文件, 回答 `CLEAN (0 items)`.
- **服务端从环境变量里找**: `KOTLIN_LSP_SERVER` (到 `intellij-server` 的完整路径),  
  `KOTLIN_LSP_HOME` (发行版根目录, 于是用 `<root>/bin/intellij-server`), 或者 `PATH` 上的 `intellij-server`.
- **索引缓存在 `<repo>/.kotlin/lsp-cache/<process.platform>`** (已 gitignore).  
  按平台分开存, 因为每个平台跑自己的发行版. 预热这样跑:  
  `<发行版>/bin/warmup.py <repo> <repo>/.kotlin/lsp-cache/<process.platform> --build-tool gradle`.  
  冷索引要几分钟, 可能顶不过 ready 超时; 热索引一分钟内就有答案.
- **Kotlin LSP 的 Gradle 同步跑在 `JAVA_HOME` 指的那个 JDK 上**. 这个 JDK 不能低于工程的 Java 工具链,  
  就是 `gradle/toml/build.toml` 里的 `javaToolchain`. 场景组:

  场景: JAVA_HOME 低于工程工具链  
  Given Kotlin LSP 的 Gradle 同步跑在 `JAVA_HOME` 指的那个 JDK 上, 且这个 JDK 低于 `javaToolchain`  
  When Kotlin LSP 做一次 Gradle 导入  
  Then 导入以 `Dependency requires at least JVM runtime version ...` 失败, Kotlin LSP 退成一个不完整的工程模型,  
  可它照样回答诊断, 于是这次运行打印出一个假的 `CLEAN`

  原因: `:build-logic:convention` 这个 included build 是按那个工具链的字节码版本编译的,  
  更老的构建 JVM 装不动这些约定插件.

  场景: 预热或者诊断之前  
  Given 工程的 Java 工具链就是 `gradle/toml/build.toml` 里的 `javaToolchain`  
  When 你要跑预热或者诊断  
  Then 你应先把 `JAVA_HOME` 指到不低于那个版本的 JDK

  Kotlin LSP 发行版自带一个同版本的 JetBrains Runtime (JBR), 在 `<发行版>/jbr` 下面.

  场景: 命令行发起的构建  
  Given 你用 `./gradlew` 发起一次构建  
  When Gradle 为这次构建选 daemon JVM  
  Then daemon JVM 取自 `gradle/gradle-daemon-jvm.properties`, 那里把它钉在工具链版本上,  
  并让 Gradle 自己 provision, 所以那条路上 `JAVA_HOME` 不决定 JVM.
- **自检用来分清"分析器没有工程模型"和"代码没问题"**, 场景如下:

  场景: 自检跑完, 哨兵上拿到 CLEAN  
  Given 自检往一个源码根写一个临时哨兵文件, 里面带一条已知的警告, 要求那条警告回来, 然后把哨兵删掉  
  When 自检跑完, 哨兵上拿到 `CLEAN`  
  Then 说明同步失败了, 不是说代码干净
- **退出码** 三个取值各对应一个场景. 场景组:

  场景: 拉取成功而且没有 ERROR 条目  
  Given 一次 Kotlin LSP 运行结束  
  When 拉取成功, 而且没有 ERROR 条目  
  Then 退出码只有这时才是 0

  场景: 运行失败或者有任何 ERROR 条目  
  Given 一次 Kotlin LSP 运行结束  
  When 运行失败 (指诊断拉取本身没成; shutdown ack 丢失不算), 或者有任何 ERROR 条目  
  Then 退出码是 1

  场景: 被打断  
  Given 一次 Kotlin LSP 运行结束  
  When 运行被打断  
  Then 退出码是 130 或 143

  退出码不管同步这件事, 所以要配上自检, 才能相信一份 `CLEAN`.
- **这个检查只管 `.kt`**: Kotlin LSP 不给 `.kts` Gradle 脚本建模型, 所以脚本在这种文件上会直接失败,  
  不会打印一份空的 `CLEAN`. 构建脚本要用 Gradle 构建本身来验.
- **Kotlin LSP 对 test 源集的测试依赖不可信**: 对测试源集里的 Kotlin 文件, 它把测试依赖的导入与引用  
  报成 UNRESOLVED (2026-11-07 实测: app 的 `MyModelTest.kt` 与 base 的 `DateTimeExtTest.kt`,  
  都是已提交且 Gradle 全绿的文件, 同样报; 机制未查明).  
  所以测试文件的编译类发现以 Gradle 的单测任务为准, Kotlin LSP 对它们既给不出可信的 CLEAN,  
  报出来的脏也不能当真.
- `KOTLIN_LSP_READY_TIMEOUT_MS` (默认 1800000) 和 `KOTLIN_LSP_CALL_TIMEOUT_MS` (默认 180000) 管两处等待, 给慢的机器用.

## 规划阶段的查询通道: kotlin-lsp-plan.js

前两条通道都是验证通道, 管写完之后的每批编辑. `scripts/kotlin-lsp-plan.js` 是写给写代码之前的规划阶段的:  
查一个符号谁在用, 定义在哪, 谁调用它, 不用 grep 猜引用. 它和验证通道共用同一份 Kotlin LSP server  
与索引缓存, server 的查找顺序, 索引预热和 `JAVA_HOME` 工具链的前提全部照 `另一条通道` 一节, 不复述.

### 用法

一次运行收一批查询, 同一次 server 会话里全查完:

```bash
node scripts/kotlin-lsp-plan.js "<file>:<line>:<col>:<method>" "<file>:symbols" "<file>:diagnostics" "wsymbol:<text>"
```

- token 从右往左按冒号切, 所以 Windows 盘符 (`D:\...`) 不受影响.
- `<line>` 和 `<col>` 都从 1 起, 和编辑器状态栏一致; 输出每条一行 `path:line:col`, 行列号同样从 1 起  
  (workspace/symbol 命中的 jar 内符号, 以及当前平台转不成文件路径的 URI,  
  那一行打原始 URI 接行列号, 再接 `kind=` 和符号名).
- `wsymbol` 的查询文本带空格时, 用引号包住整个 token.
- 批量里只有 `wsymbol` 查询时, 脚本遍历仓库里路径形如 `src/main/java|kotlin` 的目录 (跳过 build 等目录),  
  找第一个含 `.kt` 的当就绪哨兵.

方法清单:

| 查询 | 问什么 |
|---|---|
| `references` | 谁在用这个符号, 声明不计 |
| `definition` | 这个引用的定义在哪, 跨文件跳 |
| `typedef` | 这个符号的类型 |
| `implementation` | 这个符号的实现 |
| `hover` | 这个位置的类型与文档 |
| `calls-in` | 谁调用它 (incoming call hierarchy) |
| `calls-out` | 它调用谁 (outgoing call hierarchy) |
| `type-super` / `type-sub` | 类型的父类 / 子类 |
| `symbols` | 文件的符号结构 |
| `diagnostics` | 这个文件的诊断, 全部级别 |

### 读结果与坑

- **severity 四级分开打印, 不折叠**: 两条通道都打 `ERROR` / `WARNING` / `INFORMATION` / `HINT`,  
  协议外的值逐条打 `UNKNOWN(n)`, 计数归进汇总行的 UNKNOWN 桶. LSP 与它背后的 IntelliJ 分级体系里  
  都没有 Fatal 和 Critical; 实测值域是 1 和 2 (2026-11-08 全仓探针), 3 与 4 按协议保留位次.
- **`intellij/ready-for-test` 信号不可信**: didOpen 的文本带编译错误时, 这个通知可能永远不回  
  (2026-11-08 两例实测挂死). 所以规划脚本不等它, 改为轮询 `documentSymbol` 非空判定就绪. 场景组:

  场景: 哨兵判定就绪  
  Given kotlin-lsp-plan.js 打开查询涉及的每个文件, 轮询每个文件的 `documentSymbol`  
  When 全部返回非空  
  Then 判定就绪, 开始执行查询; 超时 (默认 300000ms) 则报 `no project model` 并失败

- **type hierarchy 实测为空**: 对 Kotlin 类, `prepareTypeHierarchy` 回空 (ILS-263.7084.0 实测),  
  脚本打印 `(none: ...)` 带原因, 不是脚本没查.
- **超时两个环境变量**: `KOTLIN_LSP_PLAN_READY_TIMEOUT_MS` (默认 300000) 和 `KOTLIN_LSP_CALL_TIMEOUT_MS` (默认 180000),  
  给慢的机器用. READY 预算是规划通道自己的变量, 与验证通道的 `KOTLIN_LSP_READY_TIMEOUT_MS` (默认 1800000) 分开:  
  验证通道的预算按冷索引给; 规划通道通常在热缓存下跑, 默认值按热缓存给, 缓存不在时它同样冷索引,  
  会超出这个默认预算.
- **退出码**: 0 仅当运行成功且没有 `diagnostics` 查询回 ERROR 级条目; 运行失败或有 ERROR 条目时 1;  
  被打断时 130 或 143. WARNING 及以下照打印, 不拦, 和验证顺序那条的口径一致.
- **与诊断通道互斥**: 和 kotlin-lsp-diagnostics.js 共用同一把锁 (`<repo>/.kotlin/lsp-cache/<平台>.lock`),  
  两个脚本不能同时跑.
