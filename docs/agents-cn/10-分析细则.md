# 10-分析细则

> **状态**: **living**, 是 [02-工作原则](02-工作原则.md) 那条验证顺序的细则部分, 收 analyze-file 和 ILS 两步的契约.  
> 要按 `android studio analyze-file` 的结果下判断之前, 先读这份.  
> 02 里留下的是顺序, 这份文件留下义务本身: 每批编辑之后, 每个改动过的文件都要跑一遍.

`android studio analyze-file` 驱动一个*正在运行*的 Android Studio 实例, 一次只看一个文件, 报它当下的检查结果.  
它报的是这几类: 编译错误, 各个 Severity 级别的 IDE 检查 (Warning / WeakWarning / Info), Android Lint,  
还有已装插件做的检查. 这个范围比 JetBrains IntelliJ Language Server 报的更宽, JetBrains 那份包含在里面.

## 用法

```bash
android studio analyze-file --project=AndroidLowLevelDetector <path>
```

- 路径写相对当前目录的, 也可以写绝对路径. 一次运行只收一个文件.
- 同时开着多个 Android Studio 实例时, 加上 `--pid=<pid>`.
- Android Studio 能分析的东西都能查, 包括它的已装插件检查的内容.

## 前提条件

- 这个命令自身不带任何分析器, 它问的是一个正在运行的 Android Studio. 所以项目必须先在它里面打开.
- 一份结果值不值得读, 看 `android studio check` 有没有把项目列成 `READY`.  
  没有任何实例打开了这个项目时, 运行会失败. 这时候要请负责人打开 Android Studio 和这个项目.

## 在验证流程里的位置

验证的完整顺序 (自审 → analyze-file → ILS → Gradle 三档 → 新上下文 review) 以 [02-工作原则](02-工作原则.md) 那条为准;
这份文件写前两步 (analyze-file 和 ILS) 的契约. 每个改动过的文件都要跑 analyze-file, 每个改过的 `.kt` 文件都要跑 ILS.

这么排有理由. analyze-file 排最前, 因为它几秒就回, 读的是 IDE 的实时状态, 一眼就能看出来的问题不用等慢的.  
ILS 排第二, 因为它把一个文件的每处编译类发现逐处列出来, analyze-file 做不到; 而且它自己要做一次 Gradle 导入,  
比 IDE 那次检查贵. Gradle 那几档排最后, 因为它们的活儿就是把编译类发现在整批改动上再讲一遍.

Gradle 那几档代替不了 analyze-file, 两边只部分重叠. Gradle 档管这批能不能编译, 加编译器警告和 Android Lint,  
有时也带出自己的语法级警告. analyze-file 补上 IDE 检查的其余部分: 各个 Severity 级别的用法发现, 还有已装插件的检查.  
这些内容一次编译成功的 Gradle 构建永远看不到. 所以 analyze-file 这条义务对每个改动过的文件都成立, 资源文件也算.  
跳过它是真的少了一块覆盖, 不是白跑第二遍.

编译类发现的完整清单来自 Gradle 那几档: 它们答的是和 ILS 同一类发现, 但覆盖整批改动,  
每条一个 `Problem found:` 块, 每块带一行 `Location:`.  
ILS 是这件事的单文件通道: `node scripts/ils-diagnostics.js <file>` 列出这个文件每一处编译和语义发现.  
analyze-file 做不到逐处列全 (原因见下面那条截断).

## 读结果

- 退出码不是结论. 一次打印出 `ERROR` 条目的运行照样退出 0; 退出 1 只说明调用失败了,  
  也就是没有实例打开这个项目, 或者文件不存在.
- 要看打印出来的 `ERROR` / `WARNING` / `INFO` 块, 每块都带行号和列号.
- 检查级别的发现 (比如 "Use destructuring declaration") 按语法警告处理: 直接改掉, 不写进文档.

## 结果为什么可能不完整

- **同一个文件里, 一条消息文本只回来一次.** 两条发现带着同一条消息文本时, 只有第一条回来.  
  所以 N 条发现不等于 N 处位置: 把报出来的那处改好, 下一处才冒出来.  
  这条规则看的是消息文本, 不是检查项. 三条 `Property "alpha" / "beta" / "gamma" is never used` 会全回来,  
  因为名字各不相同; 四条 `Unnecessary non-null assertion (!!)` 只回来一条, 因为四条文本一模一样.  
  编译错误也一样: 一个文件里两条 `Unresolved reference 'missingSymbolOne'.` 只回来一条.  
  全仓实测过: 74 个 Kotlin 文件, 245 条诊断, 没有一个文件里出现过两条文本相同的条目.  
  截断是 IDE 做的, 不是 CLI 做的: CLI 只打印 IDE 交给它的列表. 文件开在编辑器里和关着, 结果一样,  
  所以开在编辑器里不是原因. 数位置要在源码里数, 不要在一次运行的输出里数.
- **没索引的文件会打印一个假的 `No issues found!`**, 而且仍然退出 0. 本次会话新建的文件,  
  Android Studio 索引到它之前一直是看不见的. 所以别把这份沉默当成通过, 等索引追上之后再重跑一遍.  
  `--project` 点名路径之外的文件, 同样看不见.
- **Android Studio 已经认识的文件, 一编辑就立刻分析**, 那边不用等.

## 另一条通道: 逐处列出的编译与语义发现

`android studio analyze-file` 报的是 IDE 检查项, Android Lint 和已装插件的检查, 上面那条截断对它们全都成立.  
JetBrains IntelliJ Language Server (ILS) 是第二条通道. 它报一个文件的编译和语义发现, 每一处都给出, 从不截断.  
两边在编译类发现上重叠, 在检查项上不一样: ILS 报的检查项范围更窄,  
`Function name 'ProbeOne' should start with a lowercase letter` 这类它会报,  
`Unused import directive` 和未使用声明那类它不报. analyze-file 报的是完整的检查项范围.

驱动 ILS 的是 `scripts/` 下两个脚本:

```bash
node scripts/ils-diagnostics.js <path-to-kotlin-file>   # 一个文件的发现
node scripts/ils-selfcheck.js                            # 分析器是不是真的看得见工程
```

- **工程根目录由脚本自己的位置推出来**, 所以这两个脚本必须待在仓库根下面一层, 也就是 `scripts/`.  
  把副本挪到别处跑, 它分析的就是工程模型之外的文件, 回答 `CLEAN (0 items)`.
- **服务端从环境变量里找**: `KOTLIN_LSP_SERVER` (到 `intellij-server` 的完整路径),  
  `KOTLIN_LSP_HOME` (发行版根目录, 于是用 `<root>/bin/intellij-server`), 或者 `PATH` 上的 `intellij-server`.
- **索引缓存在 `<repo>/.kotlin/lsp-cache/<process.platform>`** (已 gitignore).  
  按平台分开存, 因为每个平台跑自己的发行版. 预热这样跑:  
  `<发行版>/bin/warmup.py <repo> <repo>/.kotlin/lsp-cache/<process.platform> --build-tool gradle`.  
  冷索引要几分钟, 可能顶不过 ready 超时; 热索引一分钟内就有答案.
- **ILS 的 Gradle 同步跑在 `JAVA_HOME` 指的那个 JDK 上**. 这个 JDK 不能低于工程的 Java 工具链,  
  就是 `gradle/toml/build.toml` 里的 `javaToolchain`.  
  `:build-logic:convention` 这个 included build 是按那个工具链的字节码版本编译的, 更老的构建 JVM 装不动这些约定插件.  
  导入会以 `Dependency requires at least JVM runtime version ...` 失败, ILS 退成一个不完整的工程模型,  
  可它照样回答诊断, 于是这次运行打印出一个假的 `CLEAN`.  
  预热或者诊断之前, 先把 `JAVA_HOME` 指到不低于那个版本的 JDK.  
  ILS 发行版自带一个同版本的 JetBrains Runtime (JBR), 在 `<发行版>/jbr` 下面.  
  命令行发起的构建是另一回事: `./gradlew` 的 daemon JVM 取自 `gradle/gradle-daemon-jvm.properties`,  
  那里把它钉在工具链版本上, 并让 Gradle 自己 provision, 所以那条路上 `JAVA_HOME` 不决定 JVM.
- **自检用来分清"分析器没有工程模型"和"代码没问题"**: 它往一个源码根写一个临时哨兵文件, 里面带一条已知的警告,  
  要求那条警告回来, 然后把哨兵删掉. 哨兵上拿到 `CLEAN`, 说明同步失败了, 不是说代码干净.
- **退出码** 只有在拉取成功而且没有 ERROR 条目时才是 0; 运行失败或者有任何 ERROR 条目是 1; 被打断是 130 或 143.  
  退出码不管同步这件事, 所以要配上自检, 才能相信一份 `CLEAN`.
- **这个检查只管 `.kt`**: ILS 不给 `.kts` Gradle 脚本建模型, 所以脚本在这种文件上会直接失败,  
  不会打印一份空的 `CLEAN`. 构建脚本要用 Gradle 构建本身来验.
- `ILS_READY_TIMEOUT_MS` (默认 1800000) 和 `ILS_CALL_TIMEOUT_MS` (默认 180000) 管两处等待, 给慢的机器用.
