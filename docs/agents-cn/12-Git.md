# 12-Git

> **状态**: **living**. 这套规则文件的入口在根 [AGENTS.md](../../AGENTS.md), 编号和阅读时机见那份索引.

## Git

- PR 打到 `develop`, 它是默认分支. 提交信息按 Conventional Commits 走, **类型 + 作用域用小写**:  
  `fix(home): ...`.
- 提交信息只写改了什么与为什么, 不写过程日志.
- 每笔提交信息都以一行 trailer 收尾, 写明产出这次工作的 agent, 模型, 还有推理强度级别.  
  级别取值是 `off` / `low` / `medium` / `high` / `xhigh` / `max`, ...  
  写法形如 `Generated with ZCode (GLM-5.3, effort: xhigh)`.  
  `effort:` 就是推理强度这个旋钮本身, 不是对推理好坏的评价. 很早期的提交写的是 `reasoning:`, 那些保持原样.  
  取值绝不猜, 也不许自己写 `unknown`: 先问负责人该记什么, 问法照 [03-工作原则](03-工作原则.md) 的 `决定逐条摆开`.  
  负责人确认这个值确实定不下来之后,  
  `unknown` 才是对的, 是商定过的写法.
- 提交信息一律英语; 语言细则见 [07-代码规则](07-代码规则.md).
  - agent 的名字要拿证据来定, 别按习惯写; 把依据摆出来, 写下去之前先让负责人同意.  
    不同版本级的名字是两回事. `Qoder CN` 和 `Qoder` 就是两个不同的 AI 开发环境 (ADE).  
    负责人没要求, 就别自己加 `IDE` / `CLI` 这种表示宿主形态的后缀.
- 提交按最小可独立编译与验证的单元拆, 不把几个可独立验证的单元并进一笔.  
  单元按可独立编译与验证划, 不按文件数划: 跨文件的同一逻辑改动算一个单元,  
  比如一条诊断输出和核它的自检正则要并进同一笔, 拆开会让中间那笔自检失败;  
  共用骨架与纯新增的辅助各成一笔. 判断拆得够不够细只问一句: 这笔单独拿出去,  
  能不能编译并且验证得起来; 能, 就到此为止, 不能再并进下一件.
- 提交的时机按活分两种: 不走 spec 的普通改动, 同类型的条目先改完 (实现与自查), 一起走 v1 / v2 / v3  
  这样的多轮 review, 提交在 review 结束后按条目拆细, 每个条目单独成笔; spec 流程的执行期,  
  task 就是这里的单元: 一个 task 一笔提交, 自查绿了就提交 (授权见下一条), 总 review 的发现修成新的提交,  
  `3-tasks.md` 里这个 task 的勾选随这笔提交入库. 三份产物经负责人确认后各自自动提交一次  
  (见 13 的三份产物各节).
- spec 流程里, 负责人确认 `3-tasks.md` 那一次同意, 同时授权清单内各 task 的提交, 不逐笔再问;  
  总 review 循环的修复提交视同这份授权的延伸;  
  清单外的提交仍要负责人单独同意; push 和删除的同意永远单独给.  
  授权的边界写在 [13-工作流](13-工作流.md) 的 `确认与接续` 一节.

## 绝不提交

- 凭据, 签名材料, 本地配置 (`local.properties`, `keys/release.jks`, `google-services.json`) 绝不提交,  
  也不许用 `git add -f` 强制加进去. 根 `.gitignore` 已经把它们排除了.
- 一个改动看着非提交这类文件不可时, 先停下来问.
