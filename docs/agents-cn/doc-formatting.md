# 文档排版细则

> **状态**: **living**, 是 [AGENTS-cn.md](../../AGENTS-cn.md) 文档规则那节的细则部分.  
> 写这些东西之前先读它, 改已有的文本时也是: 一份文档, 一条提交信息, 一条代码注释 (文档注释, 行尾注释,  
> 块注释都算), 或者给负责人的一条聊天回复.  
> 禁令写在 AGENTS-cn.md 里. 这份文件收的是禁用词表, 改名对照表, 禁止的句式, 中文的句子规则和翻译腔对照表,  
> CJK 到 ASCII 的映射, 间距例外, 豁免情形, 列表和句子的规则, 长度规则, 重写已有文本的步骤,  
> 还有语言与文件命名的细节.

## 用词要平实

这一节说什么不能写, 该改写成什么. 它管文档, 代码注释, 提交信息, 也给负责人的聊天回复.  
不管你用哪种语言写都适用: 下面的词表是本仓库写出过的写法, 和负责人点过名的写法. 起作用的是判断标准,  
词表不是规则的边界.

三类用词出局:

1. **填充词和缓和语**: 不带任何事实的说法. 删掉这个短语, 再看句子有没有少说一件事: `值得注意的是`,  
   `综上所述`, `不难看出`, `众所周知`, `毋庸置疑`, `至关重要`, `重中之重`, `让我们开始吧`,  
   `在当今快速发展的时代`. 英语: `It is worth noting that`, `In summary`, `As we can see`, `Obviously`,  
   `Needless to say`, `crucial`, `paramount`, `Let us begin`, `In today's fast-moving world`.
1. **营销式形容词**: 一句没人能核对的宣称. 要么说出事实, 要么删掉: `无缝` 该说成 "不需要人工步骤",  
   `强大` 该说这个功能做什么, `健壮` 该说它扛得住哪些失败. 同样出局: `极致`, `颠覆`, `革命性`, `全方位`,  
   `高水平`, `高质量`, `生态`, `赋能`, `抓手`, 以及英语的 `seamless`, `powerful`, `ultimate`, `disruptive`,  
   `revolutionary`, `comprehensive`, `world-class`, `cutting-edge`, `ecosystem`.
1. **把一个工作项, 一次检查, 或者一个决定, 用别的领域的比喻来命名.**  
   起作用的是判断标准, 不是清单: 一个没打开过本仓库文档的人, 能不能读懂这句. 按证据分三组列:
   - 确实写进过本仓库自己的文档: `桶`, `闸门`, `台账`/`账本`, `收口`, `收尾`, `落地`, `尾巴`, `漂移`, `债`,  
     `接缝`, `护栏`, `兜底`, `兜住`, `裁定`, `定夺`, `拍板`, `点头`, `落点`, `门禁`, `地基`, `伸手点`, `保护网`,  
     `沉淀`, `复盘`, `闭环`, `对齐` (表"一致"时), `粒度`, 以及英语的 `bucket`, `gate`, `ledger`, `close-out`, `land`/`landing`,  
     `tail`, `drift`, `debt`, `seam`, `in-flight`, `tempo`.
   - 出现在负责人对 AI 回复的抱怨里, 在本仓库的文件中从没找到过: `顶牛`, `揪出`, `放宽`, `颗粒度`.
   - 同一类失败的英语近亲, 这里还没人写过就先禁掉: `guardrail`, `harness`, `circle back`, `touch base`.

代码自己已经命名的东西, 名字照用: 布局里的 `Alignment`, Gradle 的构建产物,  
`gradle/toml/thirdParty.toml` 里的 Metro artifacts, `PropertyReader` 里那个 placeholder fallback.  
禁的是给一个已经有名字的东西, 另编一个名字.

## 本仓库改过名的术语

living 文档一律用右列. 保住旧写法的只有 `archived/` 目录下的文件名, 例如 `docs/spec/archived/`,  
`docs/dev/issues-cn/archived/` 这类路径. 改掉文件名会把指向它的链接全部弄断.  
归档文件里的标题和其他文字一样, 重写时一起改;  
同一次修改里, 指向它的每个 `](#...)` 锚点和每处正文引用都要一并改掉.  
record 不许改动的是哪些东西, 见 `重写已有文本时不改实质` 一节.  
中列说的是含义, 不是必须照抄的替换词: 能用一句白话说清含义, 就写那一句.

| 已改掉的写法 | 现在生效的写法 | 说的是什么 |
|---|---|---|
| 闸门 (计划闸门, 提交闸门), gate | 确认点, approval point | AI 停下来提问, 负责人给答复的那一处 |
| 台账, 账本, 偏差台账, ledger, deviation ledger | 进度记录, 偏差记录, progress record | `progress.md`, 以及每跳过一步记的那一行 |
| 收敛护栏, convergence guard | review 循环何时停, when the review loop stops | 轮次不再带来新发现时就别再循环 |
| 收尾 (当作阶段名时), close-out | 任务结束, finishing the task | 清空待学习清单, 开那一次横向回顾总结 |
| 裁定, 定夺, adjudicate, rule (动词: 负责人裁的) | 判定哪边错, decide which side is wrong | 负责人定, AI 不替他们定 |
| 点头, nod, say-so | 负责人的明确同意, the owner's approval | 负责人用话说同意 |
| 尾巴, tail | 没做完的部分, leftover part | 本单元里还没做完的工作 |
| 落地, land | 记录, 实现, 完成, 实施, record, implement | 写下来, 或者做出来 |
| 兜底 (当作文档术语), fallback | 失败时怎么做, what to do when it fails | 代码自己有名字时就用那个名字 |
| 漂移, drift | 过期, 不一致, out of date, inconsistent | 代码已经对不上的那句话 |
| 债, debt | 已有的问题, existing problem | 代码该做而没做完的工作 |
| 接缝, seam | 天然的边界, natural boundary | 一份长笔记从哪里切开 |
| 落点 | 归到哪一条, 记在哪一条 | 一个决定或一处修改由哪一条, 哪一步承担 |
| 门禁 | CI 上必须通过的检查 | 会把合入拦下来的那个 CI 检查 |
| 地基, 保护网 | 基础, 防回归的测试与检查 | 主线开工前本来就得先有的东西 |
| 伸手点 | 全局取用点 | 没传参数却任何调用点都能取到的值 |
| 沉淀 (当动词用) | 写成文档, 汇总成文档 | 把知识写下来让它留得住 |
| in-flight, tempo | 进行中的, 还没做完的, 多久要一次同意 | 正在执行的步骤, 以及要同意的频率 |
| 对齐 (表"一致"时) | 一致 | 两处说法讲的是同一件事 |
| 粒度 | 精确到 | 一个取值或一次切分有多细 |

## 禁止的句式

用词干净, 句子照样可能是错的. 下面这些句式在机器写的中英文里最常见, 一律改写成平实的陈述.

- **否定式对比**: `不是 X, 而是 Y`, `并非 X, 而是 Y`, `与其说 X, 不如说 Y`, 以及句子结尾那个短尾巴 (`, 不用猜`).  
  直接说 Y. 禁的是成对的骨架. `X, 不是 Y` 这种收尾否定, 在确实要纠正一个读者会有的误解时可以留,  
  但要说出那个误解是什么, 或者它来自哪里. 这条管的是正在写或正在重做的文本, 跟列表和句子那两条一样.
- **把刚说过的话再说一遍**: `这才是真正的收获`, `记住这句话`, 或者一个列表后面那句"上面列了这些". 删掉.
- **正文之前的铺垫**: `让我们深入看看`, `关键在于`, `闲话少说`. 从正文开始写.
- **跟一个不在场的对手辩论**: `我不是说 X`, `你可能觉得 X, 但其实 Y`, `一个诱人的做法是`. 直接说自己的结论.
- **让事物做人的动作**: `评级把负责人带偏`, `这一列决定范围`, `决定自然就出来了`. 点名是谁在做.  
  确实没有人做时, 就说会发生什么.
- **拔高意义**: `这是一个里程碑时刻`, `尽管困难重重, 它依然蓬勃发展`, `前景光明`. 说出事实, 否则不写.
- **没有出处的权威**: `业内共识`, `研究表明`, `专家认为`. 也不能顺手改成一句没有出处的说法, 就当成事实.  
  写本仓库代码或文档能证明的东西, 或者写 `unknown`.
- **句尾只作评论的分句**: `, 由此可见缺口`, `, 这反映了代价`, `, 凸显了风险`. 把这个意思单独成句, 或者删掉.
- **写改动本身, 不写东西本身**: `本节是为了替代早先的措辞而加的`. 描述现在的状态; 改动本身在 `git log` 里.
- **把动词写成名词**: `做一次校验`, `做一个判定`, `负责它的管理`. 直接用动词: 校验, 判定, 管理.
- **无人称的公文被动**: `由负责人决定`, `予以记录`, `这个值需要被设置`. 说清谁做, 用主动句: 负责人定, 记下来,  
  把这个值设上.
- **照搬原语言的句式和语序**: 译本会带上原文那门语言的语序和句型. 每种语言都有自己的说法, 照那门语言的写.  
  中文, 日文, 法文的副本, 都要读起来像本来就是用各自那门语言写的.
- **句式比意思还复杂**: 从句套从句, 括号套括号, 限定语上面再叠一层限定语. 用最简单的句式把意思说清.  
  一句短句就能说的, 别搭一个长句去说.
- **聊天里的残留**: `希望对你有帮助`, `好问题!`, 还有 `[你的名字]` 这类占位符.
- **装出来的人味**: 编一个第一人称, 编一段经历, 为了假装是人写的而撒 emoji, 故意写错别字,  
  或者为了看着随意而连着写短句. 说人话不等于扮演一个人.  
  聊天里负责人可以要求轻快的语气, 那是他定的; 这套不出现在文档, 注释, 提交信息里.
- **把规定写成聊天腔**: 把一条规定改得像是随口聊天. `必须`, `绝不`, 还有一条例外精确的范围, 都保持原样的精确.

## 中文怎么写

本仓库的中文文档最容易出的毛病, 是用汉字写英文结构, 再压上一层公文腔. 下面这些规则管中文文本.

- **主语和动词先出**: `在 ... 背景下`, `基于 ...`, `通过 ...` 这类前置状语一长串, 会把"谁做了什么"埋起来.  
  先把结论写出来, 再说条件和时间, 让它们挨着要修饰的那个动词.
- **不写长定语**: 把英文的定语从句整块搬到名词前面, 比如 `一个把底层系统特征摊开来看的 Android 应用`,  
  一遍读不下来. 先说这个东西是什么, 描述另起一句.
- **`它`, `该`, `其` 不连着用**: 要么把主语再写一遍, 要么在不会歧义的地方直接省掉.
- **`被` 字句不排成一串**: 连着几个 `被` 字句时, 把动作的发出者写出来.
- **不让标点承担句子该说的东西**: 冒号, 分号, 括号, 或者 `, 也就是 ...` 这种补丁把一段粘在一起,  
  是同一个毛病的另一种表现. 要改的是句子. 只换标点不算改好.
- **不把英文说法逐字译过来**: 中文要读起来像本来就是中文写的.
- **不写公文腔**: 这些话不带来任何信息, 只把句子垫长, 比如 `由 ... 决定`, `予以记录`, `该条目`, `上述`, `此类`,  
  `进行配置`, `需要注意的是`, `一般而言`. 说清是谁做, 直接用动词.
- **词要日常, 力度不许松**: 大白话不等于随便写. `必须` 和 `绝不` 保持原来的力度; 不加 `吧`, `呢` 这类语气词,  
  不写 `咱们`, 不写 `说白了`.
- **句子和段落的长短靠重写来变化**: 不要为了变化把一个句子砍成碎片, 也不要用随机的标点假装变化.

下面这张表列的是本仓库现在就有的翻译腔和公文腔.

| 翻译腔或公文腔 | 背后的英语 | 改写成 |
|---|---|---|
| `住在` | lives in | `写在`, `只放在` |
| `落在` | lands in, sits in | `在`, `归到` |
| `欠` | owes | `必须给`, `需要` |
| `带着 ... 的为什么` | carries the why | `说明 ... 为什么这样定` |
| `摊开来看` | surfaces | `展示`, `读出` |
| `驱动` (一个页面) | drives | `负责`, `管理` |
| `一笔提交信息` | a commit message | `一条提交信息` |
| `两边都不是权威` | neither side is authoritative | `哪边都不能直接信` |
| `一句关于意图的陈述` | a statement of intent | `文档里那句 "当初想这么做"` |
| `这是可验证的事实` | this is a verifiable fact | `查一下就能确认` |
| `由负责人决定` | it is decided by the owner | `负责人定` |
| `这种约定适用时` | where this convention applies | `用到这一条的时候` |
| `错的一侧是代码` | the wrong side is the code | `代码错了` |
| `排在代码之上` | outranks the code | `压过代码` |
| `予以记录` | a record shall be made | `记下来` |
| `该条目`, `其`, `此类`, `上述` | the said entry, the aforementioned | `这个条目`, `它`, `这类`, `上面那几个` |
| `进行配置` | perform the configuration | `配置一下` |
| `需要注意的是` | it should be noted that | 删掉这一句 |

## 任何语言都用 ASCII 标点

中文 (或日文) 文档用英语标点符号, 绝不用 CJK 的: `,` `.` `;` `:` `!` `?` `(...)` `"..."`,  
而不是 `，。；：！（）「」《》`.

一一对应的映射:

| CJK | ASCII |
|---|---|
| `，` `、` | `,` |
| `。` | `.` |
| `；` | `;` |
| `：` | `:` |
| `（）` | `()` |
| `「」` `『』` `《》` | `"` (嵌套时用 `'`) |
| `……` `…` | `...` |

不是标点的字形保持原样: `·` `→` `←`, 示意图里的制表线, 状态 emoji, 还有聊天里的 emoji 和颜文字.  
破折号不做映射: 本文件禁用破折号, 见下一节.

间距按英语来, 两边是什么文字都一样: 一个标记后面还有正文时, 后面留一个空格 (`每个条目, 每次检测`),  
`,` `.;:!?)` 之前不留空格, `(` 和 `"` 内部也不留. 另有两种情形:

- 紧跟在标识符之后的 `(` 是一次调用, 所以那里不留空格 (`collectModels()`).
- 数字之间的 `:` 保持紧挨 (`16:9`, `12:30`).

每一份文档都按这一节来, **frozen**, **record**, **scratch** 的也包括在内: 那里的标点属于排版,  
不是那几种状态要保住的东西. 写新文本或者重做一段时, 把这次编辑碰到的内容一并转换;  
两种语言之间翻译时也要检查标点.

标题的标点和间距决定目录所指向的那个 GitHub 锚点, 所以重排一个标题的间距时,  
要在同一次修改里改写所有解析到它的 `](#...)`.  
显式的 `<a id="...">` 锚点是稳定文本, 永不移动.

## 破折号

任何文档, 代码注释或聊天回复里都绝不把破折号当标点用: 不许有 em dash `—`, 不许有 CJK 破折号 `——`,  
不许有 ASCII 替代品 `--`, 也不许有注释开头或收尾的 `----` 装饰线.  
聊天里的颜文字不是标点, 它带的横线不归本条管.

每一处都看它表示什么关系, 改成等价的词:

| 关系 | 英语 | 中文 |
|---|---|---|
| 一个释义 | `, i.e. ` | `, 即 ` |
| 换个说法再说一遍 | `, that is, ` | `, 也就是 ` |
| 原因, 解释, 列举 | `:` | `:` |
| 两个独立分句 | `;` | `;` |
| 真正的旁白 | `(...)` | `(...)` |
| 平铺直叙地接下去 | `,` | `,` |

各项改成列表时, 冒号保留, 列表接在冒号后面.

在 inline code 里点名这个符号 (本规则自己就这么做) 是这条禁令唯一的例外.

不当标点用的 `--` 是有结构作用的, 保持原样:

- GitHub 锚点里的双连字符 (`../README.md#1--架构与分层`).
- markdown 表格分隔符 (`|---|`).
- XML 注释边界符 (`<!-- -->`).
- 命令行 flag (`--project=...`).
- 后置自减 (`i--`).
- `git ... -- ` 这个选项结束标记.

## 什么时候排成列表

两个或更多并列项, 文字给它们加了标号 (`(a)`, `1)`) 时, 或每一项本身是一个分句时,  
排成列表, 每项一行.  
句子里一串名词, 取值或短语不算枚举, 留在行内 (`off` / `low` / `high`, `read and write`).  
表格单元格里的并列项也留在行内.  
inline code 里引用的例子不触发这条规则.  
过长的项照下面的硬换行规则断行, 但两项绝不共用一行.

改到一段时, 段里的行内枚举跟着一起改. 没碰到的旧段落保持原样.

### 有序列表

有序列表第一项写真实的起始编号, 之后每一项都写 `1.`:  
从 1 开始的清单就是 `1.`, `1.`, `1.`. 从 0 开始的清单第一项写 `0.`.  
编号由渲染器生成, 插入一项时后面的编号不会整体挪动.  
顺序有意义时用编号. 其余情形用项目符号.

## 一句一个意思

一句话只装一个意思, 要用第二个连词才说到最后一个事实时, 拆开.  
英语里是 `and`, 中文里是 "和" 或 "而且".

下面任何一条成立, 就把这句话拆开:

- 一句里有三个以上并列分句.
- 句子说到一半, 主语换了.
- 要读第二遍才能说清谁对谁做了什么.

哪个句式最短还能把意思说全, 就用哪个. 一个主句加一个事实, 好过一个主句上挂三层限定语, 语法再对也一样.

一行的宽度跟着句子走, 见下面的硬换行规则.  
管的是正在写或正在重做的文本, 和列表规则一样.

## 长行按语义硬换行

一行源码太长时, 在句子或分句的边界断行 (以逗号收尾的分句是合法的断点, 但一个很短的分句可以和后面的内容留在同一行;  
短串名词保持在一起). 要点是没有任何一行整体过长, 不是固定宽度.

下面这些绝不断行; 每一项都占一行源码:

- 标题, 链接目标, URL, 代码块, inline code.
- 表格行绝不拆成两行源码, 但一个过长的单元格可以在单元格内部用 `<br>` 换行 (裸换行会破坏表格).

段落, 列表项或引用块内部的每一个换出来的行都以两个尾随空格收尾 (或用 `<br>`), 这样断行在渲染后依然成立;  
每一块的最后一行不带.  
这些空格不能少: 绝不剥掉, 也绝不合并.

代码注释走同一条规则. 和代码写在同一行的注释保持一行, 重排换行时也绝不碰任何不是注释的东西.

换行属于排版, 所以对 **frozen**, **record**, **scratch** 文档同样成立.

## 重写已有文本时不改实质

重写一份已有的文档, 改的是措辞和句子结构, 不是它说的事. 每一次这样的重写都要守下面几条.  
重写 **record** 时同样适用.

1. 逐字保留: 代码块, 命令, 文件路径, 标识符, 版本字符串, URL, 文件名, 以及从界面或另一份文档里引来的原文.
1. 不加事实, 也不减事实. 一条规定保持它原来的力度: `绝不` 还是 `绝不`, 一条例外保住它原本精确的范围.  
   一句划界的话, 重写之后还要划同一条界.
1. 在 record 里, 它说过的事一概不动. 不许改动的那几样, 列在 [AGENTS-cn.md](../../AGENTS-cn.md) 的文档规则开头那段.  
   只有不动这些内容的改写才可以做, 而且动手之前要先问负责人.
1. 保住条目的文件名. 标题可以改; 改了标题, 同一次修改就要把解析到它的每个 `](#...)` 锚点和每处正文引用一并改掉.
1. 不要挑一种读法就把意思不清的句子写下去. 判断不出原来那句话有多强时, 停下来问负责人.
1. 一次只改一个文件, 一个大文件一次改一节. 继续下一份之前, 把新文本和旧文本对着读一遍,  
   确认旧版本里的每条陈述在新版本里都还在, 新版本也没把同一句多写一份.
1. 对着读之后, 再用五项只读对照复核, 每一项都拿改前的文件和改后的文件比:
   - 行内代码的集合: `comm -23` 的输出必须为空, 多出的片段要说明理由.
   - ID 清点: 每条 ID 各出现几次.
   - 结构计数: 标题, 列表项 (缩进的子列表也算), 编号项, 表格行, 引用行各自的行数.
   - 力度词计数: `绝不`, `必须`, `一律`, `只有`, `任何`, `从不`, `恰好` 各自的次数.
   - 重复句扫描: 两句改完逐字一样时, 要说清它们本来就各管一条.
1. 跑五项只读对照之前, 先证明两边都真的读到了文件: 任何一边行数为 0, 就是路径没传进去, 那种绿是假绿.  
   每一处报出来的违规还要人工判一遍, 检查器自己也会认错.

## 长度: 不许长篇大论

- 主语换了, 或者动作换了, 就另起一段. 别等一行写长了才拆.
- 一条规定只写一遍, 写在管它的那份文件里. 别处只给指向它的链接, 不复述. 本文件收机械部分的细则,  
  [AGENTS-cn.md](../../AGENTS-cn.md) 收禁令和每条最短的说法.
- 读者要在哪一段用到这条规则, 就把它写在那一段, 段尾不再复述一遍.
- 一节值不值这个长度, 看它定了几件事. 只为说明"这条规则有道理"的句子, 删掉.

## 语言与文件命名

每份文档和文件名用什么语言, 负责人定, 仓库不做默认语言的预设. 语言定了之后, 整个目录都用这门语言写时把标识加在目录上,  
目录里的文件保持平名, `docs/dev/issues-cn/` 和 `docs/agents-cn/` 就是这样. 只有文档在混语言目录或仓库根里时,  
标识才加在文件上, `docs/dev/module-structure-cn.md` 和 `AGENTS-cn.md` 就是这样.  
译本的根 `README` 仍然是根文件: GitHub 只渲染仓库根的 `README.md`, 它搬不进语言目录.  
一个目录已经有了命名模式时, 照它来.

仓库现在没有成对镜像的文档: 规则只维护 `AGENTS-cn.md` 一份, 根 `AGENTS.md` 只有一行指向它.  
活动长文和需求正文也只有中文一份, 在 `docs/agents-cn/` 和 `docs/requirements-cn/`.  
`docs/dev/JOTTINGS.md` 只有英语, `docs/dev/module-structure-cn.md` 和 `docs/dev/issues-cn/` 是中文原创,  
都没有对应版本.

一份文档以后要留双语副本时: 两份讲同样的陈述, 小节顺序也相同, 句子内部的先后按各自的语言来;  
不带语言标识的那一份生效, 两份不一致时修另一份; 改一份就在同一次修改里把另一份一起改到底.

链接跟随承载它们的那份文档的语言: 任何一份文档都一样, 自己这门语言有这一份就指向这一份,  
没有就指向现存的另一种语言那一份. 这项义务同样管写在正文里的引用, 不只是链接:  
中文文档引用时写 `AGENTS-cn.md`, 仓库里没有中文版时才点不带标识的名字. 只有一类句子照旧用不带标识的名字:  
讲哪一份生效的那句话, 指向的是生效的那一份.

归档材料不受这条义务管辖: record 保留它归档时的链接与引用, 所以一份中文归档仍然指向英文文件是正确的现状,  
不是要就地修复的不一致.

有理由时, 文档内部仍然可以使用任何语言.
