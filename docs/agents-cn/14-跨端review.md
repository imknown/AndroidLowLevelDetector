# 14-跨端review

> **状态**: **living**. 这套规则文件的入口在根 [AGENTS.md](../../AGENTS.md), 编号和阅读时机见那份索引.

## 这份文件管什么

review 的义务本身 (证据, 漏项三档, 超出范围, 停止条件) 在 [11-构建与验证](11-构建与验证.md) 和  
[13-任务工作流](13-任务工作流.md) 里, 这里不重复. 这里只管一种情形: 某一轮 review 交给另一个  
ADE/IDE 的 session 或 task 去做, 写 review 的 agent 或模型不在当前会话里.  
两个 ADE/IDE 之间没有直接联系, 衔接只靠同一个工作树里的文件.

所以原则只有一条: 每一轮要传下去的东西全部写进文件, 下一轮从文件恢复.  
从哪个 session, 哪个模型接, 都读同一份文件.

## review 目录

- 在被 review 的目标下面建一个 `review/` 目录: review 的是 spec 任务或它的子任务, 就建在那份 spec 目录下;  
  review 的是别的目标, 就建在那个目标所在的目录下. 目标跨多个目录时, 建在多数目标所在的目录下.  
  spec 目录因此保持平铺: 这个目录是临时的, 处理完整个删掉, 不改变 13 定下的目录布局.
- 建 `review/` 的同时, 在里面建一份 `.gitignore`, 内容只有一行 `*`.  
  这个目录连同里面的所有文件都不进 git, `git status` 里看不到它们.
- 这个目录默认不提交, 发现处理完就整个删掉 (见 `报告的归宿` 一节).

## 文件命名

一轮 review 发出去时, 主 agent (发起这一轮的一方, 通常是写这次改动的会话) 在 review 目录里生成一份提示词;  
每个写完的 reviewer 落一份报告.  
文件名里的轮次就是 review 轮次 (v1, v2, ...), 格式:

- 提示词: `review-v1-prompt-<HHmm>.md`. `<HHmm>` 是发起那一刻的 24 小时制时间, 一轮作废重发时靠它分开.
- 报告: `review-v1-report-<agent-slug>-<model-slug>-<HHmm>.md`. 这两个 slug 和这里的 `<HHmm>`  
  都由写报告的 reviewer 自己填: agent 和模型报它自己, 时间是落盘那一刻;  
  slug 用小写字母, 数字, 短横线和点.

命名规则写在提示词里. 同一轮几份报告互不相同, 旧文件留在原地.

## 状态记录

review 目录带一份 `state.md`, 记五样:

- 这次 review 的是什么 (一句话), 发起时的 HEAD hash.
- 每轮一行: 轮次, scope (`full` 或 `delta`), 提示词文件, 状态 (`等待报告` / `已收` / `作废`).  
  发起时主 agent 不知道会有几份报告, 这一行不登记 reviewer.
- 每收下一份报告, 就在 `已收报告` 一节补一行: 报告文件, reviewer 的 agent 和模型, effort, 都从报告的元数据块抄.
- 各条发现的判定理由; 其中归后续单元的发现和它们的理由, 单独一节记着.
- 下一步动作.

主 agent 在每个确认点更新它, 角色跟 spec 任务的 `progress.md` 一样 (见 [13-任务工作流](13-任务工作流.md)).

## 负责人说 "review" 时怎么接

"review" 这个词跟 [13-任务工作流](13-任务工作流.md) 的 review 步骤共用, 主 agent 按这个顺序分辨:

1. 当前有状态为 `等待报告` 的轮: 按轮次扫 review 目录找报告文件, 回来一份收一份 (见 `收报告` 一节).  
   文件不在, 或者头部尾部不齐, 那份不算. 收下的发现合在一起看 (怎么合, [11-构建与验证](11-构建与验证.md) 写了).  
   负责人喊 review 收完这轮, 那轮标 `已收`, 工作树随之解冻;  
   发现的处理 (按 [13-任务工作流](13-任务工作流.md) 第 3 步修) 从解冻后开始, 中间轮次不请示负责人.  
   已收之后才回来的报告照收, 发现按当前改动判定.
1. 没有 `等待报告` 的轮: 先看有没有已收轮之后才回来的报告, 有就照上一条收;  
   然后照 `state.md` 里的下一步动作做, 多半是生成下一轮的提示词.
1. 连 review 目录都没有: 这次 "review" 走 [11-构建与验证](11-构建与验证.md) 和  
   [13-任务工作流](13-任务工作流.md) 的常规流程.

## 生成提示词

提示词要能在一个没有本仓库会话记忆的 session 里独立执行, 所以:

- review 义务抄全: 应改清单怎么枚举, 漏项分哪三档, 超出范围的改动单列, 停止条件 (只剩措辞就停),  
  每条发现带 `file:line` 证据; reviewer 之间彼此独立, 绝不读取同一轮其他 reviewer 写的报告或参考它们的结论.  
  抄的是义务的当下文本, 不写 "见某文档";  
  一轮 review 进行中, 它不依赖正在改的规则文件.
- 写死三样: 报告写进哪个目录, 按什么命名 (见 `文件命名` 一节, slug 和时间由 reviewer 自己填);  
  报告开头和结尾的固定格式 (见 `收报告` 一节); 发起时的 HEAD hash.
- 结尾附一句给对面 session 的开场白: 读根 `AGENTS.md`, 读这份提示词, 按提示词写报告.
- 这句开场白同时完整贴进发给负责人的回复里: 负责人复制就能发给任何一家, 不翻历史消息, 不开口问.
- delta 轮 (v2 起) 额外带三样: 上一轮报告全文, 上一轮的应改清单, 两轮之间的修复 (diff 或清单).  
  再加一句指令: 先逐条核对上一轮的发现是否真的修了, 再扫描新增的改动.

对面的 session 换 agent 或换模型都一样: 它没有上一轮的会话记忆, 上面那三样就是它的全部记忆.

## 一轮可以并行几个 reviewer

- 同一份提示词可以发给任意几个 reviewer: 大家读同一份, 各写各的报告, 文件名里的 slug 互不相同.
- 同一轮并行的 reviewer 彼此独立: 每个 reviewer 只凭提示词和被 review 的改动自己判断, 绝不读取  
  同一轮其他 reviewer 写的报告或参考它们的结论, 防先入为主. 上一轮的报告不在此列, 它是 delta 轮的任务材料.
- 主 agent 不关心对面是谁: 领了提示词的任何 ADE/IDE 的 agent 都能写这份报告, reviewer 是谁,  
  由它在报告的元数据块里自报.
- 挑对面的 ADE/IDE 时, 优先挑跟主 agent 不同厂商的.
- reviewer 在另一个 ADE/IDE 时, 当前 ADE/IDE 的模型清单流程 ([11-构建与验证](11-构建与验证.md)) 不适用:  
  对面用哪个模型, 负责人开那个 session 时就定了.
- reviewer 在当前 ADE/IDE 里 (窗口内的 subagent, 或并列的新 session/task), 照  
  [11-构建与验证](11-构建与验证.md) 的清单流程挑模型和 effort.

## 收报告

报告开头是一个元数据块, 一行一个字段: reviewer 的 agent, 模型, effort, 轮次, scope, 发起时的 HEAD hash, 日期.  
对面读不到自己的 effort 时, 写它模型的默认 effort; 发起方也可以把负责人定下的值写死在提示词里让它照抄.  
报告最后一行固定是 `REVIEW-STATUS: done`.

收报告时核对头部和尾部:

- 元数据块字段齐全, 最后一行是状态行, 主 agent 才收下它. 缺任何一样, 当它没写完, 那轮还在 `等待报告`.
- 元数据块里的 HEAD hash 跟当前 HEAD 不一样时, 报告过期: 那轮作废, 重新生成提示词.  
- 迟到报告 (该轮已收后才回来的) 一律走这一条: HEAD hash 一样但工作树在那轮 review 发起后修过,  
  报告照收, 发现按当前改动判定, 修掉的不再算.  
- 这两条都只在有人绕过冻结时才会出现: 提交会让 HEAD 变, 只改工作树不会.
- 收下的发现照 [13-任务工作流](13-任务工作流.md) 的处理发现那步走: AI 自己判定, 中间轮次不请示负责人.

## 有轮在外时工作树不动

有状态为 `等待报告` 的行, 就不改工作树里的任何文件, 也不提交 (提交会动 HEAD); 进度记录和 `state.md`  
这类记录文件除外. 那轮标 `已收` 或 `作废` 就解冻. 非改不可, 先把在外的轮全部作废再改.  
所有 ADE/IDE 共享同一个工作树, 这条对哪一边都一样.

## 报告的归宿

发现处理完, review 目录整个删掉; 删之前, `state.md` 里还没搬走的归后续单元交给负责人定去处.  
核心内容各有去处, 不靠这些文件留住:

- 修掉的发现, 修复它们的 commit 就是记录.
- 归后续单元的漏项, 超出范围的判定结果, 记进 spec 任务的进度记录; 没有正在跑的 spec 任务时,  
  先记进 review 目录的 `state.md`, 删目录之前交给负责人定留得住的去处.
- 任务结束那次横向回顾要的素材, 进 [13-任务工作流](13-任务工作流.md) 里说的那份 review 检查表.
- 提交信息的 trailer 照 [12-git](12-git.md) 记产出这次工作的 agent, 模型和 effort;  
  review 是谁不进 trailer, 报告的元数据块只用来登记状态.
- 负责人放行时留的那句理由, 写进对应 commit 的提交信息.
