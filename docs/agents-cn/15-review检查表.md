## 检查表

1. **改动移动行数时, 重核指向该文件的所有行号指针.** 增删一行, 同文件后面的行号全部漂移;  
   本任务三次发生 (报告指针 `:134` 被自己的拆行顶成 `:135`, 计划节 `:48` 被加行顶成 `:49`,  
   钉存范围的 `:45-48` 随之过期, 三处都靠 review 抓回).  
   做法: 同一批里 grep 报告与记录里指向被改文件的所有 `:N` 与 `:N-M` 引用, 逐一重核.
2. **每轮 review 落两条记录, 只记在 review 目录的 `state.md`.** 收报告条记各家 agent, 模型, effort,  
   报告文件名, 加元数据块与末行状态行的核过项; 判定条记三档分档与处置.  
   这两条记录本身不留; 漏了收报告条, 下一轮核不到报告是谁写的 (本任务漏过一次, 靠下一轮 review 抓回).
3. **口径与术语变更后, 按旧词全仓 grep.** "注册表引擎已兑现" 只改了书面目标句,  
   头行的撞词没跟上, 靠 review 抓回; "入表" 换 plain 说法后, 另一句话里的同词属另一件事,  
   要另判不能并进修改. 做法: 裁定或换词后, 按旧词与新词各 grep 一次, 每处判定是同类要改,  
   还是另一句话 (另一句放要问的清单).
4. **修完文档断行, 量行尾字节.** 修复断行时新行缺两个尾随空格, 断点还切在 "与" 后,  
   靠 review 抓回. 做法: 改动断行后用 `sed -n 'Np' 文件 | cat -A` 量行尾字节,  
   并对本批新增行扫破折号与 CJK 标点.
5. **全局改名按旧名清单逐个 grep 全仓.** 规则文件改号后, 旧名在报告, issues 正文与  
   进度记录里陆续被发现 (报告内五处, issues 正文十六处归清理单元). 做法: 改名时列旧名清单,  
   逐个全仓 grep 一次清零, 不按点名的几处算完.
6. **改流程规则后, 把接续步骤与未开工 spec 的头部一起核.**  
   这轮改提交时机, 接续扫描没提临时分支, daemon spec 头部还写着旧口径,  
   新词 "检查点" 也没在第一次出现处定义, 三处都靠 review 抓回.  
   做法: 改流程规则时, 列出接续步骤与在做的 spec 头部, 逐处核; 新词在第一次出现处给定义.
7. **对二进制文件判 "零命中" 之前, 先确认工具真的在搜.** 拆包核证 (AAR 里的 class 字节码) 时,  
   Git Bash 的 grep 对 `.class` 这类二进制缺 `-a` 时静默零匹配: 一个 31 个 class 都含的字符串报 0,  
   加 `-a` 才报 31, 两种跑法各跑过两次; 两个跨端 reviewer 都数对了, 发起方起初判错.  
   `strings` 在 Git Bash 里也没有. 做法: 查二进制用 `grep -a` 或 `javap -v`;  
   判零命中之前, 先拿一个已知含该字符串的文件当哨兵试一次.
8. **状态翻转后, 把描述旧状态的句子单独扫一遍.** 滚动条换官方组件后, README 路线图里  
   "#37 / #59 / #60 分别跟着官方滚动条组件, material3 1.5, foundation 1.13 的到位触发" 这句过期,  
   但残留 grep 扫的是换掉的实现词 (自绘, ScrollBarExt, 旧调用签名), 这句一个词都不含,  
   靠 reviewer 抓回 (它还与同文件已改过的 #37 状态行自相矛盾). 做法: 落地一类改动后,  
   对总览表, 路线图一类的状态句 grep 状态词 (随行, 待, 触发, 仍, 还没, 未), 逐处判它说的状态  
   还是不是当下.
9. **转写别人的发现与写工具行为断言, 都要回源, 不凭记忆压缩.** 总 review v2 抓回: 把 reviewer 的  
   "在本轮之前就已经过期" 压缩成 "在它写下时就已过期", 时间点变了 (git 证据: 那句声明写下时成立,  
   后来才被生产代码提交推翻); 同一轮还把 git 根本产不出的字符 (结尾的点与空格) 写进 "git 允许" 清单,  
   `git check-ref-format` 一跑就证伪. 做法: 记录别人的发现保留它原有的范围与时间点, 拿不准就引原文;  
   说某工具允许或禁止什么, 先跑那个工具再落笔.
