# 09-构建约定

> **状态**: **living**, 构建约定的细则; 每次构建改动的禁令也在这份文件里.  
> 改 Gradle 文件, 版本目录, 工具链版本或 CI 之前, 先读这份.

## 每次构建改动的禁令

- 依赖和版本只写在 `gradle/toml/` 下的五份目录里. 这里没有默认的 `libs` 访问器,  
  所以模块的 `build.gradle.kts` 里绝不写裸坐标; 引用之前先定这个依赖归哪份目录.
- SDK, build-tools, NDK 的版本只写在 `gradle/toml/build.toml` 里, 配一个 `isPreview` 开关,  
  再由 `build-logic` 的约定插件下发给各模块. 模块脚本里绝不硬编码 SDK 级别.
- 正文里不写版本号. 哪个构建文件存着这个值, 真值源就是它,  
  所以文档, 代码注释, 提交信息都点名那个文件或它背后的 key, 不复述数字.  
  存这些值的地方有五份目录 (`gradle/toml/` 下, 在 `build-logic` 里也能用 `buildVersion("<key>")` 取),  
  `gradle/wrapper/gradle-wrapper.properties` 和 `gradle/gradle-daemon-jvm.properties`.  
  一个 `.kts` 脚本或一个 `.properties` 文件, 分量跟一份 `.toml` 目录完全一样.  
  禁令管的是我们自己构建文件里的值. 外面世界的版本 (某条上游发布线, 某个 API level),  
  句子讲的就是它时, 就留在句子里.
- Kotlin 编译器带着一组实验性 flag 跑, 这些 flag 声明在 `build-logic` 里. 它们是故意加的, 别删.  
  每升一次 Kotlin 就把这些 flag 分组重新看一遍, 已经稳定的去掉. 代码风格是 `official`.
- 版本分级: RC 或 Stable 的依赖和工具链版本可以直接进生产.  
  Beta, Alpha, Canary 的也可以, 前提是你充分研究过它, 确认它的已知问题能修好或绕开, 并且评估过这次采用.
- 配置缓存 (带 parallel 和 integrity 检查) 和并行构建都已启用. 自定义 task 要保持配置缓存兼容.

## Flavor 与变体

- Flavor 维度叫 `IssueTracker`, 不是常见的 `mode` 或 `store`.
- `Foss` 是默认 flavor: 不加任何跟踪, 版本名带 `-Foss` 后缀.
- `Firebase` 是 Play 变体, 需要 `google-services.json`. 这个文件已经被 gitignore.
- `AndroidApplicationFirebaseConventionPlugin` 用 `firebaseImplementation` 挂 Firebase 的依赖,  
  并且给 Foss 禁用 GoogleServices 和 Crashlytics 两个任务. 所以 Foss 构建从来不需要那个文件.

## 应用标识

- Debug 构建装出来就能用. debug 会加 `applicationIdSuffix = ".debug"`, 所以它能和 release 并存安装.  
  处理应用标识的时候记得这个后缀, 比如权限和 adb.
- Release 的签名配置在仓库之外, 放在已被 gitignore 的 `local.properties` 里 (根 README 有说明).

## 两个 JDK, 各管各的

- 代码用的 JDK: 从 build 目录读 `javaToolchain` 的版本. 这个值在 `gradle/toml/build.toml` 里,  
  经 `build-logic/convention/src/main/kotlin/.../ext/ProjectExtensions.kt` 的 `Project.buildVersion()` 取出来,  
  然后用到 `KotlinAndroid.kt` 的 `jvmToolchain` 块上. 那个块把厂商钉在了 Adoptium 上.
- daemon 用的 JDK: 读 `gradle/gradle-daemon-jvm.properties` 里的 `toolchainVersion` 和 `toolchainVendor`.  
  这个文件由 `updateDaemonJvm` 生成.
- 别把两套混成一件事说. 文档和注释里也永远不要复述任何一个版本号: 这两个文件各是自己那套的真值源.
- 想看工具链解析器到底看到了什么, 跑 `./gradlew -q javaToolchains`.

## 原生与钉住的工具版本

- `:binderDetector` 的原生代码要求把 NDK 和 CMake 的版本钉在 `gradle/toml/build.toml` 里.
- CI 装的就是这些版本, 所以升级它们时要同步改 CI, 一步都不能落下.

## CI

- CI 只构建 `assembleFossDebug`. `master` 上是 `lld.json` 的数据更新, 所以别拿它当 PR 的目标分支.

## 版本目录布局

- 版本目录拆成 `gradle/toml/` 下五个文件: `build`, `android`, `kotlin`, `google`, `thirdParty`.  
  读取走 `libsAndroid`, `libsBuild`, `libsKotlin`, `libsGoogle`, `libsThirdParty` 这几个访问器.  
  依赖归哪份目录, 禁令在上面 `每次构建改动的禁令` 一节.

## 仓库过滤

- 每个仓库都做了内容过滤, 比如 `google()` 用 `includeGroupByRegex` 收窄, 同时启用 `FAIL_ON_PROJECT_REPOS`.
- `jitpack.io` 只在主构建的依赖仓库里.

## 正文里不写版本号

- 为什么: 复述出来的数字, 在那个文件升级的那一刻就过时了; 文档里一个过时的数字, 下一个会话会当成事实继承下去, 那就是 bug.
  禁令在上面 `每次构建改动的禁令` 一节.

## Kotlin 标志

- Kotlin 版本只在 `gradle/toml/kotlin.toml` 里.
- 实验性标志按引入它们的 Kotlin 版本分组; 分组和审查的禁令在上面 `每次构建改动的禁令` 一节.

## 构建缓存与 build scan

- build scan 用 Develocity 插件, 但从不发布 (`publishing.onlyIf { false }`), 只生成本地 scan.
