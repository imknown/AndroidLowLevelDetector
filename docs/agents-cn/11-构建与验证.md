# 11-构建与验证

> **状态**: **living**. 这套规则文件的入口在根 [AGENTS.md](../../AGENTS.md), 编号和阅读时机见那份索引.

## 构建与验证

```bash
./gradlew assembleFossDebug      # CI 构建的目标 (GitHub Actions)
./gradlew testFossDebugUnitTest  # 单元测试
./gradlew lintFossDebug          # Android lint
```

- 只改文档或注释的编辑跳过构建那几档, 因为没碰代码. 下面那条 review 照样要做, 文档改动拿需求正文当参照物.
- **用 Android Studio 做分析**: 每批编辑之后, 按 [02-工作原则](02-工作原则.md) 里那条验证顺序走; 每一步跑什么命令, 怎么读结果, 见 [10-分析细则](10-分析细则.md).  
  写下这次改动的 agent 先在自己的上下文里 review 自己的改动,  
  发现问题就改, 改完再自查, 一直查到最后只剩不重要的措辞问题.  
  最后找一个不带本次上下文的 reviewer, 让它 review 这次未提交的改动,  
  发现按 [13-任务工作流](13-任务工作流.md) 的处理发现那步走, 中间轮次不请示负责人.  
  自审和委派出去的 review 都要把已改的和该改而没改的一起查, 也要列出超出本次范围的改动.  
  漏改的文件根本不进 diff, 要另建应改清单才查得到.  
  没有需求正文可对照时, 目标和范围取自 `plan.md` 的子任务范围, `subtask-NN` 报告, 或者负责人的原话.  
  怎么枚举, 三档怎么分, 见 [13-任务工作流](13-任务工作流.md).  
  reviewer 的每一条发现都要有能核对的证据 (文件:行号).  
  只剩下不重要的措辞问题时, reviewer 就停止 review, 把这些发现报上来, 不再要求多一轮.  
  Review 按轮次来 (v1, v2, ... 每修一轮往后排一轮).  
  每一轮之前都要先自审, v1 和后面的每次 delta pass 都不例外.  
  任务工作流细则的 Review 步骤里写着增量复核和换新 reviewer 的做法, 每个会话都要守.  
  见 [13-任务工作流](13-任务工作流.md).  
  交出去之前的 plan 或报告也要先自审一遍, 每一次委派出去的 review 都算.  
  这些义务每个会话都要守, 不只是 spec 任务.
  - 触发 review 时, reviewer 在哪跑由负责人定: agent 摆情况和选项, 协助决定, 不替负责人定.  
    agent 汇报: 当前 ADE/IDE 能不能委派, 能委派哪一种. reviewer 放在当前 ADE/IDE 时, 再汇报模型清单:  
    可用模型 (免费的, 已授权购买的, 还有额度的, 都算) 按厂商分开列, 跟写这次改动的 agent 不同厂商的在前,  
    同厂商的别的在后. 三种委派不是一回事: subagent 是当前 agent  
    在当前环境直接开启的, 通常就在当前 agent 窗口 (ADE/IDE 的 GUI/TUI 窗口) 里;  
    session 是跟当前会话并列的新上下文, 通常不在当前 agent 窗口里; task 跟 session 一类,  
    不同 ADE/IDE 叫法不同.  
    委派对象的实际工作内容和进度用户看不看得到, ADE/IDE 自己未必分得清, 这条 agent 不判:  
    负责人实测过, 负责人挑. 选项里包括跨端: 发起和衔接见 [14-跨端review](14-跨端review.md).
  - **reviewer 用哪个模型, 用哪一档推理强度, 负责人定**: reviewer 优先用跟写这次改动的 agent 不同厂商的模型;  
    当前 ADE/IDE 挑不到不同厂商的, 就用同厂商的别的模型. reviewer 放在当前 ADE/IDE 时,  
    启动 reviewer 之前先把模型清单取出来.  
    到底有没有这份清单, 它带着哪些字段, 取决于跑这个会话的 agent; 有的暴露这样的工具, 有的没有.  
    清单回来了, 就把整张表给负责人看: 工具带一个字段就给一列, 工具对某个模型有定位说明时就附上.  
    字段比如 id, name, 价格, 发布时间, effort 取值; 列不许编.  
    清单里没有 effort 列时, 展示表格的时候就说清楚, 并让负责人点名 effort; 返回空等于取不到清单.  
    然后负责人把模型和 effort 一起定下来. 默认是多选: 点名几个模型, 就并行开几个 reviewer.  
    几个 reviewer 的报告合在一起看: 大家都同意的合成一条, 有分歧的拿证据判, 判不了就按  
    [02-工作原则](02-工作原则.md) 的分工停下来问.  
    effort 按模型逐个选. 没有这个取值的模型跑它自己的默认值, 报告里要写明.  
    这一次选定管一整串 review: 复用的 reviewer 保持它的模型和 effort, 换新 reviewer 时重新问.  
    清单取不到时, 问负责人怎么办. 想用回写这次改动的模型, 得负责人的明确同意;  
    本会话自己的 effort 级别读不到时, 这个值照样得负责人给.  
    effort 级别绝不猜; [12-git](12-git.md) 里那条提交 trailer 规则照常适用.
  - 某一轮 review 也可以交给另一个 ADE/IDE 的 session 或 task 去写: 目录, 文件命名, 状态记录和收报告的细则见  
    [14-跨端review](14-跨端review.md).
  - [10-分析细则](10-分析细则.md) 是 analyze-file 和 ILS 那两条通道的完整契约.  
    依赖任何结果之前先读它. 当心有些运行看着像通过其实没有: 坑清单和怎么读打印出来的分块都在那儿.
