## 2. 核心能力 (FR-1 ... FR-10)

### FR-1 特性支持检测 (P0)

检测全程在手机上完成: 当前系统按一份选定的 Android 系统特性清单逐条评估 (Treble / VINTF 支持,  
A/B 更新, 动态分区 / system-as-root, Mainline 等等). 逐条目的清单见  
[检测条目目录](04-detection-item-catalog.md).

**验收标准**

- AC1: 清单里每个 Home 条目每次检测产出恰好一个三态结论 (FR-3);  
  Others 与 Prop 的条目是信息行, 没有结论 (FR-14).
- AC2: 增删一个条目不能要求连周围界面一起重做.
- AC3: 所有检测都在手机上跑; 检测任何时候都不把用户数据发到任何地方.

### FR-2 系统参数展示 (P1)

应用把常见的**系统与 ROM 参数**作为辅助信息展示, 让用户一眼了解自己的手机.  
参数族逐条目见 [检测条目目录](04-detection-item-catalog.md):

- **构建 / ROM 身份**: 品牌, 厂商, 型号, 设备, 产品, 硬件, 主板; SoC 型号与厂商; 各种 SKU;  
  Build ID, Display, 构建类型, 标签, Incremental, 代号; 各分区指纹; bootloader 与基带版本.
- **Android 版本族**: 版本, SDK 扩展版本, 平台与厂商安全补丁级别, 性能等级 (Media Performance Class).
- **架构与 ABI**: CPU ABI, 支持的 32 位与 64 位 ABI, 进程位数与虚拟机架构, Binder 协议位数.
- **内核**, **WebView 的 user agent**.
- **属性与设置的原始整表输出** (Prop 屏: `getprop`, build.prop,  
  以及 `Settings.System`, `Settings.Secure`, `Settings.Global` 三张表), 逐行照原样显示, 不解析也不评判.  
- **不属于参数族的东西**: 内存, 屏幕, 电池这类硬件参数. 应用不调用  
  `ActivityManager.MemoryInfo`, `WindowManager`, `DisplayMetrics`, `BatteryManager` 中的任何一个,  
  也不读 `/proc/meminfo`; 这类值只可能被动地出现在 Prop 屏的整表输出里,  
  作为系统属性或 `Settings` 表返回内容的一部分 (比如某些机型上的 `ro.sf.lcd_density`),  
  应用既不解析也不评判它们. 唯一擦边的是 Android 版本那一行: 它读布尔值  
  `ActivityManager.isLowRamDevice()` 来追加 " (Go)", 读的不是内存大小.  
  将来真要展示这类硬件参数, 就走 [检测条目目录](04-detection-item-catalog.md) 的条目模板, 作为新条目进来.

**验收标准**

- AC1: 参数值在检测时从设备实时读取.
- AC2: 读不到的参数显示成该条目自己的失败行 (FR-6), 既不崩溃, 也不留白屏.

### FR-3 三态结果模型 (P0)

每个 **Home** 检测条目只落在三种状态之一. 行上用圆点颜色呈现这个结论 (FR-15);  
Others 与 Prop 的行完全没有结论 (FR-14).

| 状态 | 含义 |
|---|---|
| **支持** | 检测确认该特性受支持, 或已启用. |
| **不支持** | 检测确认该特性不受支持, 或已禁用. |
| **未知** | 检测给不出答案, **检测本身失败也算** (抛异常, 接口被拦, 值读不到). |

**验收标准**

- AC1: 三态指示是 Home 结果列表里最重要的视觉元素.
- AC2: 没有第四种对用户可见的状态: 检测失败就显示成该条目的未知,  
  错误文字装在该条目自己的行里 (FR-14), 细节进日志供排查.
- AC3: 旋转屏幕或其他界面重建之后显示的仍是同一个状态, 且不重跑检测.

### FR-4 进入界面自动检测 (P0)

**写法见 FR-13.** 这个编号保留, 含义是: 进入一个界面触发一次检测, 只触发一次, 不重复.

### FR-5 下拉刷新 (P0)

用户可以在结果界面**下拉刷新**, 手动触发一次完整的重新检测.

**验收标准**

- AC1: 刷新指示器从刷新开始一直可见到结束, 然后消失.
- AC2: 刷新过程中多余的下拉手势不能启动重复的检测 (与 FR-13 同一条去重规则).
- AC3: 刷新会重跑每一个条目, 期间单项隔离 (FR-6) 照常生效.

### FR-6 单项错误隔离 (P0)

任何一个检测条目失败, **只影响它自己**.

**验收标准**

- AC1: 失败的条目显示成未知, 其余每个条目保持自己的结果.
- AC2: **没有整页的错误态**: 一个或少数几个失败, 不能把整份列表换成一张错误屏,  
  也不需要 "全有或全无" 式的重试.
- AC3: 失败在日志里留下排查线索, 但从不阻塞用户.

### FR-7 服务端参考数据同步, 比对与离线缓存 (P1)

应用同步**服务端参考数据**, 并把它和设备本地的检测结果做比对, 用来交叉核对和补充展示的值.  
同步到的数据缓存在应用自己的目录里, 所以离线或关掉网络时应用照常可用.

数据怎么取, 失败时退到什么, 版本怎么合并, 写在 FR-16.

**验收标准**

- AC1: 参考数据放在应用的**私有**存储里 (应用私有的外部文件目录, 外部目录不可用时退回内部文件目录),  
  绝不放在公共存储, 且离线可用.
- AC2: 同步失败要平稳降级: 继续用旧缓存, 且按 FR-6 没有整页错误.

### FR-8 用户可控的网络开关 (P1)

应用提供一个**用户可见的开关**, 用来打开或关闭 FR-7 的**服务端参考数据同步**.

这个开关只管参考数据同步, 不管遥测: 遥测跑不跑由发布变体决定 (FR-10).

**验收标准**

- AC1: 开关关掉时不发同步请求, 应用读缓存.
- AC2: 开关不影响 `firebase` 变体里的 Firebase Crashlytics 与 Analytics.
- AC3: 开关在设置页的 Function 组里, **默认关**, 且只管服务端 json 的下载 (FR-17).

### FR-9 合法的检测手段 (P0)

检测可以用**任何合法技术手段**, 包括:

1. 公开的 SDK 接口;
2. 反射调用隐藏的或 `@hide` 的框架接口与内部服务;
3. `getprop`, `dumpsys` 这类 shell 命令的输出;
4. 有 root 或 Shizuku 时的特权检测, 这是可选增强, 不是当前版本的要求.

**验收标准**

- AC1: 特权路径是**可选增强**: 没有它, 检测退回普通手段或报未知. 它从不崩溃,  
  也从不误报成 "不支持".
- AC2: 用到的每一种手段都合法且只读 (NG5, NG6).

### FR-10 两个发布变体 (P1)

这个产品以两个构建变体发布, **检测功能完全相同**. 各自收集什么, 在哪里分发,  
写在 [变体那张表](01-product-and-users.md#37-变体与数据收集) 里; 运行时的遥测开关属于后续 (BL-7).

**验收标准**

- AC1: `foss` 变体里没有 Firebase, 也没有任何别的专有遥测, 直接和间接都没有.
- AC2: 两个变体的检测功能完全相同.
- AC3: `firebase` 变体里 Crashlytics 与 Analytics 默认开启, 且不受 FR-8 开关影响.
- AC4: 设置页有一个隐私政策入口, 用浏览器打开在线政策.

## 3. 应用外壳与界面 (FR-11 ... FR-17)

### FR-11 单 Activity, 单实例 (P0)

应用只有一个 `MainActivity`. 任何应用可以在任何时候以任何 intent 标志启动它.

**验收标准**

- AC1: 常规启动路径 (桌面, 最近任务, 别的应用) 都复用已有实例 (`launchMode="singleTop"`),  
  且应用不读重新投递的 intent. 特殊标志组合  
  (`FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_MULTIPLE_TASK`, 以及再加 `FLAG_ACTIVITY_CLEAR_TASK`)  
  仍可能新建任务或实例并清掉内存里的状态; 这个隐患暂时接受, 任务栈保护是 BL-8.
- AC2: 被外部重新启动后, 已有实例的状态保留: 既不重置, 也不会多出一份返回栈.

### FR-12 外壳布局与滚动行为 (P0)

> 这一条写的是外壳的目标形态; 今天哪些部分已经做出来了, 记在  
> [发布与路线图一篇](03-non-functional-requirements-and-roadmap.md) 里.

- 主题与控件: **Material 3**, 平台支持时使用动态取色 (Material You).
- 根布局: 三段式 Scaffold, 顶栏, 底栏, 内容.
- 顶部: **顶栏**显示应用名; debug 构建的应用名是 "LLD Debug".
- 底部: **底栏**按这个顺序放四个 tab: **Home, Others, Prop, Settings**; 大屏上显示成**导航边栏**  
  或等效的自适应形态.
- 中间: 承载当前界面的容器.
- 四个界面都可能超过一屏, 都要能滚动.
- 全面屏: 列表底部留白要算上系统导航栏和底栏, 既不裁掉内容, 也不留下点不动的死条.

**滚动行为**: 手指上滑, 也就是列表向下滚时, 顶栏被推出屏幕, 底栏隐藏, 底栏更快;  
反向滚动时两者回来, 被打断的动画从打断处往回播.

**验收标准**

- AC1: 向下滚两条栏都隐藏, 向上滚都回来, 被打断的动画平滑地反向.
- AC2: 两种栏状态下底部留白都正确.

### FR-13 列表生命周期: 进入, 懒加载, 缓存, 恢复 (P0, 含 FR-4)

适用于四个 tab; Home, Others 与 Prop 三个结果界面的列表生命周期只写在这一条里.

- 进入一个结果界面, 为该界面触发**恰好一次**检测 (FR-4); 已经有数据的界面不再跑.
- 已经有一次检测在跑时再进入, 不会并发启动第二次 (**去重**; FR-5 的刷新受同一条规则约束).
- 检测状态由**比界面重建活得更久**的对象持有: 正在跑的检测继续跑, 把结果交给重建后的界面;  
  已经完成的状态直接重新显示. 状态既不重置, 也不重跑, 也不会卡在加载图标上.
- 用户从没打开过的界面**从不初始化, 也不加载数据**.
- 冷启动显示 **Home** 界面并加载它的数据.
- 点一个 tab 先**显示**目标界面, 再**加载**它的数据.
- 加载过的界面连同**数据一起缓存**; 缓存一直复用, 直到用户刷新 (FR-5).
- 进程在后台被杀, 应用重建后, **最后显示的那个界面**恢复成当前 tab, 数据按常规的显示后加载规则加载;  
  内存里的缓存随进程一起消失了.

**验收标准**

- AC1: 冷启动只初始化 Home, 其他界面首次进入时才初始化, 每次进入触发恰好一次检测,  
  正在跑的那次不重跑.
- AC2: 切换 tab 从不重跑已加载界面的检测, 除非用户刷新.
- AC3: 进程被杀之后, 最后显示的界面恢复成当前 tab.
- AC4: 检测期间旋转屏幕或切换主题, 不会重置, 不会重复, 也不会把加载状态卡住.

### FR-14 共用的检测列表基础 (P0)

Home, Others 与 Prop 共用一套列表实现, 就写在下面; Settings 列的是偏好项, 走自己的一套行:

- **每一行是一个独立的检测条目**.
- 每一行是一张**卡片**, 由**标题**和**内容**组成, 两者都可以多行.
- **界面角色**: **Home 是结论屏**, 每行都带三态结论 (FR-3) 和结论圆点 (FR-15);  
  **Others 与 Prop 是纯展示**, 只有标题和内容, 没有圆点也没有颜色分级.
- 一行自己承担自己的失败: 失败条目的错误文字直接打进这一行的内容里 (FR-6).
- 首次显示时加载该行的数据 (FR-13); 缓存一直复用到用户刷新 (FR-5).
- 每个界面的条目顺序写在 [检测条目目录](04-detection-item-catalog.md) 里.
- 过期 targetSdk 应用的检查用到 `QUERY_ALL_PACKAGES`, 范围只限预装的 ROM 系统应用,  
  从不涉及用户自己装的应用; 仓库根目录的隐私政策里写明了这一点.

**验收标准**

- AC1: 一行里的异常显示成那一行的错误文字, 其他行不受影响 (FR-6).
- AC2: 行布局支持多行标题与多行内容, 不截断.

### FR-15 结论圆点 (仅 Home) (P0)

- 每个 **Home** 行带**一个半透明圆点**, 在标题的末端一侧; Others 与 Prop 的行没有圆点也没有分级.
- 圆点与 FR-3 的三态是**同一个指示**: 圆点是结论的可视化呈现, 不是第二套状态系统, 也不是崩溃指示.
- 颜色按**每个检测条目自己的语义**分三档, 不强加跨条目统一映射:  
  **绿**是最好的状态 (完全支持, 已是最新, 良好), **黄**是中间 (部分支持, 较新, 一般),  
  **红**是最差的 (不支持, 过时, 差), **未知或探测不到通常也落进红**.
- 某个条目落进哪一档, 由那个条目自己的语义决定.

**验收标准**

- AC1: 每个 Home 行恰好一个圆点, 取三种颜色之一; Others 与 Prop 的行一个都没有.
- AC2: 状态到颜色的映射就是那个条目自己的语义; 除了 "未知通常落进红", 没有对所有条目统一的映射.

### FR-16 Home 数据链路 (P1)

Home 界面用哪份数据由网络开关决定 (FR-8, **默认关**):

- **在线** (开关开): 下载**服务端 json**, 缓存到应用自己的目录里. 下载地址按手机时区选,  
  中国大陆时区走 Gitee, 其余走 GitHub raw; URL 固定为构建时的 `GIT_BRANCH`.
- **下载或解析失败**: 继续用**私有缓存**; 没有可用缓存, 或内置那份比缓存新时 (见下面的版本合并),  
  退回**打包在应用 assets 里的 json**; 用内置那份就是把文件复制进缓存.
- **版本合并**: 已有私有缓存时, 把它的版本与内置 json 的版本**按字符串**比较.  
  版本是 `yyyy-MM-dd HH:mm Z` 形式的日期时间, 字符串顺序就是时间顺序, 谁新用谁:  
  内置的更新就覆盖缓存, 没有缓存就直接用内置的.
- 任何失败都按 FR-6 降级, 从不出现整页错误.

**验收标准**

- AC1: 开关关着 (默认) 或没有网络时, 检测完全跑在私有缓存或内置数据上.
- AC2: 在线且服务端 json 更新时, 缓存被更新并使用.
- AC3: 服务端连不上或解析不了时退回私有缓存或内置那份, 除单项隔离之外用户看不出任何失败.
- AC4: 版本合并总是取缓存与内置中较新的那份, 比较方式就是上面的字符串比较.

### FR-17 设置页条目清单 (P1)

点整行就触发这一行的动作; 并非每一行都是开关.

**界面**

- **主题**: 跟随系统, 始终浅色, 始终深色.
- **滚动条模式**: 无, 普通.

**功能**

- **允许网络数据**开关, **默认关**: 只管服务端 json 的下载 (FR-8, FR-16).
- **优先按包名排序**开关, 默认关: 关闭时那一行按 targetSdk 列出应用, 打开时按包名.  
  它只改 Home 界面的那一行, 别的什么都不动. 列表已经加载完时切换, 那一行立刻更新;  
  首次加载还在进行时切换, 数据到了就是新顺序.

**关于**, 每一行打开它自己的目标:

- **商店页面**, 构建时按变体固定: `foss` 打开 GitHub 项目页, `firebase` 打开 Google Play,  
  没有运行时分支.
- **源码**: GitHub 项目主页.
- **隐私政策**: 托管在 GitHub 仓库里的政策文件 (FR-10 AC4).
- **许可**: 应用引用到的开源仓库.
- **语言与译者**: 当前语言以及是谁翻译的.
- **版本**: 版本名与版本号, 内置数据版本, 分发渠道, 安装来源, 首次安装时间, 最后更新时间.  
  连点这一行 7 次弹一个 toast.

**验收标准**

- AC1: 上面列出的条目一个不少, 整行可点, 且行为与上面写的一致.
- AC2: 主题与滚动条选项不用重启就生效.
- AC3: 按变体区分的条目各按自己的变体走, `foss` 的商店页面绝不指向 Google Play.
