## 1. 目的与范围

### 1.1 本篇目的

本篇说明这个产品**必须做什么** (功能需求) 和 **要做到什么程度** (非功能需求): 划出范围, 定优先级,

实现方式不写在这里; 已建成的架构见 [04-架构](../agents-cn/04-架构.md).

### 1.2 产品范围

LowLevelDetector 是一个**独立的 Android 应用**.  
它检查自己所在的这台设备, 全程在手机上, 实时完成,  
报告**当前系统是否支持**若干项关键的 Android 系统特性.

- 这个应用最初的用途是帮**刷机 / MOD 圈子**在刷入通用系统镜像 (GSI) 或第三方 ROM 之前回答一个问题:  
  "这台手机支持 Project Treble 吗?"
- **硬件参数不是重点.** 辅助内容是**系统与 ROM 的身份和状态**: 构建 / ROM 身份, Android 版本,  
  安全补丁级别, 架构与 ABI (含 Binder 位数), 内核版本, WebView 的 user agent,  
  以及系统属性和 `Settings.*` 各表的原始整表输出 (Prop 屏). 这个应用不主动读内存, 屏幕和电池:  
  这类值只可能被动出现在 Prop 屏的整表输出里, 是系统返回的内容, 应用既不解析也不评判.  
  参数族写在 [FR-2](02-功能需求.md), 逐条目见 [检测条目目录](04-检测条目目录.md).
- 当前版本**没有任何形式的导出**: 结果就在手机上现场查看, 只在这个应用里看 (NG1, NG2);  
  可能的后继工作列在 [发布与路线图一篇](03-非功能需求与路线图.md) 里.

### 1.3 术语与缩写

| 术语 | 含义 |
|---|---|
| **Treble** | Project Treble: Android 把系统拆成"厂商部分"和"Google 部分"的方案 (vendor 分区 + 稳定的 vendor HAL 接口). 这个应用最初就是为了查 Treble. |
| **VINTF** | 兼容性清单 / 框架, Treble 用它检查厂商接口是否匹配. |
| **A/B 更新** | 双槽分区方案: 更新在后台下载并安装, 重启一次就切到新系统. |
| **动态分区 / SAR** | 较新的分区方案 (super 分区; system-as-root). |
| **GSI** | Generic System Image, 通用系统镜像. |
| **三态结果** | Home 屏一个检测条目的结论: **支持 / 不支持 / 未知**. |
| **SSOT** | Single Source of Truth, 唯一数据来源: 一份状态只有一处权威. |
| **UDF** | Unidirectional Data Flow, 单向数据流: 操作从界面流向数据层, 数据流回界面; 两边互不改写对方的状态. |
| **KMP / CMP** | Kotlin Multiplatform / Compose Multiplatform: 路线图上那个跨平台查看器打算用的技术. |
| **Shizuku** | 一种机制: 应用不用完整 root 就能拿到 ADB 级权限. |
| **minSdk** | 支持的最低 Android API 级别. |
| **FOSS** | Free and Open-Source Software; 在这个产品里指**不含专有 SDK, 也不收集数据**的发布版本. |
| **变体 (`firebase` / `foss`)** | 这个产品的两个发布构建, 见 [3.7](#37-变体与数据收集). |

## 2. 用户与画像

### 2.1 主要用户: 刷机爱好者 ("Tinkerer")

- **画像**: 技术熟练; 刷 GSI 和第三方 ROM; 懂"分区"和"槽位"这类词.
- **需求**: 刷之前知道这台设备支不支持要用的系统特性; 刷之后确认新系统实际提供了什么.
- **达成**: 打开应用, 看懂三态结论, 放心去刷.

### 2.2 次要用户: 好奇的普通用户 ("Explorer")

- **画像**: 任何想弄明白自己手机系统的人; 可能完全不懂术语.
- **需求**: 一份可信的"我的手机支持什么"清单, 并且能看懂; 三个状态用大白话解释清楚.
- **达成**: 不用去别处查就能看懂这份清单; 未知的条目就明确显示成"未知", 绝不误导.

这个产品面向的是**任何想了解自己手机系统的人**.  
刷机爱好者只是起点, 也是这群用户里要求最高的那批.

## 3. 产品概览

### 3.1 背景

Google 每发布一项新的 Android 平台能力 (Treble 是第一个例子), 刷机圈子马上就想知道哪些设备能用上.  
答案散在厂商页面, 论坛帖子和自己翻 build.prop 的过程里.  
这个应用把答案收成一份清单, 就在应用里查: 打开, 看清单, 知道自己的系统支持什么.

### 3.2 定位

LowLevelDetector 是一个手机上的检查工具, 面向任何想了解自己手机系统的人, 尤其是刷机爱好者.  
它逐条列出当前系统对关键 Android 特性的支持情况, 每条都给一个三态结论.

### 3.3 价值

1. **结论一眼能读**: 结论就在那一行上, 不必自己从原始输出里推.
1. **查的是这台手机**: 应用读出的是当前装的这个系统, 不是宣传单上的参数.
1. **离线可用**: 在线参考数据缓存在应用自己的目录里, 没有网络也能用.
1. **一条坏了不影响整体**: 某个检测条目失败, 影响不到整份报告的其余部分.

### 3.4 目标 (当前版本)

- G1: 对选定的这组 Android 系统特性, 给出可靠的三态检测结果.
- G2: 旋转屏幕和界面重建后结果还在, 不重复加载, 不卡住.
- G3: 离线优先: 在线参考数据下载后缓存在应用自己的目录里.
- G4: 代码按功能组织, 人和 AI 助手都能找到该改的地方, 组织方式照 SSOT 和 UDF 来.

### 3.5 不做什么 (当前版本)

- NG1: **不导出数据**: 没有 JSON / TOML 输出, 不分享, 不整份复制 (能复制的只有系统长按选字这一种).
- NG2: **没有跨平台查看器**: 用 Compose Multiplatform 看导出数据的查看器只在路线图上.
- NG3: **没有条目详情页**: 展开一条看结论背后的原始值, 属于后续工作.
- NG4: **不做跑分和深度硬件信息**: 硬件信息只到辅助的系统参数为止.
- NG5: **从不修改系统**: 严格只读, 只检查, 不动手.
- NG6: **没有反检测功能**: 应用如实报告环境, 不帮着伪装.

### 3.6 路线图要点

备选清单和路线图只有一份, 在 [发布与路线图一篇](03-非功能需求与路线图.md) 的发布范围与路线图表里.  
别处不重复写, 所以改这一处不会漏掉另一处.  
几个主题: 通用格式的导出 (RM-1), 跨平台查看器 (RM-2), 更丰富的交互 (BL-1, BL-2, BL-3),  
开放的查询与对外暴露 (RM-3, RM-4, RM-5, 要等 Q8 定).  
产品名字保持现状: 中文名"底层探测器", 英文与代码标识 **LowLevelDetector**,  
GitHub 项目名 **AndroidLowLevelDetector** (Q3, 已定).

### 3.7 变体与数据收集

这个产品有两个发布构建, **检测功能完全相同**:

| 变体 | 数据收集 | 分发 |
|---|---|---|
| **`foss`** | **没有**: 不含专有 SDK, 不收集遥测. | GitHub Releases. |
| **`firebase`** | Firebase **Crashlytics** (崩溃报告) 与 **Analytics** (使用数据), **默认开启, 目前没有运行时开关能关掉** (专门的遥测开关属于后续, BL-7). | Google Play 和 GitHub Releases. |

应用里的网络开关只管**参考数据同步** (FR-8), 不控制 Firebase 遥测.  
隐私政策从设置页点开, 在浏览器里打开; 政策文件就在本仓库里 (FR-10).
