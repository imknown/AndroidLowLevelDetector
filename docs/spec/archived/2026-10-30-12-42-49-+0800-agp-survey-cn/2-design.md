## 预研设计 (研究阶段怎么组织)

**设计点 1: 多 agent 独立调查**  
当时可行的做法有两种:  
- 方案 A: 单个 agent 做一次综合调查. 好处: 成本只有一份. 代价: 单一模型的盲区与编造没有对照,  
  权衡利弊时只有一方之词.  
- 方案 B: 多个 agent 和模型各查一轮, 互不参考对方的子目录. 实际采用.  
  直接原因: 升级判定要权衡利弊, 各轮之间的分歧本身就是材料.  
  根本原因: AGP 大版本迁移是生疏领域, 单源结论出了错没有第三方能纠正, 只能靠独立复查暴露.  
  代价: 时间与算力成本按轮数增加, 各轮结论会有出入, 由负责人逐处比对.  
  失败时怎么办: 某一轮结论站不住时, 以有可核对证据的那一轮为准, 或再起一轮重查  
  (2026-11-04 与 2026-11-25 的追加就是这种做法).

**设计点 2: 各轮原始记录分存, 外层 README 只做索引**  
- 方案 A: 各轮合并成一份综合报告. 好处: 读起来省力. 代价: 合并必然抹掉各轮的分歧与各自的原话证据,  
  事后复核找不到原文.  
- 方案 B: 每轮一个 frozen 子目录, 外层 living README 的表只加行不合并. 实际采用.  
  理由: frozen 保住写下时的结论与证据, 更正留原处; 表格是唯一入口. 代价: 读的人要跨子目录自己比对.

**设计点 3: 复用外层目录追加**  
- 方案 A: 每轮按日期另起一个外层目录. 好处: 目录名即调查日期. 代价: 同一主题的轮次散落各处.  
- 方案 B: 复用同一外层目录, README 表末尾追加. 实际采用, 2026-11-04 与 2026-11-25 两轮照此执行.  
  理由: 一个主题一处收齐, 表即索引. 代价: 目录名日期只表示创建时间, 里面有跨日期内容; 归档成 record 后  
  不再追加, 另起新目录 (01-聊天与文档内容规则 的 archived 例外, `8e2f3054` 补进规则).

**设计点 4: 结论带证据与核实程度**  
每条核心结论标注核实程度 (已验证 附证据 / 假设 写清依据 / 不确定 写清出处), 分篇正文附文件行号或命令输出.  
无方案取舍: 照 01-聊天与文档内容规则 的 调查报告与分析报告 一节执行, 首轮落盘时就是这个写法.

**预研覆盖的事实核对 (追补于 2026-11-28)**  
四个子目录之间交叉引用 grep 为零; 每轮都含上游线分篇与仓库核对分篇; issuetracker `560282299` 记在  
TRAE 轮 `01-agp-9-1-to-9-6.md:84`; `572377862` 四轮笔记与外层 README 都没有, 网页检索无公开提及,  
建档时间查不到, 不确定它是否晚于末轮 (2026-11-25). 缺口按负责人 2026-11-28 的决定接受, 记录在案,  
不新增调查.

## 实施设计 (e584ae28 到 4041ab5a)

**实施点 1: buildConfigField 迁 variant API, 连带删实验开关 (落实 R-1)**  
- 方案 A: 先不动, 等 AGP 10.0 preview 出实际警告再迁. 好处: 当下零改动. 代价: 10.0 一到构建即断,  
  迁移被压进升级窗口; 05-适配判定 已把移除表核成原文 (已验证档).  
- 方案 B: 现在就迁到 `variant.buildConfigFields.put(...)`, 同一处取值 (分支名还被 `archivesName` 用)  
  一起挪, 不留两份来源; 连带删掉 `android.enableBuildConfigAsBytecode` 实验开关. 实际采用.  
  直接原因: 05-适配判定 判它必改, 依据是官方 roadmap 的 10.0 移除表原文.  
  根本原因: 急切写法是 AGP 10.0 明文移除的 API, 早迁晚迁都要迁, 早迁的 diff 小, 还赶得上在 9.x 线内验证.  
  开关为什么连带删: 它是仓库主动选的实验开关, 06-可选改进 第 8 项原判 "先别动"; 但迁移之后开关开着会踩  
  b/224758957 (字节码路径不写 DSL 外的字段), GIT_BRANCH 会静默丢, 所以删除跟着迁移走. 开关默认 false,  
  删行本身不改行为.  
  代价: 新写法的行为要与旧写法比对; 该比对落在本地 (仓库没有 release 的 CI).  
  失败时怎么办: 迁移后字段缺失或构建失败, 回退该笔提交并回到 `defaultConfig` 写法, 重查取值路径.

**实施点 2: release 收缩走 optimization 块 (落实 R-2)**  
- 方案 A: 保留 `isMinifyEnabled` 加 `isShrinkResources` 加 `proguardFiles` 三件套. 好处: 旧写法,  
  行为已被现有构建验证. 代价: 两个开关必须一起开, 漏配点在; 官方写明旧 DSL 继续受支持, 但写法停留在  
  AGP 9.3 之前.  
- 方案 B: 换 `optimization` 块一处开关 (AGP 9.3 起), 同时覆盖代码收缩, 资源缩减与默认 optimize 规则文件.  
  实际采用. 理由: 少一个漏配点, 规则入口集中. 代价: 新 DSL 的行为要与 release 构建比对一次,  
  成本落在本地 (06-可选改进 第 4 项的风险栏原文). 失败时怎么办: 比对不过回退三件套,  
  该项本来就是可做可不做档.

**实施点 3: Crashlytics 规则进 keepRules 源集 (落实 R-3)**  
- 方案 A: 保留两个 ad-hoc `.pro` 加插件追加. 好处: 现状, 不动. 代价: 规则靠文件列表维持,  
  Firebase 那份在约定插件里追加, 变体归属不直观.  
- 方案 B: 规则放进 `src/Firebase/keepRules/*.keep`, AGP 直接按变体读取 (AGP 9.3 起). 实际采用.  
  理由: 规则跟着变体走, Foss 变体天然不含 Crashlytics 规则. 代价: 06-可选改进 第 5 项的风险栏原文:  
  迁移期两套并存最容易漏, 要么一次换完, 要么先写清单再换; 实际是一次换完 (两个 `.pro` 同笔删除).  
  失败时怎么办: release 构建报缺规则时, 从 git 历史找回 `.pro` 内容并归进 keepRules 源集.

**实施点 4: flavor 源集目录大小写 (落实 R-4)**  
只有一种走得通: 把 `src/foss` 改名 `src/Foss`. AGP 按 flavor 名逐字建源集根, 小写目录只在大小写不敏感的  
文件系统上碰巧可用, Linux CI 上被静默跳过, strings.xml 输给主源集, 这是已经发生的实际缺陷  
(`4041ab5a` 提交信息), 保留小写目录没有可行的替代做法. 改名只动大小写, 内容逐字不变;  
风险是大小写不敏感的本地环境看不出差异, 验证要落在 CI 或大小写敏感的检出上.

**实施点 5: 失效指针留痕不回填 (落实 R-5)**  
- 方案 A: 回改笔记, 把行号与陈述改成新现状. 好处: 笔记与仓库时刻一致. 代价: frozen 笔记被改写后  
  不再是当时的现场快照, 事后复核失去原始出处.  
- 方案 B: 笔记按快照保留, 失效点逐条记进 issue 条目并按已了结归档. 实际采用  
  (负责人 2026-11-26 定的口径). 理由: 预研笔记的价值在 "当时查到什么", 读的人拿 issue #71 的对照表  
  回代码核现状. 代价: 读笔记时要带着 #71 当对照, 旧指针不能直接信. 失败时怎么办: 对照表自己失效时,  
  按死链就地修, 不回改笔记结论.
