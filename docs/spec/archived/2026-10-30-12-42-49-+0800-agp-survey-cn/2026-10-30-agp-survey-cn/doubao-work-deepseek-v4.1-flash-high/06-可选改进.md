# 9.x 线内的可选改进 (不含 Gradle 10)

> **状态**: **frozen**. 写下的结论不改; 后来的更正留在原处.  
> 硬性适配判定在 [05](05-适配判定.md); 仓库取值与实测在 [04](04-仓库核对.md).

判定日: 2026-11-25. 范围限定在 AGP 9.0 到 9.6 与 Gradle 9.0 到 9.9.2 这两条已发布线;  
Gradle 10 与 AGP 10 的东西不进来. 证据只有官方发布说明与本仓库当场跑的构建或 grep.

## 一句话

**硬性要改的仍然是零.** 下面这些都是"能更好", 不是"不改就坏".  
按收益与风险分三档: 三项建议做, 三项可做可不做, 两项先别动.

## 建议做

### 1. 给 release 路径补一道 R8 规则校验

- 依据: AGP 9.3 起有独立任务 `:app:analyzeReleaseR8Config`, 它只生成 R8 配置分析报告,  
  不走完 APK 或 Bundle 的整条流水线, 反馈比跑整个 release 快得多.
- 现状: CI 跑的是 `assembleFossDebug`, 两组单元测试与 `lintFossDebug`, 见 `.github/workflows/android-ci.yml` 第 36 到 42 行;  
  release 的压缩与混淆路径一次都没被验过, 而仓库的 release 开着代码压缩与资源缩减,  
  规则散在 app 的两个 `.pro` 与 base 的 consumer 规则里.
- 收益: 规则写错能在 CI 里暴露, 不用等发版.
- 风险: 第一次跑很可能报一堆既有规则的提示, 需要一份可接受的基线, 否则会变成噪音.

### 2. 处理 `compileSdkExtension` 这个死配置

- 依据: `gradle/toml/build.toml` 第 16 行有 `compileSdkExtension = "24"`, 注释写着 `37.2-ext24`;  
  但 `KotlinAndroid.kt` 第 40 行把它注释掉了, 值根本没进 DSL.
- 现状: 真值源说扩展 24, 代码没用; 读配置的人会以为扩展 SDK 已生效.
- 收益: 去掉一处说一套做一套的配置, 或把注释接上让扩展真的生效. 两条路选一条, 别停在这.
- 风险: 若接上, 要确认 AGP 对扩展 SDK 的支持面; 若删掉, 要确认没人指望它.

### 3. git 取值的兜底写法

- 依据: 现在 `AndroidApplicationConventionPlugin.kt` 第 37 到 39 行用 `runCatching` 包住 `ProviderFactory.exec`;  
  Gradle 在配置阶段执行外部命令失败时会记成 configuration cache problem,  
  仓库又开着 `integrity-check`, 一条 problem 就把构建判失败. 实测里两次失败都是这个路径.
- 现状: `runCatching` 接不住这一条, 环境里没有 git 时整个构建失败, 而不是退回 `unknown`.
- 收益: 构建不再被一个可选信息 (分支名) 拖死.
- 风险: 兜底出来的 `unknown` 会写进 buildConfig 与产物名, 要在产物里能看出来, 别静默.

## 可做可不做

### 4. 用 `optimization` 块替掉旧的开关组合

- 依据: AGP 9.3 起 `optimization` 块可以在 build type 里配置 R8; 开优化会同时打开代码优化与优化后的资源缩减,  
  也不必再手动指定默认的 Android keep 规则文件. 官方写明旧 DSL 继续受支持.
- 现状: `app/build.gradle.kts` 第 88 到 96 行用的是 `isMinifyEnabled` 加 `isShrinkResources` 加 `proguardFiles`,  
  写法正确, 只是旧.
- 收益: 少一个漏配点 (两个开关必须一起开), 规则入口更集中.
- 风险: 新 DSL 的行为要与 release 构建比对一次; 仓库目前没有 release 的 CI, 比对成本落在本地.

### 5. 用 keepRules 源集放规则

- 依据: AGP 9.3 引入 `src/<variant>/keepRules/` 源集, 文件后缀 `.keep`, 新旧 DSL 都能用,  
  app, library 与 KMP 的 consumer 规则都支持.
- 现状: 规则靠 `proguardFiles(...)` 拼文件列表, app 的 Firebase 那份还是在约定插件的第 41 行追加进去的.
- 收益: 规则跟着变体走, 不再靠文件列表维持顺序.
- 风险: 迁移期两套并存最容易漏, 要么一次换完, 要么先写清单再换.

### 6. 配置阶段的时间戳

- 依据: `AndroidApplicationConventionPlugin.kt` 第 36 行的 `getCurrentDatetime()` 在配置阶段取 `Instant.now()`,  
  结果进第 41 行的 `archivesName`, 也在 buildConfig 里出现.
- 现状: 产物名带分钟级时间戳, 两次构建的产物名一定不同.
- 收益: 去掉时间戳后产物名可复现, 缓存与比对都更省事.
- 风险: 发版产物名不再自带时间, 需要别处记录构建时间, 这是使用习惯的改动.

## 先别动

### 7. `configureondemand` 与并行配置缓存

- 现状: `gradle.properties` 同时开着 `org.gradle.configureondemand=true` 与 `org.gradle.configuration-cache.parallel=true`,  
  构建能过, 两条都标 incubating.
- 为什么先别动: AGP 10 要完整支持 Project Isolation, 而这个开关去留官方没说法; 9.x 线内它没有坏处,  
  现在动它等于用一次不确定的 A/B 换一个不确定的收益.

### 8. 实验开关 `android.enableBuildConfigAsBytecode`

- 现状: 每次配置打一条 experimental 警告, 构建结果正常.
- 为什么先别动: 它是仓库主动选的实验开关, 与版本适配无关; 要评估的是收益, 不是兼容.

## 为什么不把这些算成适配

AGP 9.x 的发布说明里, 旧 DSL 明确"继续受支持"; 上面第 1 到 3 项都不涉及兼容性, 只涉及配置正确性与反馈速度.  
第 4 到 6 项是写法新旧, 不做也不会在 9.x 线内报警.  
所以 9.x 线的答案是: **没有要适配的; 有三处值得顺手修, 三处看心情, 两处先放着.**
