# 03 可以直接采用的改进

> **状态**: **frozen**. 记下调查时 (2026-11-20) 能走得通的几种写法, 每种的好处与代价.  
> 这些是本篇的判断, 不构成项目规定.

## 1. 删掉 `AppRoot` 里那行 `@OptIn`

`ui/AppRoot.kt:142` 的 `@OptIn(ExperimentalMaterial3Api::class)` 和它后面那句注释, 前提是 `TopAppBar` 还实验性.  
1.5.0 把它转成稳定, 前提没了.

- 好处: 少一个用不上的 opt-in, 注释和当前库对得上.
- 代价: 只动 `ui/AppRoot.kt` 一行注解加一行注释. 用户看不到变化. 失败时把这行加回去即可.
- 失败时怎么办: 编译报 "This declaration is experimental" 就把 `@OptIn` 恢复, 并把注释改成实际版本前提.

核实程度: 转述未核 (出处: material3 `TopAppBar` 的 API 参考页, 重载上只剩 `@Composable`).

## 2. `ListItem` 三处迁到新重载

`ui/settings/SettingsScreen.kt:214`, `:222`, `:300`.

- 好处: 消掉弃用警告; `:300` 那处 `SettingsChoiceRow` 还能顺手用新重载的 `onClick` 参数,  
  把现在挂在 `Modifier` 上的 `clickable` 换成组件自带的交互 (见第 3 条).
- 代价: 动 `ui/settings/SettingsScreen.kt` 三处调用加 `SettingsChoiceRow` 的函数体.  
  用户能看到的变化是行高与内边距可能差一点, 因为新重载的形状和内容内边距默认值换了.  
  `FR-12` 的 "主题与控件: Material 3" 那一条的验收要看设置页截图.  
  回退就是恢复旧的带 `headlineContent` 的写法, 三处一起回.
- 失败时怎么办: 迁完对着旧截图比, 行高对不上就在调用点显式传 `contentPadding` 和 `elevation`;  
  显式传参也调不回旧观感, 就整条回退, 先留着弃用警告.

核实程度: 弃用事实转述未核 (出处: material3 `ListItem` API 参考页的弃用说明);  
三处行号与 `clickable` 挂点当场核过.

## 3. 列表行从 `Modifier.clickable` 换成组件自带的交互

`ui/settings/SettingsScreen.kt:218`, `:236`, `:304`.

- 好处: 点击语义由组件给, 读屏念的角色和状态跟 M3 一致; 少一个自己挂的 `clickable`.
- 代价: 动同样的三处. 用户能看到涟漪范围与按压反馈可能变, 还多一个副作用:  
  1.13 起 `clickable` 自动播系统点击音, 换成组件自带的交互后这条依旧生效, 见 04.  
  回退是把 `onClick` 参数删掉, 把 `Modifier.clickable` 加回去.
- 失败时怎么办: 涟漪范围对不上就把 `clickable` 加回去; 声音那条单独按 04 处置, 不混在这次里改.

核实程度: 三处挂点当场核过; 交互效果的差别是本篇按 API 形状推断的, 没在设备上比过.

## 4. 用官方的 `Modifier.nonInteractiveScrollbar` 替掉手写的那份

现在 `ui/common/ScrollBarExt.kt` 整份是自己画的滚动条, 文件开头的注释就写着它是等官方修改器的替代品.  
material3 1.5.0 给了 `Modifier.nonInteractiveScrollbar(state: ScrollIndicatorState, orientation: Orientation, ...)`,  
没有实验性注解.

- 好处: 删掉一份自维护的绘制代码 (整个文件) 和它的两个调用点; 以后滚动条跟 M3 一起更新.
- 代价: 动 `ui/common/ScrollBarExt.kt` (整份删), `ui/base/list/MyModelListScreen.kt:118`, `ui/settings/SettingsScreen.kt:160`.  
  用户能看到的变化集中在三处观感, 都要显式传参才守得住旧样子:
  1. 厚度: 手写版是 4dp (`ScrollBarExt.kt:19`), 官方的默认厚度不同, 要传 `thickness`.
  2. 淡出节奏: 手写版是 250ms 淡出加 300ms 延迟 (`ScrollBarExt.kt:21-22`), 官方有 `fadeDurationMillis` 与 `fadeDelayMillis`.
  3. 颜色: 手写版是 `onSurfaceVariant` 加 0.52 透明度 (`ScrollBarExt.kt:52-54`), 官方要传 `thumbColor`.  
  另外官方有个 `thumbMinLength`, 轨道长度短于它就直接不画; 手写版的下限是两倍厚度 (`ScrollBarExt.kt:71`).  
  条目特别长的列表上, 拇指会不会消失要用真机看. 还有 `enabled` 参数官方没有, 现在 `enabled = scrollBarMode.drawsScrollBar`  
  那层条件要挪到调用点去判断 `scrollIndicatorState` 是否为 null.  
  回退是把整个文件恢复, 两个调用点恢复原样, 一处改动一份.
- 失败时怎么办: 参数全传一遍还调不出旧观感, 就保留手写版, 只把注释里 "官方还没提供" 那句改成 "官方已提供, 暂不采用"  
  并写清为什么不换.

核实程度: 官方 API 的签名与默认值差异转述未核 (出处: `nonInteractiveScrollbar` 的 API 参考页, 标 Added in 1.5.0, 参数表齐全);  
手写版的参数值与调用点当场核过.

## 5. 给 `LazyColumn` 显式配 `cacheWindow`

1.13 把 `LazyLayoutCacheWindow` 转正, 预取从 `LazyListState` 挪到 composable 的参数上.

- 好处: 快速滑动时提前组合下一屏的条目. 这个项目的列表一个屏就装得下全部条目, 收益接近零.
- 代价: 动两个列表页的 `LazyColumn` 调用, 多一个要真机验证的变量.
- 结论: 这次不推荐. 等哪天真有个长列表再说.

核实程度: 预取位置迁移转述未核 (出处: compose-foundation 1.13.0 发行说明的弃用清单);  
"一屏装得下" 是照检测条目数量判断的, 没数过具体条数.

核实程度: 转述未核 (出处: 2026 年 11 月发布博客的性能一节).

## 7. 查重组用 `runtime-tracing`

BOM 里已经有 `runtime-tracing` 1.13.0, 1.13 的重组追踪能记下状态读写与调用栈, 输出给 Perfetto 看.

- 好处: 卡顿时能定位到哪个状态写入触发了重组.
- 代价: 要加一个只在排查时用的依赖, 还要有 Perfetto 和一段抓取脚本; 追踪本身开销大, 不能开着测帧耗时.
- 结论: 等真出现卡顿再考虑, 现在项目没有性能问题记录.

核实程度: 追踪能力转述未核 (出处: compose-runtime 1.13.0 发行说明与发布博客);  
BOM 里有这个构件当场核过.
