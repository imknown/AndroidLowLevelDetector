## 原始需求 (负责人预写, 任务结束前不改)

问题, 目前 Kotlin LSP 脚本性能太差, 所以重构  
打算: 作为 独立进程, 可以一直活着. 长时间没人使用, 再停止  
风险: 涉及 LSP 功能比较多, 可能需要大量例子和时间重新测试

## 需求条目

工具链任务, docs/requirements-cn 的全局需求正文不覆盖;  
每条验收标准的来源一律标明 (负责人原话, plan.md 目标段, 或 plan 判据).

**R-1 性能**  
单文件诊断与规划查询各降到热查询 2 秒内, 冷启动 (前台启动到 `status` 就绪) 25 秒内, 在本机实测并记录.  
来源: 负责人 2026-11-10 定的核心目标 ("一切为了提升性能, 减少 LSP 时间") 加 plan.md 目标段.  
验收: 热查询同一份文件连续跑十次取最慢一次达标; 冷启动计时达标; 数字只记事实, 不拿另一台 macOS 机器的基线当本机结论.

**R-2 外部契约不变**  
三个 CLI 的命令行, 查询串格式, 输出行, 退出码全部不变, 现有调用处 (03 的核对义务, 10 与 11 的契约, 各调用方) 不用改.  
来源: plan.md 目标段 ("命令行与输出形状不变" 排第一判据).  
验收: 接入前把旧版在同一批查询或文件上的完整输出存成基线文件落本目录; 改完与基线逐行对比, 除 server 版本行外一致.

**R-3 常驻与启动**  
daemon 独立进程常驻, 只由负责人前台启动一次, 这条启动命令是唯一入口; 客户端不自动拉起.  
空闲 20 分钟自动退出; `status` 查状态; `stop` 立刻释放, 之后端点, 锁, JVM 全部清干净; 机器重启或空闲退出后重起一次.  
来源: 负责人预写的 "打算" 加 2026-11-10 的 T1 A 决定 (删自动拉起, 只留手动前台启动).  
验收: 冷启动能起, `status` 能看到, `stop` 后无残留; 陈旧的端点与锁能自动接管.

**R-4 硬失败, 不回落**  
连不上 daemon 时三个 CLI 全部非 0 退出, 打印明确原因与那条可复制的启动命令, 绝不上报 `CLEAN`;  
没有一次性模式, 没有客户端自动拉起, 不自己起 server.  
来源: 负责人 2026-11-10 的 1A 与 2A 决定.  
验收: 三个 CLI 的失败路径各验一遍; 这次没跑 LSP 要写进报告, 不退 0 让流程读成假 `CLEAN`.

**R-5 锁与并发**  
索引缓存锁归 daemon (防多个 daemon 实例抢同一份缓存), 启动时原子拿锁, 退出释放; 客户端不碰锁, 请求按 FIFO 排队,  
两个客户端同时来不互相打断; `workspace/applyEdit` 只回发起命令的那个客户端, 不广播.  
来源: 负责人 2026-11-10 的 3B 决定加共享范围 A (本机所有进程可连, 只服务本仓库).  
验收: 两个客户端并发发同一批请求, 响应按队列顺序不交错不丢失.

**R-6 能力一项不丢**  
能力盘点的每个脚本化行在 daemon 化之后各有一条记录 (能力, 命令, 期望, 实际, 结论); 停用的 `format` 与  
`organize-imports` 修好恢复可用; 未接能力逐样重探, 判定能不能接成可写操作并写清所需条件 (接入实现归后续任务);  
结论回写 10-代码分析规则 的能力盘点, 回写后盘点无过期或互相矛盾的行, 退步项写明原因与去处.  
来源: 负责人 2026-11-09 的决定 ("尽可能保留所有 Kotlin LSP 能力") 加 4A (非提速项全留).  
验收: 矩阵无空行; 五项重探 (format, organize imports, rename, quickfix, type hierarchy) 各有真实请求与应答.

**R-7 非提速项全留**  
版本检查: 读发行版 `build.txt` 加 GitHub releases 最新 tag, 按天缓存, 就绪后异步跑; 有新版本提示附下载链接与校验位置,  
已装旧两代以上额外提示换索引缓存; 发行版过期由启动失败判定并提示, 不混进新版本提示; 只提示, 不下载不安装,  
下载与升级要负责人单独同意. 文档修订与 `ILS-263.7084.0` 注明照旧交付; selfcheck 走 daemon 且分得清  
"没有工程模型" 与 "代码干净".  
来源: 负责人 2026-11-10 的 4A 决定加 plan.md 目标段.  
验收: 断网, 有新版本, 已是最新三种各跑一次 (用可注入的假 tag 与请求失败造), 注入过期信号单列核对; 文档清单逐项 grep 到.

**R-8 单仓库**  
一个 daemon 只服务本仓库, workspace 单根, 不做全机多项目共用.  
来源: 负责人 2026-11-09 定不做多项目.  
验收: 起会话前后比对 workspace 根列表与 `workspace-model-v2.cache` 的键, 只有本仓库一个根, 没有多余项目模型.

**R-9 结果真实**  
常驻会话看到的文档与磁盘一致: 改文件, 回滚, 再改三种情况下诊断都与磁盘一致, 未提交改动也算;  
诊断拉取前等沉降窗口过去; 不存在假 `CLEAN`.  
来源: plan.md 风险段 ("快的前提是文档状态正确, 刷新漏了就是假结果, 比慢更糟") 加判据汇总.  
验收: daemon 侧探针验证 (不经过三个 CLI); 故意构造带编译错误的文件, 改完立刻查不能回 `CLEAN`.

## 技术补充项 (不许替代主标准)

- 协议版本与代码指纹校验: 客户端连上先验, 不匹配报错并提示重启; 后续任务的验证不许落到旧代码的服务进程上.
- Unix socket 权限 0600; daemon 日志按启动截断, 不无限增长.
- Windows 具名管道与路径分支在本机真跑; macOS 那侧只能代码层核对, 不写成实机验证.
- 脚本改动过 `node --check`.
