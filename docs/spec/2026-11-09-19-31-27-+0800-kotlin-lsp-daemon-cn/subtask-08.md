- `10-分析细则:229-230` 现在写"三个脚本不能同时跑", 共用一把锁.  
  daemon 化之后锁归 daemon, 客户端按 FIFO 排队, 这句要改.
- `10-分析细则:232-258` 是编辑产出通道的契约. 规划 (`kotlin-lsp-plan.js:127`) 与编辑  
  (`kotlin-lsp-edit.js:102`) 共用 `KOTLIN_LSP_PLAN_READY_TIMEOUT_MS` 默认 300000,
  验证 (`kotlin-lsp-diagnostics.js:164`) 用 `KOTLIN_LSP_READY_TIMEOUT_MS` 默认 1800000.
- `11-构建与验证:18` 与 `02-工作原则:122` 把每批编辑后的验证顺序写成自审,  
  analyze-file, Kotlin LSP, Gradle 三档, 再委派 review.
- 每个文件的诊断规则在 `10-分析细则:36` 与 `:59`; 按 `plan.md:212` 改成批量一次,  
  11 不写诊断规则.
- `14-跨端review` 记着 review 目录, 提示词, 收报告与工作树冻结. 跨端 reviewer 要用同一个 daemon,  
  指向 10 里那条启动命令.
- 回退丢掉的三处文档修订: `11` 里自审与委派 review 用规划通道查引用面的义务,  
  `10` 里对 `ILS-263.7084.0` 的注明, `scripts/kotlin-lsp-edit.js` 注释里的同一句注明.
- `ILS-263.7084.0` 是发行版 `build.txt` 里的 build 号, server 启动时打印  
  `== Kotlin LSP ILS-263.7084.0 ==`. 字面保持原样, 注明写清它是 server 自报的标签,
  规则文件和脚本里一律叫它 Kotlin LSP.
- `kotlin-lsp-selfcheck.js:1-25` 说明临时哨兵的原理, 写法在 `:92-113`,  
  `:121-141` 按输出里的 `CLEAN (0 items)` 与计数行判模型是否活着.
