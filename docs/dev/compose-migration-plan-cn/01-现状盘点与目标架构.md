# 01 现状盘点与目标架构

> 所属迁移计划：[README](README.md) · 上一章：无 · 下一章：[02 Compose 核心概念速成](02-Compose核心概念速成.md)

本章回答三个问题：现在有什么、痛点是什么、迁完长什么样。 只盘点**界面层**；数据层（DataSource / Repository）与 Compose 无关，全部原样保留。

## 1. 现有界面层清单与迁移处置

### 1.1 Activity 与导航骨架

| 文件 | 职责 | 迁移处置 |
| --- | --- | --- |
| `MainActivity.kt` + `main_activity.xml` | CoordinatorLayout 骨架：MaterialToolbar 顶部栏 + FragmentContainerView 容器 + BottomNavigationView 底部导航；手动做 edge-to-edge 内边距；用 `commitNow` 手动 show/hide 四个 Fragment | 第 6 步内容替换为 `setContent { }`（Activity 本体暂留 `AppCompatActivity`，见 1.4），Scaffold + Navigation 3 接管骨架 |
| `MainViewModel.kt` | 用 SavedStateHandle 记住"上次停在哪个标签页" | 删除；Navigation 3 的返回栈自带 `rememberSaveable` 级保存 |
| `bottom_nav_menu.xml` | 四个标签的图标/文字 | 第 6 步删除；NavigationBar 的 item 在 Kotlin 里声明 |
| `drop_scale.xml` | Fragment 切换缩放动画 | 删除；切换动画交给 Navigation 3 / Material 3 动效 |

### 1.2 列表基建（三个列表页共用）

| 文件 | 职责 | 迁移处置 |
| --- | --- | --- |
| `BaseListFragment.kt` + `base_list_fragment.xml` | SwipeRefreshLayout 包 RecyclerView；订阅 ViewModel 的 `StateFlow<State<List<MyModel>>>`；手动设置内边距、滚动条模式、刷新圈颜色 | 第 2 步起由一个 `@Composable` 列表屏幕替代；第 7 步删除 |
| `MyAdapter.kt` / `MyViewHolder.kt` | ListAdapter + DiffUtil 样板；把 MyModel 绑到控件上 | 第 1、2 步由 `MyModelCard` + `LazyColumn` 替代；第 7 步删除 |
| `MyItemDecoration.kt` | 卡片四周间距 | 由 `LazyColumn` 的 `contentPadding` / `spacing` 替代 |
| `my_view_holder.xml` | 单个条目布局：MaterialCardView 里 标题 + 详情 + 右上角状态色圆点 | 第 1 步重写为 `MyModelCard.kt` |
| `BaseListViewModel.kt` | 加载/刷新/更新列表状态机（`State` 密封接口） | **保留不动**——它只暴露 `StateFlow`，天然适配 Compose |
| `MyModel.kt` / `MyModelExt.kt` | 条目数据模型（标题/详情/颜色/类型）与构造工具函数 | **保留不动**（02 章会讲它和"重组稳定性"的关系） |

### 1.3 四个页面

| 文件 | 职责 | 迁移处置 |
| --- | --- | --- |
| `PropFragment.kt` / `OthersFragment.kt` | 纯列表页，只负责创建自己的 ViewModel | 第 2、4 步换壳为 ComposeView 宿主；第 6 步随导航切换删除 |

### 1.4 主题与工具

| 文件 | 职责 | 迁移处置 |
| --- | --- | --- |
| `resTheme/` 下 themes.xml / colors.xml | View 侧 Material 3 Expressive 主题、动态取色 | 窗口级保留（启动画面、窗口背景仍由 XML 主题提供）；MDC 属性体系随 View 控件一起退役 |
| `ui/theme/` 下 Color.kt / Theme.kt / Type.kt | **已就绪**的 Compose Material 3 主题（含动态取色、高中对比度方案） | 直接使用，个别地方按 M3 Expressive 增强（见第 6 步） |
| `ViewExt.kt`（滚动条开关） | RecyclerView 滚动条设置项 | 处置方案见第 3 步（Compose 官方滚动条现状见附录调研） |

## 2. 现有痛点 → Compose 对应解法（迁移动机）

| 现状痛点（代码位置） | Compose 解法 |
| --- | --- |
| 手动给每个控件挂 `setOnApplyWindowInsetsListener` 算内边距（`MainActivity.initWindowInsets`、`BaseListFragment.initWindowInsets`，后者还要跨 View 拿底部导航高度） | `Scaffold` 自带 `contentWindowInsets`，内容区自动避开系统栏和底部导航栏，零手动计算 |
| 手动 `commitNow` + show/hide Fragment，还要防重复选中（`FragmentManager.switch`） | Navigation 3：一个 `NavDisplay` + 返回栈状态即全部逻辑，且天然支持预测性返回手势 |
| Adapter / ViewHolder / DiffUtil / ItemDecoration 四件套样板 | `LazyColumn { items(list, key = ...) }` 一个函数搞定 |
| SwipeRefreshLayout 刷新圈要手动取两个主题色（`BaseListFragment.initViews`） | `PullToRefreshBox` 的指示器自动用 MaterialTheme 配色 |
| 界面写在一半 XML 一半 Kotlin 里，改个字号要跳两个文件 | 单一 Kotlin；IDE 里改完直接预览（`@Preview`） |
| 主题双轨制：View 控件走 XML 主题、Compose 内容走 `AppTheme`，动态色要两头接 | 迁完后只有 `AppTheme` 一条路 |

## 3. 目标架构

```
net.imknown.android.forefrontinfo.ui
├── MainActivity.kt                // AppCompatActivity + setContent，只做窗口级初始化（第 6 步定型）
├── AppRoot.kt                     // Scaffold + NavigationBar + NavDisplay 多返回栈（第 6 步产出）
├── navigation/NavKeys.kt          // Navigation 3 的四个 @Serializable 目的地（第 6 步产出）
├── base/list/MyModelCard.kt       // 条目卡片组件（第 1 步产出）
├── base/list/MyModelListScreen.kt // 三个列表页共用的屏幕组件（第 2 步产出）
├── base/list/VerticalScrollbar.kt // 自绘滚动条修饰符（第 3 步产出）
├── common/ScrollBarMode.kt        // 滚动条偏好 → Compose 状态（第 3 步产出）
├── home/HomeScreen.kt             // Home 专属屏幕组件：事件收集 + 包一层共用列表（第 4 步产出）
├── settings/SettingsScreen.kt     // 偏好设置重建（第 5 步产出）
├── theme/                          // 已就绪的 Color/Theme/Type + 第 1 步新增 ExtendedColors.kt
└── (home/others/prop/settings 包内现有 ViewModel、repository、datasource 全部原样保留)
```

> Others 与 Prop 两页不设独立 Screen 文件——它们没有页面特有逻辑，第 6 步的 `entryProvider` 里直接装配 `MyModelListScreen(viewModel(...))`（见第 9 章 9.2）。

依赖方向和现在完全一致：**Screen（可组合函数）→ ViewModel → Repository → DataSource**。 变化只有最外层：原来"Activity 持有 Fragment 持有 View"，迁完是"Activity 持有 Compose 内容树"。

## 4. 迁移策略：为什么"先内容、后骨架"

官方迁移指南（[Migrate to Compose](https://developer.android.com/develop/ui/compose/migrate)）推荐的增量路线是： View 体系里先嵌 Compose（`ComposeView` 互操作），一屏一屏换，最后再收骨架。 本项目体量小（单 Activity、四屏、零自定义 View），但这个顺序仍然最优，原因：

1. **每一步都可独立编译、运行、回退**——每步只改几个文件，出问题 git revert 单步即可。
2. **学习曲线平滑**——第 1、2 步只碰"函数 + 状态"两个核心概念；导航和 Scaffold 这些"骨架级"概念留到最后，此时你已具备阅读 Compose 代码的肌肉记忆。
3. **风险递增排序**——列表内容（低风险）→ 偏好设置重建（中）→ 导航与 Activity 切换（高）。最险的一步放在你 Compose 经验最足的时候做。

