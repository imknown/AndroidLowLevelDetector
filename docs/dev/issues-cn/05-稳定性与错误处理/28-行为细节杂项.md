# 28 行为细节杂项

> 返回 [README 索引](../README.md) · [5 · 稳定性与错误处理](../README.md#5--稳定性与错误处理).

**严重程度: P3 | 修复难度: 低**


- `HomeViewModel`: 不再注册任何 SP 监听 (换源到 `SettingsStore` 后手写监听器整体删除, 原条目见 [archived #08](../archived/2-SSOT-唯一数据来源/08-设置无唯一数据来源.md)) — 排序开关由 `init` 里收集 `SettingsStore.outdatedOrderFirst` 实时同步那一条目 (每次发射折成世代计数, Rule 1 即时补 / Rule 2 落地补); `allow_network` 由 `collectModels()` 每次加载时经 `settingsStore.allowNetworkData.first()` 现读, 所以改完开关要手动下拉刷新才生效.
- `LldDataSource`: 下载源由 `isChinaMainlandTimezone()` 单选 (大陆时区 → Gitee, 其余 → GitHub), **失败不回退另一个源** — `HomeViewModel.tryDetectOnline()` 的 catch 直接进 `tryDetectOffline()`, 回退只到离线这一层. 同文件里的 `TrafficStats` 标签按线程走: `EventListener.connectStart()` 拿当前线程 id 调 `setThreadStatsTag()`, 只有 `connectEnd()` 调 `clearThreadStatsTag()`; `EventListener` 没有重写 `connectFailed` (重写 `connectFailed` 的是那个 `ProxySelector`, 里面只 `printStackTrace()` 再转给 `getDefault()`), 所以连接失败的那条线程带着未清的标签回到线程池.
- `MainActivity`: `setTheme(...)` 只在 `onCreate()` 里跑一次, 运行中切主题不会再来一遍; `AppTheme` 的 `SideEffect` 只动系统栏图标明暗 (`WindowCompat.getInsetsController(...)` 的 `isAppearanceLightStatusBars` / `isAppearanceLightNavigationBars`), 不碰 window 底色. 于是切主题后 window 的底色停在旧值 — 用的正是那张底色的地方 (最近任务缩略图, 退出动画) 会闪旧底色.
- `MyModelCard`: 标题 `Text` 在 `Box` 里 `fillMaxWidth()`, 状态圆点是 `Modifier.align(Alignment.TopEnd)` 叠在同一个 `Box` 的右上角, 没有给标题预留 end inset, 所以长译文标题的首行右端会被圆点压住.
- `BaseListViewModel.startLoad()`: `loadJob = viewModelScope.launch { setLoading(true) ... }` 把 "登记 Job" 与 "置起转圈" 分成两步, 两步之间没有原子性 — 从主线程进来时协程体先跑 (`Dispatchers.Main.immediate` 免派发), 此时 `loadJob` 还是上一个值; 从别的线程进来时 `loadJob` 先被赋值, 转圈后起. 去重条件 `loadJob?.isActive == true` 因此读到的不是 "本次加载 + 本次转圈" 这一对状态. 真要收紧, 就把两者合进同一步 (先赋值再置 loading, 或反过来, 总之让状态与 Job 同时可见).
- `base/.../shell/impl/ShellDefault`: 先 `waitFor()` 再读输出流, 管道死锁隐患 (详见 [#24 第 1 项](24-杂项隐患.md)). 它是 AGENTS.md 记在案的 **不依赖 libsu 的原生备选实现**, 零调用是有意状态; 要接线启用, 前置条件是先修这个死锁, 不存在 "顺手删掉" 这个选项.
- `ArchitectureDataSource.getBinderVersionOrThrow()`: `System.loadLibrary(BinderDetector.PREFIX)` 写在函数体里, 每调用一次就调一次 `loadLibrary`.
- `OthersRepository.getBinderStatus()`: `try { architectureDataSource.getBinderVersionOrThrow(driver) } catch (e: UnsatisfiedLinkError) { e.printStackTrace() }` — catch 分支的值是 `printStackTrace()` 的 `Unit`, 与 try 分支的 `Int` 取共同父类型, 于是 `binderVersion` 推断成 `Any`. 命中 catch 时它的值是 `Unit`, 下面那个 `when` 只能落到 `else` (显示 unknown), 64/32 位与 ENOENT/EACCES 的档位全部失效.
