# 18 滚动条数组长度不一致 (真实数据 Bug)

> 返回 [README 索引](../README.md) · [5 · 稳定性与错误处理](../README.md#5--稳定性与错误处理).

**严重程度: P1 | 修复难度: 低**


**直接原因**: 下线 "fast scrollbar" 选项时只改了 keys 一侧:  
`ui/settings/res/values/arrays.xml` 的 `scrollBarKeys` 只剩 2 项 (`fast` 那一行被注释掉),  
并行的 `scrollBarValues` 仍是 3 项 (`fast` 未同步注释).

**根本原因**: 平行数组的两侧没有一起维护; 用两个平行数组 + `zip` 表达 (label, value) 对的建模方式本身就缺少长度一致性保障.

**问题代码**:

- `ui/settings/res/values/arrays.xml`: `scrollBarKeys` 2 项 / `scrollBarValues` 3 项;  
  同文件的 `themeKeys` 与 `themeValues` 是 3/3 对齐的, 两组数组风格不一致.
- `ui/settings/res/values/strings.xml` 与 `values-zh-rCN` / `values-zh-rTW` / `values-fr-rFR`:  
  `interface_fast_scroll_bar_key` 四个文件全部是注释状态, `interface_fast_scroll_bar_value` (= `"2"`) 四个文件全部仍是活资源.
- `SettingsScreen.kt` `SettingsChoiceDialog()` 的 `labels.zip(values)`: `zip` 截断到较短的一侧,  
  第 3 个 value 因此 "藏" 在界面之外, 所以现在既不崩也不显示错.

补齐两侧不是 "把注释放开" 那么轻, 按直觉改一侧的后果是:

- 只放开 `arrays.xml` 里注释掉的 key 行: `@string/interface_fast_scroll_bar_key` 在四个 locale 文件里都是注释状态,  
  资源引用解析不到 → **资源链接失败**, 编译不过.
- 数组项与四个 locale 的 key 字符串一起放开: 长度回到 3/3, 但把已下线的 "可拖动" 选项放回设置界面:  
  `MyApplication` 的 `ScrollBarMode.Draggable` 一直在,  
  `drawsScrollBar` 仍为 false (无实现, 见 [#37](../07-UI与无障碍/37-滚动条可拖动是stub.md)), 选中它等于选 "什么都不画".

反过来把 values 一侧对齐成 2 项是安全的: 界面少一项, 而存着 `"2"` 的老用户读到的仍是 `Draggable`:  
枚举值与那条映射  
(`SettingsStore.parseScrollBarMode()` 里 `getMyString(R.string.interface_fast_scroll_bar_value) -> ScrollBarMode.Draggable`)  
保留着, 正是为了认得它.

所以危害是 **补齐即翻车**, 不是当下已经错位: 现在两侧不一致, 而两种 "把它补回来" 的改法各自撞上一个后果.

**修改方案**:

- 短期: 把 `scrollBarValues` 里 `@string/interface_fast_scroll_bar_value` 那个 item 注释/删除, 让 values 与 keys 一样是 2 项.  
  只能动 item, 不能动字符串本身, 因为 `SettingsStore` 的解析引用着 `R.string.interface_fast_scroll_bar_value`, 删掉它编译不过.
- 更好 (消灭整类问题): `SettingsChoiceDialog()` 不再接收两个平行 `PersistentList<String>` (`labels` + `values`), 改为接收一个  
  `PersistentList<Choice(label, value)>`, 单一数据来源天然不可能长度错位, 也免去 `zip`.
