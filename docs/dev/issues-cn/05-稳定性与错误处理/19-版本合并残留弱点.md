# 19 版本合并的残留弱点

> 返回 [README 索引](../README.md) · [5 · 稳定性与错误处理](../README.md#5--稳定性与错误处理).


**严重程度: P1(🟡) | 修复难度: 低**

字典序比较的四处主体见 [#45 第 8 项](../08-反模式与卫生/45-零散小问题.md); 本条只记其中 lld 版本那一路的两个残留弱点:

- **时区偏移假设**: `LldFileStore.copyJsonIfNeededOrThrow()` 里 `savedLldVersion < assetLldVersion` 是原始字符串比较, 结论正确完全依赖两侧同用固定位宽的 `yyyy-MM-dd HH:mm Z` (`DateTimeExt.kt` 的 `LLD_DATETIME_PATTERN`, 格式化器 `LLD_DATETIME_FORMATTER` 钉 `Locale.US`; 资产 `app/src/main/assets/lld.json` 现为 `"version": "2026-09-28 08:25 +0800"`). 偏移写法不同 (`+0800` vs `+0000`) 时字典序比的是本地钟面数字, 与真实先后无关: `2026-09-28 23:00 +0800` (= 15:00 UTC) 会排在 `2026-09-28 16:00 +0000` (= 16:00 UTC) 之后, 而后者才是较新的一份.
  这条格式假设已经由测试锁定一半: `base/src/test/.../DateTimeExtTest.kt` 覆盖偏移后缀 (`+0800` 通过; `+08:00`, 缺偏移, `T` 分隔与空串不通过) 与同偏移下的往返; `HomeViewModel.tryDetectOnline()` 在联网数据进门处用 `isLldDatetime()` 验货. **仍未锁的两处**: 跨偏移的先后顺序 (没有任何测试拿两个不同偏移的串比较), 以及 `LldFileStore` 本身 (`copyJsonIfNeededOrThrow()` 无测试, 全仓唯一的真实单元测试类就是 `DateTimeExtTest`).
- **在线路径不做版本比较**: 拉取成功后 `HomeViewModel.tryDetectOnline()` 直接 `LldFileStore.saveLldJsonFileOrThrow(lldString)` 无条件覆盖缓存, 前面那道 `isLldDatetime()` 只验格式不验新旧. 于是过期的服务端文件会把本地较新的缓存换掉, 且不会自动回涨: 只要 `allow_network` 开着, 每次联网加载都再覆盖一次; 离线路径的 `copyJsonIfNeededOrThrow()` 只在 `savedLldVersion < assetLldVersion` 时把 **内置资产** 那份拷回去, 所以降级最多退回资产版本 — 一份比资产新但比原缓存旧的过期文件会长期停在缓存里, 被它覆盖掉的那份数据无从恢复.

在线覆盖是当前形态的行为 (服务端副本通常较新), 但过期覆盖这一条不是格式问题而是策略问题: 要么在 `saveLldJsonFileOrThrow()` 之前比较一次版本再决定写不写, 要么认下 "联网时以服务端为准". 两个方向都能落地, 尚未选定, 动手前要先定下来.
