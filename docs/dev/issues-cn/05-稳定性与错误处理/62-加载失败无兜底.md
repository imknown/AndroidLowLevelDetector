# 62 加载失败没有兜底, 结果是崩溃与永久转圈而非降级

> 返回 [README 索引](../README.md) · [5 · 稳定性与错误处理](../README.md#5--稳定性与错误处理).

**严重程度: P1 | 修复难度: 低~中**
**影响文件: `ui/base/list/BaseListViewModel.kt`, `ui/home/HomeViewModel.kt`, `ui/settings/SettingsViewModel.kt`**

## 问题核心

逐条错误隔离 (`guardedMyModel` / `guardedMyModels`) 只罩住每个检测块自己; 守卫之外与守卫本身还有四条失败路径, 通向的是**整页崩溃或永久转圈**, 而不是一条错误行:

1. **`BaseListViewModel.startLoad()` 的 `launch` 没有任何兜底**: 无 `try/finally`, 无兜底 `catch`, 无 `CoroutineExceptionHandler`. `collectModels()` 抛出非 `CancellationException` 时整个 job 失败 — `setModels()` 不执行, `setLoading(false)` 轮不到, 转圈停在半途且列表无任何失败提示 (job 已死, 之后再下拉能重试, 但用户从界面上看不出发生过什么).
2. **`getMounts()` 是检测链中唯一没被守卫的调用** (`HomeViewModel.detect()` 的第二个 `withContext(Dispatchers.Default)` 块内): 22 个 `detectXxx()` 各有 `guardedMyModel(s)` 罩着, 夹在中间的 `homeRepository.getMounts()` 没有 — `MountDataSource.getMounts()` 无 try, shell 失败或解析抛出的 `RuntimeException` 直接穿透 `collectModels()`, 汇入第 1 条的链.
3. **守卫只 `catch (e: Exception)`, `Error` 一律穿透**: `PropertyDefault` 是 object, 初始化时 `Class.forName("android.os.SystemProperties")` — 反射失败会包成 `ExceptionInInitializerError` (是 `Error`), 第一次属性读取就把整页带走, 而不是降级成一行.
4. **`SettingsViewModel` 的加载同样裸奔**: `initBuiltInDataVersionJob = viewModelScope.launch { ... }` 无兜底 — `SettingsRepository.getBuiltInDataVersion()` 里 lld 资产版本那一段 (`withContext(Dispatchers.IO)`) 没有 try, 抛出即 job 静默死亡, 版本行停在空值.

## 直接原因

错误隔离做在了 "每个检测块" 这一层, "块的组合层" (`startLoad` 的 launch 体) 与 "隔离机制自身" (只 catch `Exception`) 没有兜底 — 任何一层失守都没有下一层接.

## 根本原因

失败路径没有被当作一等用例设计: "加载失败该显示什么" 没有答案, 所以各层都默认 "不会失败". 与 [#21](21-网络零超时.md) (请求挂起不结束) 是同一个缺口的两半 — 那条管 "永远不返回", 这条管 "返回得太快 (以异常的方式)".

## 修复方向

- `startLoad()` 的 launch 体包 `try/catch/finally`: `finally` 里 `setLoading(false)`; `catch` 里把异常渲染成一条页面级错误行 (或复用 `toErrorMyModel` 的形态), `CancellationException` 原样上抛.
- `getMounts()` 纳入守卫 (调用点包 `guardedMyModels`), 或把 "失败得空表" 的语义下沉进 `MountDataSource` (与 [#63](63-失败折成结论.md) 的 "不查 `isSuccess`" 一并定).
- 守卫是否扩到 `Error` 需要斟酌 (吞 `Error` 违背惯例), 最小对价是给 `PropertyDefault` 的类初始化加保护或在文档上接受该风险; 随 [#03](../01-架构与分层/03-无三态模型与注册表.md) 重排检测执行模型时一并定.
- 与 [#21](21-网络零超时.md) 同批处理: 那条补超时, 这条补兜底, "加载永远不结束" 的两个出口一起堵上.
