# 63 检测失败被渲染成确定的设备结论 (假阴性/假阳性)

> 返回 [README 索引](../README.md) · [5 · 稳定性与错误处理](../README.md#5--稳定性与错误处理).

**严重程度: P1 | 修复难度: 中 | 状态: 开放 (随行 [#03](../01-架构与分层/03-无三态模型与注册表.md))**

## 问题核心

这个 App 的立身之本是 "报出来的话是真的". 下面的路径里, **读不到 / 读失败** 被折叠成**确定的设备结论** — 方向有错报为红 (假阳性) 的, 也有失败报为绿/否定 (假阴性) 的, 根因相同: 异常、空输出与 "否" 不分.

1. **属性读失败 = "不支持"**: `PropertyReader.getBoolean()` 把任何异常折成 `false` (`catch (e: Exception) { ... false }`), 消费点直接当判定 — A/B (`detectAb()` 的 `PROP_AB_UPDATE`), 动态分区 (`PROP_DYNAMIC_PARTITIONS`), Treble (`PROP_TREBLE_ENABLED`): 反射读失败即整行报 "不支持" + 红. 动态分区的 super 分区兜底还被注释停用了 (`HomeRepository` 里 `// || hasSuperPartition` 一带), 判定只剩两个 boot 属性.
2. **进程位宽读失败 = "32-bit"**: `OthersRepository.getProcessBit()` 里 `isProcess64BitOrThrow()` 任何 `Exception` → `false` → 行显示 "32-bit" — 该行只有 32/64 两态, 异常被当成了其中一个.
3. **失败渲染成健康**: `detectSELinux()` 的失败分支把输出以 "Permission denied" 结尾映射成 **Enforcing + 绿** — "没权限读" 被当成 "正在强制". 又因 `ShellLibSu` 只搬 stdout (stderr 整条丢弃, 见第 5 条), 这个分支实际很可能不可达 — 同一丢弃让失败**既无法归因也无法正确呈现**.
4. **"无证据" 报成具体否定**: `detectAdbAuthentication()` 拿 `ro.adb.secure` 的读数与 `"1"` 比较, 属性缺失/读失败时得到的是占位文案 → 不等 → 报 **Disabled + 红**; 而 AOSP user build 默认就是 1. 同形状: `detectDeveloperOptions()` / `detectAdb()` 用 `Settings.Global.getInt(..., SETTINGS_DISABLED)` 的默认值路径, 读失败即报 "禁用".
5. **shell 失败 = 空表 = 成功路径**: `MountDataSource.getMounts()` 与 `PropRepository.getBuildProp()` 都不查 `isSuccess` 就遍历 `.output` — 命令失败时得到空列表, 走成功路径零行: SAR/APEX 的判定静默退化 (Q+ 上 SAR 那行的结论本就不取决于挂载解析 — `isThe2siSar` 的 `mounts.none {}` 对空表真空成立, 末尾还 `|| isAtLeastAndroid10()`), Prop 的 getprop 块整块无声消失. 配套事实: `ShellLibSu` 只映射 `result.out` (stderr 整条丢弃, `ShellResult.output` 的注释 "Stdout + Stderr" 与实现不符), `ShellResult.exitCode` 全仓零消费 — 失败的信息在源头就被扔了.
6. **参考数据缺失 = 设备落后**: `lld == null` 或库里没收的取值落在各行的 CRITICAL 分支 — 未知渲染红这一半已被接受为各检测项语义的现状 ([#33](../07-UI与无障碍/33-Unknown渲染红色.md), 有意接受), 本条只管反方向的另一半: 缺数据被报成绿 / 否定 (本条 3/4/5).

## 直接原因

取数函数的返回类型表达不了 "有值 / 无值 / 失败" 三种状态, 失败在各自函数里就地折成了布尔或空集合.

## 根本原因

与 [#03](../01-架构与分层/03-无三态模型与注册表.md) (无三态结果类型) / [#42](../08-反模式与卫生/42-字符串当哨兵值.md) (状态藏在字符串内容里) 同根: 没有 "未知/失败" 的一等表示, 每个消费点只能各自猜.

## 修复方向

随 [#03](../01-架构与分层/03-无三态模型与注册表.md) 的三态结果类型一次收口: 取数层返回 "发生了什么" (Found / Missing / Failed), 失败有自己的呈现而不是被折成结论 — 颜色呈现不设统一映射 (见 [#33](../07-UI与无障碍/33-Unknown渲染红色.md), 有意接受). 独立小件进展: `getBuildProp` 已查 `isSuccess` 并渲染源级错误行, `exitCode` 已用起来 (随止血批落地); `MountDataSource` 一半与 `ShellLibSu` 合并 stderr 待做, 后者随 [#03](../01-架构与分层/03-无三态模型与注册表.md) 的主体一并定.
