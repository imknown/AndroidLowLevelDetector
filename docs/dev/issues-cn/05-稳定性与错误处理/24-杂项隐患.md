# 24 杂项: 死代码隐患, 错误信息丢栈, HTTP 状态不查等

> 返回 [README 索引](../README.md) · [5 · 稳定性与错误处理](../README.md#5--稳定性与错误处理).


**严重程度: P2 | 修复难度: 低 (各项独立, 顺手修)**

## 1. ShellDefault 若被启用, 自带管道死锁隐患

`base/src/main/java/.../shell/impl/ShellDefault.kt`: 先 `waitFor()` 再读输出流: 当输出超过管道缓冲区时,  
子进程阻塞在写, 父进程阻塞在等,  
**互相死锁**; 且 `waitFor()` 无超时. 该实现是 **不依赖 libsu 的原生备选**,  
按 [AGENTS.md](../../../../AGENTS.md) 的约定保留 (实际使用的是 `ShellLibSu`),  
目前 `grep ShellDefault` 除定义外 0 命中.

**处置**: 不删. 既然留在仓里, 这条就是 **启用前必做的前置条件**: 任何时候要接线启用,  
必须先改成 "边消费 stdout/stderr 边等进程结束" (读流完成后再 `waitFor()`, 或用独立协程消费流),  
并给 `waitFor()` 加超时. 在满足之前, 它只能保持零调用.  
同一形状的另一处记录见 [#45 第 6 项](../08-反模式与卫生/45-零散小问题.md).

## 2. fullMessage 丢失堆栈, 并把异常类名拼进用户可见文案

`base/extension/ExceptionExt.kt`:

```kotlin
val Throwable.fullMessage
    get() = "${javaClass.canonicalName}: $message\nCaused by: ${cause?.message}."
```

- 整个调用堆栈被丢弃 (`cause?.message` 只有一层), 排障时基本没有信息量;
- 无 cause 时输出 `Caused by: null.`;
- 引用它的文件现有 **10 个**  
  (定义文件之外; `HomeRepository`, `OthersRepository`, `PropRepository`, `SettingsRepository`, `MyModelExt`,  
  `HomeViewModel`, `LldFileStore`, `AndroidVersionExt`, `PropertyReader`, `ShellDefault`).
- 它触达用户可见文案的地方不止一处: 逐条错误隔离之后,  
  `MyModelExt.toErrorMyModel()` 对 **每一个失败的探针** 都渲染 `R.string.result_detect_failed` 并把 `e.fullMessage` 当参数拼进去  
  (`OthersRepository.getPartitionFingerprints()` 的分区错误行同形状),  
  于是异常类名 (例如 `kotlinx.serialization.json.JsonDecodingException`) 直接出现在列表行里;  
  联网链路的 `lld_json_parse_failed` /  
  `lld_json_fetch_failed` / `lld_json_save_failed` 三处同样带 `fullMessage`  
  (`HomeViewModel.errorMessage()`, `LldFileStore.copyJsonIfNeededOrThrow()`).

**修复方案**:

- 就地补齐 cause 链 (改动量 ~10 行, 文件 `base/.../extension/ExceptionExt.kt` + 新增 1 个测试):

```kotlin
val Throwable.fullMessage: String
    get() = generateSequence(this) { it.cause }
        .joinToString("\nCaused by: ") { "${it.javaClass.canonicalName}: ${it.message}" }
```

  两个修复点: cause 链整条保留 (原来只有一层, 深层根因全丢); 无 cause 时只输出一行,  
  不再出现 `Caused by: null.` (尾部句号也随之消失). 现有 10 个引用文件零改动. 配套测试:

```kotlin
// base/src/test/java/net/imknown/android/forefrontinfo/base/extension/ExceptionExtTest.kt
class ExceptionExtTest {
    @Test
    fun fullMessageFollowsCauseChain() {
        val e = IllegalStateException("top", RuntimeException("root"))
        assertEquals(
            "java.lang.IllegalStateException: top\nCaused by: java.lang.RuntimeException: root",
            e.fullMessage
        )
        assertEquals("java.lang.IllegalStateException: top", IllegalStateException("top").fullMessage)
    }
}
```

  现状成因: 模板只取一层 `cause?.message`, 链式异常的深层根因整条丢失;  
  cause 为空时模板照样输出 `Caused by: null.`, 因为拼接模板没有按 "有没有 cause" 分支,  
  而错误摘要的生成规则没有任何测试锁定, 坏了也不会被发现. 该写法出自 `5f8fc45f` (仓库化重构时引入该属性)  
  与 `1266cb6f` (异常处理改造时写成现在的单层形式).

- 再往外一步: Log 里打完整堆栈 (`Log.w(tag, "...", e)`), 用户文案只保留简短摘要  
  (或干脆只说 " 解析失败"), `fullMessage` 仅供调试日志使用. 这一条不夹带在上面那个就地修复里.

范围说明: 异常类名出现在用户可见条目里, 是逐条错误隔离 (`f089854a`) 选定的 "错误行自带证据" 形态, 保留不动;  
完整堆栈进 Log 属于后续增强.

## 3. Ktor 不校验 HTTP 状态码

`LldDataSource.fetchOnlineLldJsonStringOrThrow`: `client.get(url)` 拿到 `HttpResponse` 后直接 `response.body()`,  
全程不看 `status`. 404/500 返回的 HTML 错误页会被当作 "JSON 解析失败"  
降级 (落点见 [#22](22-scheme闸门未启用.md)), 行为碰巧可接受 (有离线兜底),  
但错误归因失真 (用户看到的是 "解析失败" 而不是 "网络/服务异常").  
修复 (客户端复用已随 DI 接入落地, 见 [#16](../04-并发与调度/16-阻塞调用跑在CPU线程池.md) 的历史注记;  
这道闸门单独做):

```kotlin
val response = client.get(url) { headers { append(HEADER_REFERER_KEY, HEADER_REFERER_VALUE) } }
if (!response.status.isSuccess()) {
    throw IOException("HTTP ${response.status.value}")
}
return response.body()
```
