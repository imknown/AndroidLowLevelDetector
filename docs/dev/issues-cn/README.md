## 阅读说明

- **编号是全局顺序号** (`#01` ~ `#58`): 按类别目录的顺序发出, 一个条目一个号. 号只作标识 — 不代表严重程度, 不代表先后, 也不代表类别 (类别看所在目录). 条目被删除后号**不回收**, 所以号会跳空, 目录内也不要求连号; 新条目取下一个号. 条目之间互指写 `[#NN](路径)`, 索引里可以带短题 (`[#NN 短题](路径)`).
  - 本目录不再使用任何按取证批次分的旧代号 — 那些批次各自的文档已删, 代号不再携带信息. 条目正文只留能对代码核对的事实.
  - 严重程度 P0~P3 保留, 它是量级不是标识.
  - 有一个待拍板的问题独立于条目存在: **三态 → 圆点颜色映射** 至今未定, 它是 [#33](7-UI与无障碍/33-Unknown渲染红色.md) 与 [#03](1-架构与分层/03-无三态模型与注册表.md) 的开工前置; 承载问题登记表的文档已删, 所以这个决定在仓库里没有别的落点.
- 每个条目包含: **问题核心代码** (标位置用符号不用行号: 代码成员写 `类.成员()`; 要指到函数内某一句, 再附一句可 grep 的代码原文; 配置与资源条目写 `文件 → 键`), **直接原因**, **根本原因**, **修复方案** (含目标代码). 单点小修与杂项束用简化格式 (结论 + 证据 + 修复方向).
- **严重程度** (问题本身的危险度): **P0** 核心架构问题, 影响全局, 新代码会不断复制坏模式, 或已证实会崩溃卡死 · **P1** 结构性耦合, 或已证实的实际风险 (性能, 正确性, 工程配套) · **P2** 局部坏味道或低概率隐患 · **P3** 卫生项或远期低概率风险. 少数条目在 P1/P2 之下带 🔴🟡🟢ℹ️ — 那是它的原始评估等级, 读的时候按 P0~P3 为准.
- **修复难度**: **低** 原地小改, 1~2 个文件, 不动函数签名 · **中** 跨多个文件或签名会变, 但方案明确, 一次提交可完成 · **难** 需要引入新抽象或新设计决策, 必须分步迁.
- **状态** (现在能不能动): **开放** 无不利前提, 可随时动手 · **随行 X** 与 X 合流实施最省, 不单独开工 · **有意接受** 现状是明确的取舍或非缺陷, 无待办, 保留只为防止重复讨论 · **待负责人定** 动手前需要负责人先给结论 (要么定一个前置选择, 要么确认这件事还做不做).
- 引用已删除的代码时写 "原 `X.kt`, 已随 `<commit>` 删除", 不重定向到替代文件, 也不给行号 — 那是历史, 不是现状.
- 已修复, 已消解, 或描述对象已不存在的条目**直接从本目录删除**, 不保留 "已解决" 行, 不写修订记录 — 记录见 `git log`.

## 总体诊断

项目分了四层 (`Composable` → `ViewModel` → `Repository` → `DataSource`), 方向对, 但**层和层之间传的东西类型不对**: 从 DataSource 一路到 `MyModelCard`, 传的都是 `MyModel` — 一个已经拼好翻译文案, 带好状态色 (`StatusColor`) 的**界面模型** (#01). 于是:

1. 仓库本该只管取数和判断, 却必须拿着 `Context` 才能干活: `MyApplication.getMyString` 今天有 93 处限定调用 (算上 `MyApplication` 内部自调用是 102 处), 其中 70 处在 `HomeRepository` (#01, #02).
2. 设置没有可观察的唯一来源, 五个读取点各自 `getString` / `getBoolean` (#08, #10).
3. 没有注入渠道, 全局可变单例成了默认选项: `myAndroid`, `PropertyManager.instance`, `ShellManager.instance`, `LldManager` (#09, #02, #17).

"高内聚低耦合" 的判断标准是 **改一处, 只动一个文件**. 现在加一个设置项要动 3~4 个文件 (存储键与文案, 选项数组, 设置页的状态/行/回调, 消费方), 加一个首页检测条目要动 2~3 个文件 (`HomeViewModel`, `HomeRepository`, 还要小心列表下标 — #11). 这些不会让 App 直接崩, 但会让每次改动的心理负担越来越重.

与分层无关, 但同级的是三类会直接伤到用户或伤到进度: Prop 页一次加载要做几百次串行跨进程查询 (#30); 检测链在 CPU 线程池上做阻塞 shell 调用 (#14, #16); 测试只有 `base` 一个真实测试类, CI 只编译 (#50, #06). 崩溃链上最紧的一条是 #20: 逐条错误隔离落地后, 两个检测块同时失败会产出同 key 的两行, `LazyColumn` 直接抛异常.
