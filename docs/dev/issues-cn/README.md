## 阅读说明

- **编号是全局顺序号** (`#01` ~ `#67`): 按类别目录的顺序发出, 一个条目一个号. 号只作标识 — 不代表严重程度, 不代表先后, 也不代表类别 (类别看所在目录). 条目被删除后号**不回收**, 所以号会跳空, 目录内也不要求连号; 新条目取下一个号. 条目之间互指写 `[#NN](路径)`, 索引里可以带短题 (`[#NN 短题](路径)`); 指向**已结**条目的编号链到它在 [archived/](archived/) 的原件 (如 [#08](archived/2-SSOT-唯一数据来源/08-设置无唯一数据来源.md)).
  - 本目录不再使用任何按取证批次分的旧代号 (AR-xx / N-xx / F-xx / R-xx 等) — 那些批次的原文档已随各代 tracker 的退役删除, 记录见 `git log`; 现行条目正文只留能对代码核对的事实.
  - 严重程度 P0~P3 保留, 它是量级不是标识.
- 每个条目包含: **问题核心代码** (标位置用符号不用行号: 代码成员写 `类.成员()`; 要指到函数内某一句, 再附一句可 grep 的代码原文; 配置与资源条目写 `文件 → 键`), **直接原因**, **根本原因**, **修复方案** (含目标代码). 单点小修与杂项束用简化格式 (结论 + 证据 + 修复方向).
- **严重程度** (问题本身的危险度): **P0** 核心架构问题, 影响全局, 新代码会不断复制坏模式, 或已证实会崩溃卡死 · **P1** 结构性耦合, 或已证实的实际风险 (性能, 正确性, 工程配套) · **P2** 局部坏味道或低概率隐患 · **P3** 卫生项或远期低概率风险. 少数条目在 P1/P2 之下带 🔴🟡🟢ℹ️ — 那是它的原始评估等级, 读的时候按 P0~P3 为准.
- **修复难度**: **低** 原地小改, 1~2 个文件, 不动函数签名 · **中** 跨多个文件或签名会变, 但方案明确, 一次提交可完成 · **难** 需要引入新抽象或新设计决策, 必须分步迁.
- **状态** (现在能不能动): **开放** 无不利前提, 可随时动手 · **随行 X** 与 X 合流实施最省, 不单独开工 · **有意接受** 现状是明确的取舍或非缺陷, 无待办, 保留只为防止重复讨论 · **待负责人定** 动手前需要负责人先给结论 (要么定一个前置选择, 要么确认这件事还做不做) · **暂缓** 负责人已过目并决定先不动; 不是有意接受, 查清或重启时回到开放.
- 引用已删除的代码时写 "原 `X.kt`, 已随 `<commit>` 删除", 不重定向到替代文件, 也不给行号 — 那是历史, 不是现状.
- 已修复, 已消解, 或描述对象已不存在的条目**挪入 [archived/](archived/)**, 按删除时的原路径原样保存 — 归档即声明 record (见 [AGENTS.md](../../../AGENTS.md) 的 Documentation rules), 内容不再修订; 本页不保留 "已解决" 行.

## 总体诊断

项目分了四层 (`Composable` → `ViewModel` → `Repository` → `DataSource`), 方向对, 但**层和层之间传的东西类型不对**: 从 DataSource 一路到 `MyModelCard`, 传的都是 `MyModel` — 一个已经拼好翻译文案, 带好状态色 (`StatusColor`) 的**界面模型** (#01). 于是:

1. 仓库本该只管取数和判断, 却必须拿着 `Context` 才能干活: `MyApplication.getMyString` 今天有 99 处限定调用 (`MyApplication` 内部已无自调用), 其中 69 处在 `HomeRepository` (#01, #02).
2. 注入渠道已随 Metro DI 接入落地, 依赖型静态单例已清空 (`PropertyManager` / `ShellManager` / `LldManager` 的静态槽与全局 `HttpClient` 每请求新建均不复存在); 剩 `myAndroid` (#09, #17) 与 `MyApplication.instance` / `getMyString` 的收口 (#02, #01).

"高内聚低耦合" 的判断标准是 **改一处, 只动一个文件**. 现在加一个设置项要动 4~6 处 (`strings.xml` 及三份翻译, `SettingsStore.kt` 的 key + flow + 监听分支 + setter, 选项型再加 `arrays.xml`, `SettingsViewModel.kt` 的暴露, `SettingsScreen.kt` 的行, 消费方), 加一个首页检测条目要动 2~3 个文件 (`HomeViewModel`, `HomeRepository`, 还要小心列表下标 — #11). 这些不会让 App 直接崩, 但会让每次改动的心理负担越来越重.

与分层无关, 但同级的是三类会直接伤到用户或伤到进度: Prop 页一次加载要做几百次串行跨进程查询 (#30); 检测链在 CPU 线程池上做阻塞 shell 调用 (#14, #16); 测试只有 `base` 一个真实测试类, CI 只编译 (#50, #06). 崩溃链上最紧的两条: #20 — 两个检测块同时失败会产出同 key 的两行, `LazyColumn` 直接抛异常; #62 — 加载失败没有兜底, 异常穿透时是崩溃或永久转圈而不是错误行. 与之配套, #63 收口另一半: 读不到/读失败被渲染成确定的设备结论 (报 "不支持"/"32-bit"/绿, 或整页涂红).
