# 32 启动路径与性能杂项

> 返回 [README 索引](../README.md) · [6 · 性能](../README.md#6--性能).

**严重程度: P3 | 修复难度: 低 (各项独立)**

一组各自都不大, 但都落在启动路径或每次加载路径上的开销, 逐条记在这里, 攒批处理.

- **`MyApplication.onCreate()` 主线程同步读 SharedPreferences**: 昔日的 `initTheme()` / `initScrollBar()` 已随 `SettingsStore` 的落地删除 (原条目见 [archived #08](../archived/02-SSOT-唯一数据来源/08-设置无唯一数据来源.md)), 但启动路径上仍有一次等价的主线程 SP 读 — store 首次解析 (= 构造) 时同步播种两条模式流, 且 `onCreate()` 显式触发该解析. 这是**有意接受的取舍**: 播种必须先于任何组合前读取 (`MainActivity.setTheme`), 换首帧正确性; 若将来要优化, 把播种挪到启动后的后台任务并让界面接受首帧默认值, 是唯一的路.
- **`initMyAndroid()` 主线程反射**: 它经 `getApiAndDesserts()` 反射遍历 `Build.VERSION_CODES` / `Build.VERSION_CODES_FULL` 的字段 (`kClass.java.fields` + `getInt(null)`), 只为算出 "最后一个版本码" 和 `apiFull` / `version` 的推导. [#09](../02-SSOT-唯一数据来源/09-myAndroid可变单例.md) 的方案把它改成 `AndroidInfo.current by lazy { build()}`, 顺带就把这份启动期开销推到了第一次真正需要的时候.
- **`MyDebugApplication` 的 StrictMode 开晚了**: `app/src/debug/.../MyDebugApplication.onCreate()` 先 `super.onCreate()` 再 `StrictMode.enableDefaults()`, 于是 `initMyAndroid()` / store 播种 / `initShell()` 这段启动路径的违规全部漏检. `StrictMode.enableDefaults()` 不依赖 `MyApplication.instance`, 移到 `super.onCreate()` 之前即可.
- **`PropertyDefault` 每次调用重新反射**: `getStringOrThrow()` / `getBooleanOrThrow()` 每次调用都 `getDeclaredMethod(...)`, 而 `PropertyDefault` 正是图里 `IProperty` 的绑定实现 (`PropertyContainer` 的 `@Provides`), `PropertyReader` 每读一个属性走一次. 修法: 把 `Method` 缓存成对象成员, 反射一次复用.
- **`SettingsDataSource` 每 key 一次反射**: `getStringOrNullOrThrow()` 在每个 key 的循环里重新 `getDeclaredMethod("getString", ...)`, 叠加在 [#30](30-Prop页逐key查询.md) 的逐 key 查询上. 同上一条一样, `Method` 提取一次即可.
