# 64 滚动条在组合期订阅滚动状态, 每次滚动起止各重组整页

> 返回 [README 索引](../README.md) · [6 · 性能](../README.md#6--性能).

**严重程度: P2 | 修复难度: 中**

## 问题核心

`ui/common/ScrollBarExt.kt` 的 `Modifier.nonInteractiveScrollbar()` 在**组合期**读滚动状态:

```kotlin
val scrolling = enabled && scrollState.isScrollInProgress
```

这个 modifier 挂在两个页面的滚动容器上  
(`ui/base/list/MyModelListScreen.kt` 的 `MyModelListContent()`,  
`ui/settings/SettingsScreen.kt` 的 `SettingsContent()`), 于是 `isScrollInProgress` 翻动 (滚动开始一次,  
停止一次) 各触发整块 `MyModelListContent` / `SettingsContent` 重组: 重组的不是滚动条, 是挂着 modifier 的整个子树.

**受害面只有开启者**: `enabled` 走 `&&` 短路, 滚动条档位为 None 时不读该状态、不订阅; Normal 档用户滚动全程多付两次整页重组.

## 直接原因

自绘滚动条要跟随 "是否正在滚动" 淡入淡出, 而实现把它当组合期状态读, 建了组合订阅.

## 根本原因

`isScrollInProgress` 是频繁翻动的快变状态, 该在 draw/节点层消费 (`Modifier.Node` 的 `DrawScope` 内读取, 或监听 `interactionSource`),  
不该进组合, 与官方 `scrollIndicatorState` 的设计一致.  
这个文件本来就是官方 `Modifier.nonInteractiveScrollbar` 的替身 (见 [#37](../07-UI与无障碍/37-滚动条可拖动是stub.md)),  
替身比正身多付的重组代价即本条.

## 修改方向

改成 `Modifier.Node` 实现: 滚动状态在节点的 draw/观察逻辑里读, 不建组合订阅, 滚动起止只重画滚动条.  
官方 API 到位后该文件整体删除 (见 [#37](../07-UI与无障碍/37-滚动条可拖动是stub.md) 的既定动作), 本条是替身退役前的性能修正.
