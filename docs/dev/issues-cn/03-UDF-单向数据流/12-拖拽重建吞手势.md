# 12 拖拽进行中 Activity 重建会吞掉下拉手势

> 返回 [README 索引](../README.md) · [3 · UDF · 单向数据流](../README.md#3--udf--单向数据流).

**严重程度: P1(🟡) | 修复难度: 难**

**问题**: 若 Activity 重建恰好落在下拉拖拽进行中, `PullToRefreshBox` 的 `onRefresh` 就不会触发, 没有任何请求发出, 重建后的界面继续显示旧列表.

**载体 (已是 Compose, 页面无 Fragment)**: 三个列表页共用 `MyModelListScreen`, 下拉手势是它内部 `MyModelListContent()` 的 `PullToRefreshBox`, 事件接线是 `onRefresh = viewModel::refresh`; 拖拽进度握在 `MyModelListContent()` 里的 `rememberPullToRefreshState()`. 进页面的加载由 `MyModelListScreen()` 的 `LaunchedEffect(viewModel) { viewModel.init() }` 触发, 而 `BaseListViewModel.init()` 只在 `modelsStateFlow.value == null` 时启动加载, `startLoad()` 另有 `loadJob?.isActive` 去重 — ViewModel 跨配置变更存活时旧列表还在, 于是重建后既没有别处补触发这次手势, 也不会重新加载.

**能否复现**: 未证实, 也无法从源码判定. 是否发生取决于重建落在拖拽的哪一刻, 真机之外没有可检证的渠道; 载体换成 Compose 之后这条链没有在设备上重新验过.

**治好的一半已落地**: "显示过期" 里由设置驱动的那一项 (outdated 目标 SDK 条目的排序) 已由 `HomeViewModel` 收集 `SettingsStore.outdatedOrderFirst` 实时同步, 并由 `HomeViewModel.onModelsLoaded()` 用 `loadStartGeneration` 在每次加载落地后兜底比对 — 这条路就是 [#11](11-HomeViewModel手工编排.md) 的 "纯推导 + 可观察设置" 目标里已经实现的部分.

**取舍 (永久接受, 无待办)**: 不排期 "待处理刷新重放" 特性. 按手势重放做过的修复曾因过于侵入而回退, 留下的代价是极端时机下列表停在旧数据, 用户再下拉一次即可. 保留本条只为防止重复讨论.
