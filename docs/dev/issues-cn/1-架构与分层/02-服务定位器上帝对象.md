# 02 服务定位器满天飞, MyApplication 是上帝对象

> 返回 [README 索引](../README.md) · [1 · 架构与分层](../README.md#1--架构与分层).

**严重程度: P0 | 修复难度: 中 (分两段走, 第一段已随 DI 接入落地)**
**影响文件: `MyApplication.kt`, `PropertyManager.kt`, `ShellManager.kt`, `LldManager.kt`, `PropertyExt.kt`, `ShellExt.kt` 及所有调用方**

## 问题核心代码

`MyApplication` 伴生对象身兼八职 (`MyApplication 的 companion object`): 全局实例, SharedPreferences 持有者, 下载目录工具, 字符串工具, 主题状态流, 主题写入口, 滚动条状态流, 滚动条写入口. 全项目靠它伸手取物:

```kotlin
companion object {
    lateinit var instance: MyApplication                     // ① 全局实例
    val sharedPreferences: SharedPreferences by lazy { ... }  // ② 全局偏好
    fun getDownloadDir() = getFileDir(Environment.DIRECTORY_DOWNLOADS)  // ③ 目录工具
    fun getMyString(@StringRes resId: Int) = ...             // ④ 字符串工具 (102 处调用点, 其中限定形式 93 处)
    val themeMode: StateFlow<AppThemeMode> field = MutableStateFlow(...)  // ⑤ 主题状态流
    fun setMyTheme(themesValue: String?) { ... }             // ⑥ 主题写入口 (`themeMode.value` 的唯一写点)
    val scrollBarMode: StateFlow<ScrollBarMode> field = MutableStateFlow(...)  // ⑦ 滚动条状态流
    fun setMyScrollBar(scrollBarValue: String?) { ... }      // ⑧ 滚动条写入口
}
```

后四项是设置项迁移的产物 ([#08](../2-SSOT-唯一数据来源/08-设置无唯一数据来源.md)): 可观察性是有了, 但 "偏好状态" 这份职责又往同一个伴生对象上叠了两层 — 上帝对象的特征是 "只能长不能缩", 这里正是证据.

base 模块的 "Manager" 不管理任何东西, 只是给全局单例披了层皮 (`PropertyManager`):

```kotlin
class PropertyManager(property: IProperty) : IProperty by property {  // 零附加行为
    companion object {
        lateinit var instance: PropertyManager                        // 存在意义只有这个静态槽
    }
}
```

`ShellManager` 同形. 两者的 `instance` 都在 `MyApplication.initShellAndProperty()` 里被赋值.

顶层函数把全局依赖藏进签名里 (`getShellResult()`, `getStringProperty()`), 调用方完全看不出有隐藏依赖:

```kotlin
fun getShellResult(cmd: String, condition: Boolean = true) = if (condition) {
    ShellManager.instance.execute(cmd)      // ← 看不见的依赖: 谁执行? 线程? 可替换吗?
} else { ShellResult() }
```

此外: `LldManager` (object 单例, 文件 IO) 被 `HomeViewModel`, `LldDataSource`, `SettingsRepository` 三个文件直接引用, 并与 `LldDataSource` 互相引用成环 — Manager 用 `LldDataSource.LLD_JSON_NAME` 定位文件, DataSource 的 `fetchOfflineLldFileOrThrow()` 又返回 Manager 的 `savedLldJsonFileOrThrow`. `HomeViewModel` 还越过仓库直接调 `LldManager` 做文件编排: 三处调用分别在 `tryDetectOnline()` (`saveLldJsonFileOrThrow`), `fetchOfflineLldOrNull()` (`copyJsonIfNeededOrThrow`), `getAssetLldOrNull()` (`getAssetLld`), ViewModel 干了数据源的活.

## 直接原因

需要 Context, 需要跨层取物的代码都从 `MyApplication.instance` / `XxxManager.instance` 这个 "全局服务台" 现拿现用, 构造函数注入只覆盖了 DataSource 一层 (`HomeRepository` 注入了 3 个 DataSource, 但同文件里仍直接用 `MyApplication.instance.packageManager`, `MyApplication.instance.contentResolver`, `MyApplication.sharedPreferences` — 注入了假的, 真的走全局).

## 根本原因

服务定位器 (service locator) 反模式: 依赖不体现在构造函数上, 而是运行时全局抓取. 后果:

- **依赖关系隐形**: 看 `HomeRepository` 的构造函数以为它只依赖 3 个 DataSource, 实际上它还依赖 `MyApplication`, `PropertyManager`, `ShellManager` — 换实现, 写测试, 理清所有权都无从下手.
- **上帝对象**(god object): `MyApplication` 承担了本该属于 "组装处" 和 "工具层" 的职责, 任何新需求都倾向往里加静态方法, 只能长不能缩.

## 修复方案

建一个组合根 (composition root: 全项目唯一一处负责创建和装配对象的地方), 把散落的全局单例 (`MyApplication.instance`, `PropertyManager.instance`, `ShellManager.instance`, `LldManager`, 顶层可变 `myAndroid`) 归拢进去. 组合根由 DI 框架的图承担 (选型见下), 分两段走:

**第一段: 图落地, 接线集中** — `@DependencyGraph` 图 + `@Inject` 构造 + MetroX 工厂接管四个伴生 `Factory`, 第一段已随 DI 接入落地. 本条目点名的四个全局单例与 `myAndroid` 此阶段不动, `MyApplication` 只多持有图:

```kotlin
// MyApplication — 只加一行: 图的持有者 (组合根即图, 不再需要手工容器层)
class MyApplication : Application() {
    val appGraph: AppGraph = createGraph<AppGraph>()
    // ...onCreate 等现状不动...
}
```

**第二段: 静态单例逐个汇入图** — 即下面的配套动作; 每搬一个, 对应的静态槽与全局引用随之删除. `HttpClient` 收成图中的 `@SingleIn` 绑定 (现在是每次请求 new 一整套 OkHttp 引擎, 见 [#16](../4-并发与调度/16-阻塞调用与HttpClient.md)); `LldManager` 改造后的 `Context` / 文件路径与 `SharedPreferences` 由图绑定. DataSource 层需要 `Context` 时由图提供 (一个 `@Provides`), 不引入 `metrox-android` (它走 `AppComponentFactory`, 要求 API 28, 本项目 minSdk 24).

配套动作:

- `PropertyExt` / `ShellExt` 顶层函数改为 DataSource 的构造依赖: `class MountDataSource(private val shell: IShell)`, `getShellResult(cmd)` 变成 `shell.execute(cmd)` — 依赖显式出现在构造函数里.
- `LldManager` 从 `object` 改成普通类 `LldFileStore(context)`, 文件路径从 `MyApplication.getDownloadDir()` 改为构造时解析好并持有; `LldDataSource` 的取数职责随之并入或注入它, 环消除; `HomeViewModel` 不再直接碰文件 — 持久化编排归仓库.
- 删除 `ShellManager`, `PropertyManager` 这两层薄委托壳. `ShellDefault` **不在此列** — 它是不依赖 libsu 的原生备选实现, 按 [AGENTS.md](../../../../AGENTS.md) 的约定与 [#45 第 6 项](../8-反模式与卫生/45-零散小问题.md) 保留, 不是待删的死代码 (启用前需先修它 `waitFor()` 之后读管道的死锁).
- `getMyString` 的 102 处调用点随 [#01](01-无领域模型.md) 的 mapper 迁移自然消亡: mapper 拿 `Context` 参数, 不再需要全局函数.

**依赖注入选型说明**: `MyApplication.instance` 在过渡期仍作为全局入口保留 (第二段逐步撤除). 方向已定: 引入 DI 框架, 选型 **Metro + MetroX**. 对比如下:

| 方案 | 特点 | 对本项目的判断 |
|------|------|----------------|
| Metro + MetroX | Kotlin 编译器插件, 不经 KSP/KAPT, 编译期建图校验, Anvil 式聚合, KMP; MetroX 覆盖 ViewModel/Compose 注入 | **选定**. 依赖全为具体类型, 现有对象图零 `@Provides` 即可建图; Kotlin 2.4.20 要求 Metro ≥ 1.2.0 (现版 1.4.5, Stable), 插件/运行时/MetroX 须同版本锁升; `metrox-android` 走 `AppComponentFactory` 需 API 28, minSdk 24 不可用, Activity 层走 `LocalMetroViewModelFactory` |
| 手工 AppContainer | 零依赖, 零生成代码, 对象图一目了然 | 过渡形态: 图落地后整层删除, 不单独立项 |
| Hilt | Android 事实标准, KSP2 编译期生成 (无 KAPT stub, Dagger/Hilt/dagger.android 均已支持), Activity/Fragment 注入开箱即用 | 注解与构建复杂度较高; 仅限 Android, 未来走 KMP 需再换 |
| kotlin-inject | 纯 KSP2, 编译期校验, KMP 友好 | 同样可行, 但仍是独立的源码生成 pass, 不进编译器增量路径 |
| Koin | DSL 上手快, 注解扩展可补编译期校验 | 核心仍是运行时解析, 错配运行期才暴露 |

判断依据: 版本兼容 (Kotlin 2.4.20 ↔ Metro 1.2.0+, 无 KSP 依赖, minSdk 24 无约束), 接入面 (MetroX 直接接管四个伴生 `Factory` 与 `viewModel(factory = ...)`, Navigation 3 的 entry 作用域不变), 隔离面 (Foss/Firebase 双 flavor 无交互, Metro 为 Apache-2.0 纯 Kotlin 库), 构建性能 (官方基准: ABI 变更增量构建约为 Dagger+KSP 的 1/4). 一项待验证: Gradle 9.7.1 + AGP 9.4.1 组合不在官方兼容矩阵内 (矩阵只约束 Kotlin), 接入时以 `assembleFossDebug` 冒烟. 升级纪律: 升 Kotlin 必须同步升 Metro, 以官方兼容矩阵为准.

**不采纳的一条路线**: 把 `PackageManager` / `packageName` 下沉进仓库. Context 是 View 层的东西, 压进 ViewModel/Repository/DataSource 会让这些层绑死 Android 框架, 没法做 JVM 单测, 也是 Compose 迁移的阻碍; View 层解析 Context 后把值传下去是正路. 真正的依赖抽象 (让仓库不再需要 `PackageManager`) 归本条目与 DI 重构.
