# 02 服务定位器: DI 接入已落地, 剩 `MyApplication` 收口

> 返回 [README 索引](../README.md) · [1 · 架构与分层](../README.md#1--架构与分层).

**严重程度: P1 (DI 接入后由 P0 收窄) | 修复难度: 中 (两段均已落地, 剩最后收口)**
**影响文件: `MyApplication.kt` 及剩余全局引用方**

## 已落地 (随 DI 接入, 明细见 git log)

- 组合根收敛为 `di/AppGraph.kt` 的 Metro 图 (`@DependencyGraph(AppScope)`, 图工厂经 `@Provides` 参数绑定 `MyApplication`): 四条 ViewModel 链全部 `@Inject` 构造注入, entry 经 `metroViewModel<>()` 解析, 四个伴生 `Factory` 整体删除 (第一段).
- 依赖型静态单例清空 (第二段, 每搬一个删对应静态槽): 全局 `HttpClient` 收成图内 `@SingleIn` 绑定, 经 `Provider` 惰性解析; `ShellLibSu` 以 `@ContributesBinding` 直接贡献 `IShell`; `IProperty` → `PropertyDefault` 容器绑定, 回退逻辑类化为 `PropertyReader`; `LldManager` 改为注入类 `LldFileStore`, 与 `LldDataSource` 的引用环消除, `HomeViewModel` 不再直接碰文件; `SharedPreferences` 容器绑定, `HomeViewModel` 构造注入 (现由 `SettingsStore` 消费).
- 随之消亡的形态 (引用已删除的代码时按规则记历史): 原 `PropertyManager.kt` / `ShellManager.kt` 两层零行为委托壳已分别随 `8b5dc266` / `c87137a2` 删除; 原 `PropertyExt.kt` / `ShellExt.kt` 顶层函数 (把全局依赖藏进签名里的形态) 已随 `8b5dc266` / `c87137a2` 删除, 职责分别由注入的 `IShell` / `PropertyReader` 承接; 原 `LldManager.kt` object 单例已随 `6e4e9ebf` 删除.

## 剩余问题核心 (现状代码)

`MyApplication` 伴生对象仍身兼数职 (`MyApplication 的 companion object`):

```kotlin
companion object {
    lateinit var instance: MyApplication                     // 全局实例
    val sharedPreferences: SharedPreferences by lazy { ... }  // 全局偏好持有 (图已绑定, 唯一消费者是 SettingsStore)
    fun getMyString(@StringRes resId: Int) = ...             // 字符串工具 (99 处调用点, 全部为限定形式 → [#01](01-无领域模型.md))
}
```

(`getDownloadDir()` / `getFileDir()` 已随 `LldFileStore` 落地移出伴生, 成为实例成员. 伴生对象上曾经的主题 / 滚动条 StateFlow 与写入口已随 `SettingsStore` 的落地迁出本类, 原条目见 [archived #08](../archived/2-SSOT-唯一数据来源/08-设置无唯一数据来源.md).)

`MyApplication.instance` 仍是图之外的全局伸手点: `HomeRepository` / `HomeViewModel` / `LldFileStore` / `OthersViewModel` / `PropRepository` / `SettingsRepository` 等直接经它取 `packageManager` / `assets` / `contentResolver` / 字符串 (`getMyString`).

## 直接原因

`MyApplication.instance` 是图之外的第二个入口: 图只负责构造期的装配, 而 "运行中途随手拿" 的调用点 (`Composable` 里的 `MyApplication.getMyString`, 仓库里的 `instance.packageManager`) 从未纳入构造签名.

## 根本原因

服务定位器 (service locator) 反模式的残余: 依赖不体现在签名上, 而是运行时全局抓取. DI 接入已证明图能覆盖构造期依赖; 剩余抓取点都是 "图建立之后才发生的取用", 各归其条目收口 (见下).

## 修复方案 (剩余收口, 各归其条)

- `getMyString` 的 99 处调用点随 [#01](01-无领域模型.md) 的 mapper 迁移自然消亡: mapper 拿 `Context` 参数, 不再需要全局函数.
- `myAndroid` 归 [#09](../02-SSOT-唯一数据来源/09-myAndroid可变单例.md) (独立小件, 不在本条目).
- 上述全部完成后, `MyApplication.instance` 静态槽随之撤除 — 最终形态: Application 只持图与生命周期.

**选型记录 (已验证)**: 方向已定并落地 — **Metro + MetroX** (Kotlin 编译器插件, 不经 KSP/KAPT, 编译期建图校验, Anvil 式聚合, KMP; MetroX 覆盖 ViewModel/Compose 注入). 落地后的核对结论: Kotlin 2.4.20 要求 Metro ≥ 1.2.0 (现版 1.4.5, Stable), 插件/运行时/MetroX 同 `version.ref` 锁升; Gradle 9.7.1 + AGP 9.4.1 组合不在官方矩阵内 (矩阵只约束 Kotlin), 已实测 `assembleFossDebug` 通过; `metrox-android` 走 `AppComponentFactory` 需 API 28, minSdk 24 不可用, Activity 层走 `LocalMetroViewModelFactory`. 升级纪律: 升 Kotlin 必须同步升 Metro, 以官方兼容矩阵为准 (已写入 [AGENTS.md](../../../../AGENTS.md)). 手工 AppContainer 只作为过渡形态存在过, 图落地后未单独立项; Hilt / kotlin-inject / Koin 的对比见 git log 里本条目的历史版本.

**不采纳的一条路线**: 把 `PackageManager` / `packageName` 下沉进仓库. Context 是 View 层的东西, 压进 ViewModel/Repository/DataSource 会让这些层绑死 Android 框架, 没法做 JVM 单测, 也是 Compose 迁移的阻碍; View 层解析 Context 后把值传下去是正路. 真正的依赖抽象 (让仓库不再需要 `PackageManager`) 归本条目与 [#01] 的领域模型.
