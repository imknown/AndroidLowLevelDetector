# 15 检测严格顺序执行, 不感知取消

> 返回 [README 索引](../README.md) · [4 · 并发与调度](../README.md#4--并发与调度).

**严重程度: P1(🟡) | 修复难度: 中**

**结论**: `BaseListViewModel.startLoad()` 只启动**一个**协程;  
三个 ViewModel 的 `collectModels()` 逐个 `tempModels += repository.detectXxx()` 顺序跑完检测器  
(`HomeViewModel.detect()`, `OthersViewModel.collectModels()`, `PropViewModel.collectModels()`).  
app 主源码里 `async(` 为零; 检测序列内部也没有取消检查,  
全仓只有 `BaseListViewModel.startLoad()` 与 `SettingsViewModel` 的 `job?.isActive` 式加载去重.

**取消为什么感知不到**: `HomeRepository` 的 `detectXxx()` 都不是 suspend 函数,  
`HomeViewModel.detect()` 的 22 个调用挤在同一个  
`withContext(Dispatchers.Default)` 块里. 协程只在挂起点观察取消, 所以这一块一旦开跑,  
即使 `viewModelScope` 被取消也要等整块返回才中断,  
块内唯一的例外是读 `/proc/mounts` 那处内层 `withContext(Dispatchers.IO)`.

**调度事实**: 整条检测序列本来就离开主线程: `HomeViewModel.detect()`, `OthersViewModel.collectModels()`,  
`PropViewModel.collectModels()` 外层都是 `withContext(Dispatchers.Default)`;  
`Dispatchers.IO` 用在 lld.json 的拉取/解析/落盘 (`HomeViewModel.tryDetectOnline()`,  
`fetchOfflineLldOrNull()`) 与 `/proc/mounts` 读取 (`HomeRepository.getMounts()`).  
池选得对不对是 [#14](14-检测链用CPU线程池.md) 的事.

**危害**: 慢设备上串行的 shell / `getprop` 探针拉长加载时间; 加载窗口越长, [#17](17-myAndroid并发读写.md) 那类  
" 别的协程正好读到改写到一半的 `myAndroid`" 的机会越大.

**修复归属**: 有界并发落在 [#03](../01-架构与分层/03-无三态模型与注册表.md) 的注册表引擎里: 上限并发, 可取消,  
同时保住**固定展示顺序**与检测器之间的依赖关系,  
取消检查由引擎统一做 (本条与 #03 合流实施最省). 它与 [#14](14-检测链用CPU线程池.md) 同属检测执行模型但相互独立:  
#15 讲并发度与取消, #14 讲线程池的选择.
