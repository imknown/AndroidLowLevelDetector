# 21 网络请求零超时配置, 配合加载去重可永久卡死

> 返回 [README 索引](../README.md) · [5 · 稳定性与错误处理](../README.md#5--稳定性与错误处理).

**严重程度: P2 | 修复难度: 低**

**结论**: `LldDataSource.fetchOnlineLldJsonStringOrThrow()` 建的 `HttpClient(OkHttp)` 只设了 `eventListener` 与 `proxySelector`, 外加 debug 构建的 `Logging` — 没装 Ktor 的 `HttpTimeout` 插件, 引擎配置里也没有 OkHttp 的 `callTimeout` / `connectTimeout` / `readTimeout`, 调用方 `HomeViewModel.tryDetectOnline()` 也没包 `withTimeout`. 全仓 `grep` 这几个名字与 `withTimeout` 均 0 命中.

缺的是 "整体上限" 而不是 "任何一层的超时": OkHttp 自身的默认值仍然生效 (connect / read / write 各 10 s, `callTimeout` 为 0 即无限制), 所以暴露面是服务端慢速吐 body 那一类 — 每次读都在 10 s 内落到几个字节, 单层超时永不触发, 整个请求却没有上界.

**证据**: 请求一旦挂住不再返回, `BaseListViewModel.startLoad()` 的去重就把这次挂起变成永久的 — `if (loadJob?.isActive == true) return` 让之后每次下拉刷新与 `init()` 都静默返回, 不再启动新的加载. 转圈也停不下来: `setLoading(false)` 只在 `setModels()` 里被调用, 协程不结束就轮不到它. `startLoad()` 的 `launch` 块顶层不做兜底 catch, 因此这条链上没有任何自愈.

**修复方向**: 装 Ktor `HttpTimeout` (request / connect / socket 三个时限), 或给 OkHttp 设 `callTimeout`, 或在 fetch 处包 `withTimeout`. 三者都只解决 "请求不结束"; `loadJob` 去重本身保留 (它是配置变更后不重复加载的机制, 见 README "已经做对的地方").
