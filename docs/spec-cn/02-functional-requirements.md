## 2. 核心能力(FR-1 … FR-10)

### FR-1 特性支持检测(P0)

应用在手机本地就能完成检测:按一份 **Android 系统特性检测目录**(特性族如 Treble/VINTF 支持、A/B 无缝更新、动态分区 / system-as-root、AVB / dm-verity;条目级的正式清单见《[检测条目目录](05-detection-item-catalog.md)》,目前是 **TBD**,等产品负责人整理)逐条评估当前系统。

**验收标准**

- AC1:目录里的每个条目,每次检测都恰好得出一个三态结果(见 FR-3)。
- AC2:目录要足够「数据驱动」:加一条、删一条条目,不用把周边界面重新设计一遍(见架构篇的检测引擎)。
- AC3:检测全部在手机本地完成;检测本身不会把任何用户数据发出去。

### FR-2 系统参数展示(P1)

应用把常见的**系统参数**作为辅助信息展示(候选的参数族:构建信息,如品牌/型号/Android 版本/安全补丁级别/指纹;SoC/CPU/ABI;内存;屏幕;电池;系统属性 —— 条目级清单 TBD,见《[检测条目目录](05-detection-item-catalog.md)》)。

**验收标准**

- AC1:参数值是检测时从设备上实时读的。
- AC2:读不到的参数按 FR-6 显示为未知,绝不崩溃或白屏。

### FR-3 三态结果模型(P0)

每个 **Home** 检测条目的结论,只能是下面三种状态之一(负责人澄清,2026-09-06:Others/Prop 是纯展示,没有判定状态 —— 见 FR-14/FR-15):

| 状态 | 含义 |
|---|---|
| **支持** | 检测明确确认该特性受支持 / 已启用。 |
| **不支持** | 检测明确确认该特性不受支持 / 未启用。 |
| **未知** | 检测给不出答案 —— 包括*检测本身失败*(抛异常、API 被拦、读不到值)。未知的条目绝不能显示成肯定或否定。 |

**验收标准**

- AC1:三态指示是结果列表里**最重要的视觉元素**。
- AC2:不存在第四种用户能看到的状态;未知条目背后的错误细节会记到日志里(供排查 / 以后的详情页用),本版本不要求展示。
- AC3:转屏 / 界面重建后,显示的还是原来那个状态,不重新跑检测。

> 视觉呈现见 FR-15;叫什么名字还没统一(Q9,见《[03](03-nfr-release-and-open-questions.md)》)。

### FR-4 进入屏幕自动检测(P0)

**已并入 FR-13** —— 列表生命周期只在这一条里规定:进入就跑、去重、重建安全、懒加载、缓存与恢复。FR-4 这个编号保留,含义是:*进入屏幕就自动触发一次检测,而且只触发一次,不重复*。

### FR-5 下拉刷新(P0)

用户应该能在结果屏幕上**下拉刷新**,手动触发一次完整的重新检测。

**验收标准**

- AC1:刷新图标从刷新开始到结束一直可见,完成后消失。
- AC2:刷新过程中,再多下拉几次也不能启动重复的检测(和 FR-13 的去重规则一致)。
- AC3:刷新会重跑全部条目;刷新过程中单条隔离(FR-6)照常生效。

### FR-6 单条错误隔离(P0)

任何一个检测条目失败,**只影响它自己那一条**。

**验收标准**

- AC1:失败的条目显示为未知;其余条目不受影响,照常正确。
- AC2:**不存在整页级的错误状态**:一条(或几条)失败,不能把整个列表换成一屏错误,也不需要「要么全重来、要么全不动」式的重试。
- AC3:失败要留得下证据(日志)方便排查,但不能挡着用户用。

隔离在架构上怎么落实,见架构篇「错误处理策略」;错误文字怎么显示在行里,见 FR-14。

### FR-7 服务端参考数据同步、比对与离线缓存(P1)

应用要能同步**服务端参考数据**,并拿它和本地查到的数据**比对**(用来核对 / 补充展示的结论)。服务端数据要**缓存在应用自己的私有目录里**,这样离线或禁网时应用照样完全可用。

拉取 / 内置回退 / 版本合并的具体行为在 FR-16 里规定。

**验收标准**

- AC1:参考数据放在应用**私有目录** —— 应用私有的外部文件目录(Downloads 子目录),按 Android 存储规范可以退回到内部 files 目录;绝不放公共存储 —— 且离线可用。
- AC2:同步失败就平稳退回:继续用过期的缓存;按 FR-6,不会出现整页错误。

拉取 / 解析 / 版本合并 / 离线的验收标准统一写在 **FR-16** —— 只维护这一处,不重复。

> 具体比什么、比不上怎么展示 —— 处理方式见《[03](03-nfr-release-and-open-questions.md)》Q2(2026-09-12 已定)。

### FR-8 用户可控的网络开关(P1)

应用要提供一个**用户能看到的开关**,用来开 / 关**服务端参考数据同步**(FR-7)。

这个开关**故意只管参考数据同步**,不管遥测 —— 遥测行为由发布版本决定(FR-10)。

**验收标准**

- AC1:开关关闭时不发任何参考数据同步请求;应用读缓存。
- AC2:开关不影响 `firebase` 版本里的 Firebase Crashlytics/Analytics(遥测归 FR-10 管)。
- AC3:开关在设置页「功能」组,**默认关闭**,当前只控制服务端 json 的下载(FR-17;2026-09-05 决定)。

### FR-9 合法检测手段(P0)

检测可以用**任何合法的技术手段**,包括但不限于:

1. 公开的 SDK API;
2. 反射调用隐藏 / `@hide` 框架 API 和内部服务;
3. Shell 命令输出(如 `getprop`、`dumpsys`);
4. root 或 Shizuku 可用时的提权检测(可选的增强路径)。

**验收标准**

- AC1:提权路径(root/Shizuku)是**可选的增强**;没有它就退回普通方式检测,或者显示未知 —— 绝不崩溃,也绝不误报「不支持」。
- AC2:用的所有手段必须合法且只读(NG5、NG6)。

### FR-10 双发布变体 —— `firebase` / `foss`(P1)

产品以两个构建变体发布,**检测功能完全一样**。每个版本的事实(收集什么数据、在哪发布、遥测默认开不开、F-Droid 历史)以《[01 — 产品与用户](01-product-and-users.md)》的变体与数据收集表为准 —— 只写这一处,不重复。以后可能会加一个运行时的遥测开关(BL-7)。

**验收标准**

- AC1:`foss` 变体不直接或间接包含任何 Firebase(或其他专有遥测)组件。
- AC2:检测功能(FR-1 … FR-6)在两个变体里完全一致。
- AC3:`firebase` 变体里 Crashlytics/Analytics 默认开启,行为不受 FR-8 网络开关影响。
- AC4:设置页有隐私政策入口,在浏览器里打开在线政策。

## 3. 应用外壳与界面(FR-11 … FR-17)

### FR-11 单 Activity、单实例(P0)

应用有且只有一个 **`MainActivity`**。任何应用随时可以用任意 intent 标志启动它。

**验收标准**

- AC1(修订,负责人裁定 2026-09-06):正常启动路径(桌面、最近任务、外部应用)都复用已有的那个 `MainActivity` —— `launchMode="singleTop"`,重复发来的 intent 走 `onNewIntent`。遗留问题:特殊的标志组合(`FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_MULTIPLE_TASK`、`… | FLAG_ACTIVITY_CLEAR_TASK`)还是可能创建新任务 / 新实例并把内存状态清掉;先接受这个隐患 —— 要不要加任务栈方面的防护记在 **BL-8**(可能没必要)。
- AC2:被外部重新拉起后,已有实例的状态完整保留(不重置、不产生重复的返回栈)。

### FR-12 外壳布局与滚动行为(P0)

> 2026-09-12 决定:下面的**滚动行为**(AC1)和「大屏显示 NavigationRail」这两件,**推迟到 Compose 改版一起做** —— 现在用 View 做,Compose 时也要整个重写,等于做两遍。

- 主题和控件:**Material 3 Expressive**(View 体系)。
- 根布局:**CoordinatorLayout** 或 Scaffold 布局。
- 顶部:**Toolbar** 显示应用名;debug 构建标题固定为 **「LLD Debug」**。
- 底部:**BottomNavigationView**,四个标签依次是 **Home、Others、Prop、Settings**,分别对应 `HomeFragment`、`OthersFragment`、`PropFragment`、`SettingsFragment`。大屏上显示为 **NavigationRail**(或等效的自适应形态;这一条推迟到 Compose 批次)。
- 中部:fragment 容器,放当前 fragment。
- 四个 fragment 的内容都可能超出一屏,必须能滚动。
- Edge-to-Edge:因为底栏可以隐藏,列表底部留白 = **导航栏高度 + BottomNavigationView 高度**。

**滚动行为**(推迟到 Compose 批次;优先用框架默认;实现保持简单;细节可以再商量):

- 手指从下往上拖(定义为*列表向下滚动*):Toolbar 被慢慢推出屏幕,**BottomNavigationView 隐藏**(快一点的动画)。
- 反方向滚:Toolbar 回来,**BottomNavigationView 重新出现**;动画必须能被打断,并从打断的位置往回放。

**验收标准**

- AC1:向下滚动时 Toolbar 和底栏都隐藏;向上滚动两者都回来;被打断的动画平滑反向。
- AC2:底栏两种状态下,底部留白都正确(内容不被裁掉,也没有点不到的死区)。(随滚动行为一起推迟到 Compose 批次;底栏只有一种状态时,留白正确的要求照常生效。)

### FR-13 列表生命周期:进入、懒加载、缓存、恢复(P0;含 FR-4)

四个 fragment 都适用 —— **列表生命周期只在这一条里规定**(FR-4 的进入 / 去重 / 重建内容并在这里):

- 进入结果屏幕就自动触发**恰好一次**检测 —— 第一次进入和之后再进都算(含 FR-4)。
- 已经有检测在跑的时候再进入,绝不启动第二个并发的完整检测(**去重**;FR-5 刷新同样受这条约束)。
- 检测状态由**活得比 Activity/Fragment 重建更久**的对象保存:正在跑的检测继续跑,把结果交给重建后的屏幕;或者已经完成的状态直接重新显示 —— 绝不重置、绝不重复跑、绝不卡在加载图标上。
- 用户从没打开过的 fragment **绝不初始化、绝不加载数据**。
- 正常首次启动显示 **HomeFragment**(底部导航选中 Home)并加载它的数据。
- 点击标签时:**显示**目标 fragment,**隐藏**上一个,**然后加载**目标的数据。
- 已加载的 fragment 保持**缓存 —— 数据也在内**;缓存一直复用,直到用户主动刷新(FR-5)。
- 进程在后台被杀后应用重建:**最后显示的那个 fragment** 直接恢复为当前标签,数据按「先显示后加载」的常规规则来(内存缓存随进程没了;活下来的 ViewModel 缓存照用)。

**验收标准**

- AC1:冷启动只初始化 HomeFragment;其余 fragment 第一次被访问时才初始化;每次进入只触发一次检测 —— 正在跑的绝不重复跑。
- AC2:切换标签绝不重新跑已加载 fragment 的检测,除非用户刷新。
- AC3:进程被杀后,最后显示的 fragment 恢复为当前标签,数据按常规规则加载。
- AC4:检测期间转屏 / 换主题,绝不重置、重复或卡死加载状态。

### FR-14 共享检测列表基类(P0)

`HomeFragment`、`OthersFragment`、`PropFragment` 共用一个列表基类(按特性放在一起的架构原则 P4):

- 基于 **RecyclerView**;**每行 = 一个独立的检测条目**。
- 每行是一张 **MaterialCardView**,由**标题和内容**组成(两者都可以多行)。
- **屏幕分工**(负责人澄清,2026-09-06):**Home 是判定屏** —— 每行带三态结论(FR-3)和判定圆点(FR-15)。**Others 和 Prop 是纯展示**:只有标题 + 内容的信息行 —— 没有圆点,没有绿/黄/红分级。
- 行内容展示检测到的系统信息;**异常由该行自己兜住**(FR-6),异常信息**直接打印进那一行的内容里**。
- 第一次显示 → 初始化 → 加载数据(FR-13);缓存复用到用户刷新(FR-5)。
- 每屏条目顺序的正式定义在《[检测条目目录](05-detection-item-catalog.md)》(来自核对过的 `detect()` / `collectModels()` 顺序)。
- 过期 targetSdk 应用检查用 `QUERY_ALL_PACKAGES`,范围只限**预装 ROM 的系统应用**(绝不含用户自己装的应用)—— 见仓库根目录的隐私政策。

**验收标准**

- AC1:某行出的异常显示成那一行的错误文字;其他行不受影响(FR-6 AC1/AC2)。
- AC2:行布局支持多行标题和内容,不截断。

### FR-15 判定圆点 —— 仅 Home(P0)

- 每个 **Home** 行的**右上角有一个半透明圆点**:绿 / 黄 / 红 = **正常 / 警告 / 错误**。Others/Prop 行**没有圆点、没有分级**(纯展示,FR-14)。
- 这是人为规定的分级 —— 不是崩溃指示。**结论的含义归 FR-3 管**;圆点只是它的视觉呈现,叫什么名字等 Q9 统一。
- 判定逻辑代码里已经存在,但**没验证过,故意先不管**(Q9,「后续补充」):这条需求只固定指示器的存在、颜色、含义和位置。

**验收标准**

- AC1:每个 **Home** 行恰好一个圆点,三色 / 三态之一;Others/Prop 行不显示。
- AC2:Q9 解决之前,其他需求都不得依赖圆点的含义(哪个结果对应哪个级别)。

### FR-16 Home 数据管线(在线 / 离线 / 内置 / 合并)(P1)

数据源由设置里的网络开关(FR-8,**默认关闭**)决定:

- **在线**(开关打开):下载**服务端 json** 并缓存到**应用私有目录**。下载主机按中国大届时区选(Gitee vs GitHub raw),URL 固定用构建时的 `GIT_BRANCH`(负责人裁定,2026-09-06;过期的风险见架构篇风险表)。
- **下载或解析失败**:退回**随应用 assets 内置的 json** —— APK 里自带的普通文件;所谓「使用」它,就是**把它复制进私有缓存**(之前「压缩 / 解压」的说法是叫错了 —— 负责人裁定,2026-09-06)。
- **版本合并**:如果私有缓存已存在,拿它的版本和内置 json 的版本比 —— **按字符串字典序比较**;版本是 ISO 日期格式,字典序和时间先后等价,且有测试锁住这个格式假设(负责人裁定,2026-09-06)。**谁新用谁**:内置的比缓存新就覆盖缓存;没有缓存就直接用内置的。
- 服务端的通常更新;本地 debug 构建可以随便改数值做测试。
- 本条细化 FR-7(同步 + 私有缓存 + 离线优先);一切失败按 FR-6 退回 —— 绝没有整页错误。

**验收标准**

- AC1:开关关闭(默认)或离线时,检测完全靠私有缓存或内置 assets 运行。
- AC2:在线且服务端 json 更新 → 缓存被更新并使用。
- AC3:服务端连不上或解析不了 → 退回应用内置的;除单条隔离外,用户看不到任何失败。
- AC4:版本合并永远选缓存和内置 assets 里较新的那个(**对 ISO 日期版本串按字典序比较** —— 和时间先后等价这一点已被测试锁住),覆盖路径也一样。

### FR-17 设置页条目清单(P1)

基于 **androidx PreferenceFragmentCompat** 搭建。**点整行就触发它的动作** —— 条目不限于开关。

**显示**

- **主题**:跟随系统 / 跟随省电模式 / 强制深色 / 强制浅色。
- **滚动条模式**:无 / 普通 / 可拖动。

**功能**

- **允许网络访问**开关 —— **默认关闭**;当前**只**控制服务端 json 下载(实现 FR-8;细化 FR-16;解决 Q5)。
- **优先包名排序**开关 —— 默认关闭(关 = 按 targetSdk 排序)。只重排 Home 的「过期 targetSdk 应用」列表(2026-09-12 核对过代码,Q10 已解决)。**切换时的行为(负责人 2026-09-12 定;实现推迟到 Compose 迁移之后)**:列表为空或首次加载中 → 界面不动,数据来了按开关排;列表加载完成且非空 → 立即只重排「过期 targetSdk 应用」这一行;下拉刷新进行中 → 也立即只重排旧行,刷新成功新数据按开关排,刷新失败相当于什么也没发生、按前两条处理。

**关于**(每行点开对应的目标)

- **商店页面**(修订,负责人裁定 2026-09-12):按变体在**编译期**用变体资源定死 —— `foss` → GitHub 项目页;`firebase` → Google Play。运行时零判断,没有时区分支。
- **源代码**:GitHub 项目主页。
- **隐私政策**:托管在 GitHub 仓库里的 Google Play 数据安全 markdown(实现 FR-10 AC4)。
- **开源许可**。
