# 01 — 产品与用户

属于《[LowLevelDetector 规格文档](README.md)》(中文整理版)。

## 1. 引言

### 1.1 本文档的目的

这份文档说清楚产品**必须做什么**(功能需求)和**要做到什么程度**(非功能需求),并划清范围、排好优先级、写明每条怎么才算做完。一个特性算当前版本的、以后再做的(backlog)、还是排在路线图上的(roadmap),都以这份文档为准。

具体怎么实现这里故意不展开;那属于规格的架构部分(《[04 — 架构与决策](04-architecture-and-decisions.md)》)。

### 1.2 产品范围

LowLevelDetector 是一个**独立的 Android 应用**:查它所装的那台设备,实时、全部在手机本地完成,报告当前系统对几个关键 Android 系统特性**支持不支持**。

- 最初的目的,是帮**刷机 / MOD 社区**在刷入通用系统镜像(GSI)或第三方 ROM 之前回答一个问题:「这台手机支持 Project Treble 吗?」
- **硬件参数不是重点。** 常见的系统信息(构建信息、SoC/内存、屏幕/电池、系统属性)是后来加的辅助内容,方便用户顺手了解自己的手机。
- 当前版本**没有任何形式的数据导出** —— 结果都是当场在手机上查的,只在应用里看(NG1–NG2;以后可能做的见《[03](03-nfr-release-and-open-questions.md)》的发布范围清单)。

### 1.3 术语与缩写

| 术语 | 含义 |
|---|---|
| **Treble** | Project Treble:Android 把系统里「厂商的部分」和「Google 的部分」拆开的方案(供应商分区 + 稳定的供应商 HAL 接口)。这个应用最初就是为查它而做的。 |
| **VINTF** | Treble 用的一套兼容性清单/框架,用来检查供应商接口匹不匹配。 |
| **A/B(无缝)更新** | 双槽位分区方案:更新在后台下载安装,重启一下就切到新系统。 |
| **动态分区 / SAR** | 较新的分区方案(super 分区;system-as-root)。 |
| **AVB / dm-verity** | Android 的开机校验(Android Verified Boot)和磁盘数据的完整性校验。 |
| **GSI / GKI** | 通用系统镜像 / 通用内核镜像。 |
| **三态结果** | 每个条目的结论模型:**支持 / 不支持 / 未知**。 |
| **SSOT** | Single Source of Truth,唯一数据来源 —— 一份状态只有一个地方说了算。 |
| **UDF** | Unidirectional Data Flow,单向数据流 —— 操作从界面往数据层传,数据再流回界面,不存在两头互相改。 |
| **KMP / CMP** | Kotlin Multiplatform / Compose Multiplatform —— 以后跨平台打算用的技术。 |
| **Shizuku** | 不用完整 root,就能让应用拿到 ADB 级权限的机制。 |
| **minSdk** | 支持的最低 Android API 级别。 |
| **FOSS** | Free and Open-Source Software,自由开源软件;在本产品里指**不含专有 SDK、不收集数据**的发布版本。 |
| **变体(`firebase` / `foss`)** | 应用的两种发布版本 —— 见 FR-10(《[02 — 功能需求](02-functional-requirements.md)》)。 |

## 2. 用户与画像

### 2.1 主画像 —— 刷机爱好者(「Tinkerer」)

- **画像**:技术熟练;刷 GSI / 第三方 ROM;听得懂「分区」「槽位」「启动校验」这类词。
- **需求**:刷机前,知道设备支不支持要用的系统特性;刷机后,验证新系统实际给了什么。
- **成功**:打开应用,看懂三态答案,心里有底地去刷机。

### 2.2 次画像 —— 好奇的一般用户(「Explorer」)

- **画像**:任何想了解自己手机系统的人;可能完全不懂行话。
- **需求**:一份可信、「我的手机支持什么」的清单,看了不会一头雾水;三个状态各自是什么意思,说得直白。
- **成功**:不用另外上网查就能看懂列表;未知的条目看起来就是「未知」,绝不误导。

> 按负责人的决定,产品面向**「所有想了解自己手机系统的人」**;Tinkerer 只是起点和要求最高的那类用户。

## 3. 产品概述

### 3.1 背景

每次 Google 发布新的 Android 平台能力(Treble 就是最初的例子),刷机社区马上想知道哪些设备能用上。而答案散落在厂商页面、论坛帖子,还有翻 build.prop 的过程里。这个应用把答案收拢成应用里就能自己查的一份清单:打开应用,看列表,清楚你的系统支持什么。

### 3.2 定位声明

> 面向所有想了解自己手机系统的人 —— 尤其是刷机爱好者 —— LowLevelDetector 是一个装在手机里的检查工具,逐条列出当前系统对关键 Android 特性的支持情况,每条给一个简单的三态结论。

### 3.3 价值主张

1. **答案一眼就能看懂** —— 头部的结论不用自己去啃原始 dump 数据。
2. **查的是这台手机本身** —— 反映的是*当前装着的*系统,不是广告参数页。
3. **可以离线用** —— 网上的参考数据会缓存到本地;不开网络应用照样能用。
4. **单项坏了不连累整体** —— 一个检测项出问题,绝不会搞坏整份报告。

### 3.4 目标(当前版本)

- G1:在一批精选的 Android 系统特性上,给出可靠的三态检测结果。
- G2:转屏、界面重建之后检测结果还在,不重复加载,也不会卡死。
- G3:优先按离线设计:网上的参考数据下载后缓存到应用自己的目录里。
- G4:代码按业务分好类,人和 AI 助手都容易找到想改的地方(按 SSOT/UDF 的思路组织)。

### 3.5 非目标(当前版本)

- NG1:**不做数据导出** —— 不输出 JSON/TOML、不能分享、不能复制整份报告(系统自带的长按选文字是唯一的复制办法)。
- NG2:**不做跨平台查看器** —— 面向导出数据的 Compose Multiplatform 查看器只存在于路线图里。
- NG3:**不做单条详情页** —— 展开看详情(原始值、判定依据、大白话解释)是以后想做的,本版本没有。
- NG4:**不做跑分和深度硬件信息** —— 硬件信息只限于辅助性的「系统参数」部分。
- NG5:**不改系统** —— 严格只读,只查不动。
- NG6:**不做反检测 / 隐藏特性** —— 应用如实报告环境,不帮忙伪装。

### 3.6 路线图要点

路线图和待办只记在**一张清单**里 —— 《[03 — 非功能需求、发布与开放问题](03-nfr-release-and-open-questions.md)》的「发布范围与路线图清单」(只维护这一处,别处不重复列,免得改了一处忘了另一处)。主题一览:通用数据格式导出(RM-1)、跨平台查看器(RM-2)、更丰富的交互(BL-1/BL-3)、开放查询和 AI(RM-3/4/5,要先由 Q8 拍板),以及产品命名(Q3)。

### 3.7 变体与数据收集(构建变体)

产品有两个发布版本,**检测功能完全一样**:

| 版本 | 数据收集 | 发布渠道 |
|---|---|---|
| **`foss`** | **无** —— 不含专有 SDK,没有遥测。 | GitHub Releases。 |
| **`firebase`** | Firebase **Crashlytics**(崩溃报告)和 **Analytics**(使用数据)会收集用户信息 —— **默认开启,目前没有运行时关闭开关**(以后可能会加一个专门的遥测开关,BL-7)。 | Google Play 与 GitHub Releases。 |

应用内的网络开关(FR-8)只管**参考数据同步**,管不到 Firebase 遥测。隐私政策从应用设置页就能打开(在浏览器里打开,政策文件就放在本仓库)。完整需求见 FR-10。
